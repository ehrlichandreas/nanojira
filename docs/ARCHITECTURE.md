# Architecture

For someone opening this repository for the first time. Every claim below was
measured against the code — originally on 2026-09-23, with every "imported
by" count in § 2 re-walked mechanically again for v3.3 (DECISIONS 148,
exports, import edges, commands) — not recalled from memory or from the
task history that produced this code.

It describes the code as built, which implements spec **v3 through v3.8**
(DECISIONS 86–173): V3-1, the backlog location (`--backlog`, `NJ_BACKLOG`,
`.njrc`, in `core/config.ts`); V3-2, the layout (groups `type`, `hierarchy`
and `flat`, configurable folder names, the recursive element scan,
`layout:misplaced`, and moves in `archive`, `rm` and `doctor --fix`; in
`core/layout.ts`); V3-3, the generated `STATUS.md` (in `core/status.ts`:
written by `init` and after every successful write, checked by `doctor`,
regenerated by `--fix` step 9); and V3-4, the bookkeeping move into
`.nanojira/` and the legacy migration (`--fix` step 0; `.nanojira/config.json`
and `.nanojira/ids/` replace the v2 `.nanojira.json` and `.ids/`; a legacy
backlog is `legacy_layout` to every command but `doctor`). The two
intermediate follow-up commits (V3-2/TSK-029 findings, DECISIONS 102/105/106)
are folded into the module descriptions below rather than listed separately.

**v3.1–v3.3** added, on top of that round-one core: `NJ_AUTHOR`/`--as` (the
acting name, `core/actor.ts`), `nanojira claim`/`nanojira release`/`nanojira unarchive`
(`core/claims.ts`, `cmd-claim.ts`, `cmd-release.ts`, `cmd-unarchive.ts`),
`nanojira check`/`nanojira find` (`cmd-check.ts`, `cmd-find.ts`), batch writes,
`--id=A,B,C` (`core/batch.ts`), and the MCP wrapper, `dist/nanojira-mcp.mjs`
(`src/nanojira-mcp.ts`, `core/flag-table.ts`). Each is described in its own place
below rather than repeated here.

**v3.4–v3.5** added two more, read directly from their own source (not
re-walked backlog-mechanically like § 2's import counts): `nanojira --version`
(`core/version.ts`, read once at build time from `package.json`, embedded
into both `dist/nanojira.mjs` and `dist/nanojira-mcp.mjs`; checked before any command
dispatches, § 9), `nanojira next` (`cmd-next.ts`, § 12b — reuses `cmd-list.ts`'s
own `applyFilters`/`availableToActor` and `cmd-claim.ts`'s `claimOne`
rather than re-deriving either; adds the D156 leaf-work filter on top),
and `nanojira log` (`cmd-log.ts`, § 12c — a pure read, no `core/store.ts` import
anywhere in the file; reuses `core/claims.ts`'s generation-reading helpers
via the new `allEntriesAscending` export and adds `parseNotes` to
`core/parse.ts`). Both new commands are exposed as `nanojira-mcp` tools the same
way every other command already is, through `core/flag-table.ts`'s shared
schema generation — neither needed its own MCP-side code.

**v3.6** (DECISIONS 158, 160) is docs-and-discoverability plus two outside
teams' bug reports, not new commands:

- **Global flags before the command word** (EV-6): `nanojira.ts`'s own
  `splitCommand` scans a leading run of exactly `--backlog`/`--json`
  looking for the command word; a token that is neither stops the scan
  outright, so the whole, unmodified `argv` becomes the bare invocation's
  own arguments — no partial reordering, no silent fallback to a
  different command.
- **Per-command `--help` and did-you-mean** (EV-2/EV-3/PA-1): `core/help.ts`'s
  `commandHelp` renders one command's own synopsis and flags (reusing
  `core/flag-table.ts`'s existing schema, the same source `nanojira-mcp`'s tool
  schemas already came from); `core/suggest.ts` is new — a tiny fixed
  synonym table checked first, then an OSA (optimal-string-alignment,
  DECISIONS 160) distance against the allowed values, length-dependent
  threshold — feeding the `did you mean '<value>'?` hint onto an
  `invalid_value` failure's existing `hint`, never the message or the
  accepted vocabulary.
- **Multi-line notes** (EV-7): `core/parse.ts`'s `parseNotes` now reads a
  two-space-indented continuation line as part of the previous note
  instead of flattening it; `nanojira note` writes the same shape back out.
- **The leaf-work rule reused one more place** (EV-4/D157, on top of
  D156's rule `next` already used): `cmd-status.ts`'s bare-`nanojira` "Ready to
  work" now also filters out any element with an open child, via
  `core/derive.ts`'s shared `hasOpenChild` — `list --ready` itself is
  unchanged, a pure readiness filter with no leaf condition.
- **`next` respects an existing `assignee`** (PA-5): `cmd-next.ts`'s own
  candidate filter now also requires `assignee === '' || assignee ===
  <acting name>` — an element explicitly assigned to someone else is
  never a candidate, closing the "assign a review to the reviewer" gap
  (PA-4) without a new field.

**v3.7** (DECISIONS 163, 165, 166, 167) is a second outside-team feedback
round, again no new commands:

- **`rm`'s own flag-table entry** (163 A): `core/flag-table.ts` gains a
  `rm` spec (`id`, `file`, `cascade`) purely so `core/help.ts`'s
  `commandHelp` has one to read for `nanojira rm --help` — `nanojira-mcp.ts`'s own
  `TOOL_NAMES` still omits `rm` unconditionally, so this does not expose
  it as a tool.
- **`set --add-tags`/`--remove-tags`** (163 B): `cmd-set.ts` computes the
  resulting `tags` list itself (remove phase, then add phase, each
  checked for membership against what the other phase already produced)
  before the usual override map is built — no new `core/` module, the
  same list-field machinery `--tags=` already used.
- **The leaf-work/acceptance-quality warnings are backlog config, not
  just `core/constants.ts`'s fixed `SEVERITY` table** (163 E/F, 165, 166,
  167): `core/config.ts` is where nearly all of this round lives —
  `acceptance:no_checkbox`/`done:no_acceptance` detection is in
  `core/load.ts` (one of the nine derivers, alongside
  `incomplete:acceptance`), reusing a new span-check in `core/parse.ts`
  for the acceptance section's own content and excluding archived
  elements (DECISIONS 167), but `problems.ignore`'s validation
  and suppression, every config key's new warning-instead-of-error
  status (`config:unknown_key`/`config:unknown_code`), and `minVersion`'s
  own `needs_newer_nj` short-circuit (checked first, before any other
  config validation, so an old binary gets one specific reason rather
  than a confusing report about fields it doesn't recognise) are all
  `config.ts` additions. `cmd-doctor.ts`'s own findings loop reports the
  two new warning codes the same way it already reports every other
  backlog-level one.

**v3.8** (DECISIONS 171–173) is one new module plus additions to two
existing ones, again no new commands:

- **JSON plans for `new`/`set`** (171 A, 172, 173): `core/input.ts` is new
  and deliberately tiny — `readInputText` (stdin-or-file, the same
  convention `--description-file` already has) and `parseInputJson`, no
  plan logic at all. The whole plan engine lives in `cmd-new.ts`:
  `flattenPlan` walks an array/`children` tree into one pre-order list
  (`FlatNode[]`, each carrying its own JSON-path label), `validatePlanNode`
  checks one flattened node against the hierarchy, `ref`/`depends_on`
  rules and every ordinary `new` rule, and `emitPlanFailure` builds the
  `{ok:false, failed_at, created?, refs?}` shape. DECISIONS 173's
  forward/self-ref rule is enforced in `validatePlanNode` by checking a
  `depends_on` target's ref against `declaredSoFar` (refs seen strictly
  before this node in the same pre-order walk) rather than against the
  whole plan's ref index — the bug it fixes (live at d50b3fa) was exactly
  that the first version checked existence only, against the whole-plan
  index, so a later-declared ref still resolved. `cmd-set.ts` reuses
  `core/input.ts` for its own single-object field-map form; neither
  module gained a plan-of-its-own, by design (§ 9 "`--input`").
- **Final status releases the claim** (171 B, § 12a): `core/claims.ts`
  gains `releaseUnconditional` (and its rollback mirror, `undoRelease`) —
  called from `cmd-set.ts` and `cmd-claim.ts` (and, through `cmd-claim.ts`'s
  own `claimOne`, from `cmd-next.ts` too) whenever a guarded write's target
  status is the last configured one, regardless of who holds the claim;
  rolled back the same way `claim`'s own mirror write already was if the
  guarded write that follows fails.
- **`show --json` carries `entry`** (171 C, § 9): `cmd-show.ts` adds one
  field to its existing result, `entries.length === 1 ? { entry:
  entries[0] } : {}` — no new module, no change to `list`/`find`, which
  never spread this object in.

**v3.9** (DECISIONS 176, 177) is `set`'s first write to `parent`, plus a
third acceptance-quality warning — no new module, both additions to
existing ones:

- **`set --parent`** (176 A, 177): `cmd-set.ts` reuses `cmd-new.ts`'s own
  `checkExplicitParent` unchanged for the missing/wrong-type/archived/
  epic validation, so the two commands' error codes for the same four
  conditions can never drift apart. `reparentMove` (new, `cmd-set.ts`)
  computes the `hierarchy`-layout move — `core/layout.ts`'s
  `expectedPlace` against a shadow copy of the element with `parent`
  already swapped, never touching the real graph — and returns `null`
  under `type`/`flat`, where reparenting only ever changes the
  frontmatter. The frontmatter write (`guardedWrite`/
  `guardedWriteCatchable`) lands first; the physical move (`core/store.ts`
  `runMove`, the same primitive `archive`/`doctor --fix` already use for a
  subtree) runs only once that write has actually landed, so a crash
  between the two never leaves a half-moved element. `set --parent` never
  calls `core/load.ts`'s `descendants`, so the `childMap`/`ctx.kids` memo
  (§ 4 "Invariants", DECISIONS 81) is never populated during a reparenting
  call — the invariant that memo depends on now has its first real verb
  to watch, and holds.
- **`done:open_acceptance`** (176 B): the third deriver alongside
  `acceptance:no_checkbox`/`done:no_acceptance` in `core/load.ts`, reusing
  the same span-and-checkbox scan `core/parse.ts` already exposed for
  those two (and for `nanojira check`'s own scan) — one more count read off the
  same pass, not a second scan. `core/derive.ts`'s new
  `openAcceptanceExtra(el, cfg, isFinal)` is the one place the additive
  `open_acceptance: {unticked, total}` field is built, called from both
  `cmd-set.ts` and `cmd-claim.ts` for the same `--status=<last>` condition
  `released?` (171 B) already uses, so the two additive fields share one
  "did this call land the element in the final status" test. `doctor`'s
  and `new`/`set`/`note`/`check`'s own prose (`core/output.ts`) name the
  count via the same deriver output, never re-deriving it.

## 1. Build

```
src/nanojira.ts      (entry, ES module)            src/nanojira-mcp.ts  (entry, ES module)
 └─ imports src/commands/*.ts + src/core/*.ts       └─ imports src/core/{args,config,output,flag-table}.ts
                              │                                         │  — never src/commands/*, § 17:
                              │  esbuild --bundle --format=esm          │    one dist/nanojira.mjs child process per tool call
                              ▼                                         ▼
                       dist/nanojira.mjs                          dist/nanojira-mcp.mjs
                 (one file, checked into git, what ships, each built the same way)
```

`tools/bundle.ts` builds **two targets** from the one `src/` tree:
`dist/nanojira.mjs` (round one's CLI, importing everything under `src/commands/`
and `src/core/`) and `dist/nanojira-mcp.mjs` (§ 17, importing only the handful of
`src/core/` modules it needs to resolve a backlog, parse its own flags and
generate MCP tool schemas — `dist/nanojira-mcp.mjs` never imports a `cmd-*.ts`
module directly; a tool call spawns `dist/nanojira.mjs --json` as a child process
instead). Both are esbuild `--bundle --format=esm` outputs (addendum
9b3d0de — the earlier extensionless CommonJS `dist/nanojira`/`dist/nanojira-mcp` pair
is gone, in the repo and in every export alike), rejecting at build time any
import that is not a `node:*` built-in; both committed, both checked for
staleness by `build:check`.

`src/nanojira.ts` is a real ES module like every other file under `src/`, which a
single `src/package.json` (`{"type": "module"}`) marks for the whole
subtree — one file, not one per module directory: a directory-scoped
`package.json` would leave the entry's import boundary untyped (`import`
inside a CommonJS-resolved `.ts` file elaborates to `any`; a probe proved it
directly — a wrong-arity call across that boundary passed `tsc` with zero
errors) and Node would additionally warn `MODULE_TYPELESS_PACKAGE_JSON` on
every direct run. `node src/nanojira.ts` runs with neither warning, and the same
probe (a wrong-arity `cmdList` call in `src/nanojira.ts`) is now a `tsc` error
(TS2554), confirming the entry boundary is type-checked again. Node's native
`.ts` execution needs no build step for any of this. `core/types.ts` is the
one exception among the modules: it holds only `export
interface`/`export type` declarations and is never imported for value use —
only ever reached through `import type`, which erases completely under
`erasableSyntaxOnly`. That is not incidental: esbuild classifies any file
with its own `export` as an ES module regardless of whether the export is
type-only, and a file that is both ES-module-shaped *and* does
`module.exports = {…}` at runtime gets a broken bundle (found live during the
`import`/`export` conversion — `dist/nanojira.mjs` crashed with `NEW_FIELDS` undefined
while `tsc` reported zero errors). Keeping every real declaration in
`types.ts` sidesteps the whole class of bug.

Every module otherwise only *defines* — functions, constants, nothing runs
until a command calls into it — except `core/kernel.ts` (TSK-018, `36dd9dc`;
moved from `core/output.ts` by TSK-050, DECISIONS 231): importing it
registers a `process.stdout.on('error', …)` handler immediately, since every
command's output already flows through it and the handler has to be in place
before the first line is printed (§ 4's EPIPE decision); and `core/output.ts`,
which hands the kernel its failure decorator (`setFailureDecorator`) at load
time, so a failure result carries `files` (DECISIONS 222).

## 3. Data flow of one call

```
argv
 └─ parseArgs (args.ts)                  → { flags, positional }
     └─ context() (context.ts)
         ├─ findBacklog(flags) + loadConfig (config.ts)
         └─ loadBacklog (load.ts)
             ├─ loadElement × N          — nine derivers, Skeleton→…→Element
             └─ deriveGraph × 1          — eleven steps over the whole set
     └─ cmdX(flags, …) (cmd-*.ts)        — resolves target, reads/writes,
                                           re-derives after a write
         └─ out / writeFeedback / emitWriteResult / emitFailure (output.ts)
```

`loadElement` runs once per file and only ever sees that one file; `deriveGraph`
runs once per loaded set and is the only place duplicate IDs, parent/depends_on
cycles, and open-children checks exist — a single element can never detect
these on its own. A write command (`set`, `note`, `archive`, `new`) calls
`deriveGraph` a second time after writing, on the changed array, so the
printed feedback reflects the post-write graph, not the pre-write one.

## 5. Safety net

Three independent nets; the team refers to them as the Oracle, the Corpus,
and the Blindness matrix (Orakel/Korpus/Blindheits-Matrix in team shorthand).

**Oracle** (`test/`, files derived only from `SPECIFICATION.md` in `ac/`,
`edge/`, `fault/`, `stress/` and `tools/` — run via `npm test`, whose summary
counts them): black-box,
spawns `nanojira`/`dist/nanojira.mjs` (and, for the MCP suites, `dist/nanojira-mcp.mjs`), asserts
exit code/stdout/stderr/file bytes, never reads implementation source.
Reach for it to answer "is this still spec-conformant" — it is what
CI-equivalent gating runs by default.

**Corpus** (`tools/refactor-harness`, `record`/`verify` against the frozen
`c7-baseline` tag): answers a different question — "does this behave
*exactly* like the pre-refactor revision", including things the spec never
pins (byte order of `_problems`, the sequence `fixed[]` reports actions in).
Run `verify` by hand after any change that is supposed to be behaviour-
preserving; it is not part of `npm test` because it is slow (4–6 minutes,
measured) and only meaningful for refactors, not features.

**Blindness matrix** (`tools/blindness-matrix`): answers a third question —
"if I mutate this one line, does *any* suite in the other two nets go red?"
A mutant that survives green is a documented gap, not a bug. Run it after
touching test infrastructure itself (a needle can silently stop matching, as
happened during this project's ES-module conversion) or before trusting a
"no regression" claim about coverage, since neither the oracle nor the corpus
can tell you that on their own.
