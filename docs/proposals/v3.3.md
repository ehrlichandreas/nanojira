(DECISIONS 144) — not part of the specification.** Written against spec
v3.2 as of `c8eeac3` (v3.2 functionally complete: `nj check`, stale

the spec's own register, so accepted text can be moved over with minimal
editing. Section numbers (§ n) refer to that spec. Per DECISIONS 122, this
is the fifth item the user released, deliberately run as its own project
after v3.2 finished, with its own written proposal before anything is
promoted. Every open question from the first draft (`0fba429`) is ruled
(DECISIONS 144), one of them (B-1) deviating from the Oracle's own

promotion follows that review.

It picks up the last item of § 16 "Not in Round One": an MCP wrapper, so an
MCP-speaking agent can call `nj` as structured tools instead of shelling
out to a CLI and parsing `--json`.

Written by the oracle author of AC-21…AC-31. By the project's rule
(DECISIONS 86: author ≠ implementer ≠ verifier), the author of this text
does **not** write its tests.

**Every open question below is now RULED (DECISIONS 144)**, marked in
each section for traceability, same as v3.2's rulings (DECISIONS 123)
were. Unlike v3.1/v3.2, this round adds **no new CLI behaviour**: every
section here is about a *new, separate* artifact (an MCP server) that
calls `nj` the way any other caller already can. `dist/nj`'s flags, JSON
shapes and exit codes keep their meaning — the CLI's own contract (§ 9) is
consumed, not extended (§ A/§ D) — even where moving its argument parsing
onto a shared flag table (§ C-2) touches its internals: that move is
required to be byte-identical in its observable behaviour, proven by the
replay gate against `c7`, not merely asserted.

---

## Motivation

An MCP client (an agent's own harness) that wants to work a NanoJira
backlog today has one option: shell out to `nj`, parse stdout, branch on
exit codes and `--json` fields by hand. That already works — it is the
same contract every test in this project drives — but MCP gives agents a
more native integration: declared tool schemas, structured results, and
(depending on the client) better tool-call ergonomics than freeform shell
invocation. An MCP wrapper is a second **front end** on the exact same
backend: it must not become a second, looser contract that drifts from the
one § 9 already guarantees.

## A. Shape

```
dist/nj-mcp [--backlog=<path>]
```

A **separate entry point**, its own bundled executable (parallel to
`dist/nj`), speaking MCP over stdio: the MCP client spawns it as a child
process (the standard local-server pattern — the same relationship a test
in this project already has with `dist/nj` itself) and communicates via
newline-framed JSON-RPC on stdin/stdout, per the MCP spec's stdio
transport. Nothing on stdout is ever human prose or a startup banner —
stdio carries protocol frames only, the same discipline § 9 already holds
for `--json`'s stdout purity, just absolute instead of conditional on a
flag.

**Backlog resolution — RULED (DECISIONS 144, A-1): identical to today,
once, at startup.** `nj-mcp` resolves its backlog exactly the way every
command does today (§ 4: `--backlog`, then `NJ_BACKLOG`, then the nearest
`.njrc`, then a `backlog/` folder, searched from the process's cwd upward)
and serves **that one backlog** for the life of the process. The
alternative — a `backlog` parameter on every tool call, so one server could serve many
backlogs — is rejected: it would mean re-running the whole location search
(and the ownership-sensitive `.njrc` machinery, § 4) on every call instead
of once at startup, and it does not match how an MCP client is normally
configured (one server process per project root, the same model
filesystem- and git-flavoured MCP servers already use). A caller who
genuinely wants two backlogs runs two `nj-mcp` processes, exactly as they
would run `nj` from two different working directories today.

## B. Dependencies — RULED (DECISIONS 144, B-1), deviating from the Oracle's recommendation

`nj` today ships as one bundled file with **no runtime dependency and no
`node_modules`** (`package.json`, `tools/bundle.js`; DECISIONS 83: build
tooling may use its own libraries, the runtime artifact may not). The
Oracle's first draft recommended bundling the official
`@modelcontextprotocol/sdk` the way `esbuild` itself is already bundled
away as a `devDependency`. **The lead ruled otherwise: `nj-mcp` hand-rolls
its own small stdio JSON-RPC/MCP subset, genuinely zero new dependencies,
even at build time** — nj's defining property is one bundled file with no
dependency tree at all, and the SDK would add a real dependency tree for
what is, in protocol terms, a few hundred lines. Bundling it away still
leaves that tree sitting in `package-lock.json`, in every future audit,
and in every future "what does this pull in" question — a cost the
one-file property was specifically designed to avoid, not merely to hide.

**What the hand-rolled subset covers, exactly:**

- **Methods:** `initialize`, `tools/list`, `tools/call`. Nothing else —
  no `resources/*`, `prompts/*`, `completion/*`, `logging/*` (§ G already
  rules those out of scope for v3.3).
- **Required notifications:** `notifications/initialized` (sent by the
  client after a successful `initialize` response, per the MCP handshake)
  is accepted and otherwise ignored — `nj-mcp` has no state that depends
  on it, since every tool call is already a fresh `nj` process (§ D).
  `notifications/cancelled` is accepted and a no-op: a spawned `nj`
  process is not killed mid-call by this round (cancelling a write
  mid-flight is exactly the kind of half-done state § 12's
  compare-before-write exists to prevent reaching in the first place).
- **Protocol version: pinned to one stated version**, named in the
  implementation (the MCP version current when `nj-mcp` ships).
  `initialize`'s response always declares that one version, never
  negotiates a fallback. **A version mismatch is the client's decision to
  make**, exactly as the MCP handshake already specifies: the client sees
  the server's declared version in the response and disconnects if it
  cannot work with it. `nj-mcp` does not detect or special-case a
  mismatch itself — there is nothing for it to do differently, since it
  only ever speaks the one version it declared.
- **An unknown method** (anything outside the three above, or a malformed
  JSON-RPC envelope) gets the standard JSON-RPC error object, `{code:
  -32601, message: "Method not found"}` for an unknown method (`-32700`/
  `-32600` for a parse/invalid-request failure) — never a crash, never a
  silently dropped request.

**Compatibility risk is answered by tests, not by the SDK's runtime
presence**: the oracle drives `dist/nj-mcp` using the **official MCP SDK's
client**, added as a `devDependency` for tests only, bundled into nothing,
never shipped (the same `devDependency`-but-not-shipped treatment
`esbuild`/`typescript` already get, § 13's comfort-bar precedent for
"build tooling may use libraries the runtime may not"). A real client
talking the real protocol, against the hand-rolled server, is the
functional test that a from-scratch implementation needs and a bundled
SDK would not have required as urgently — this project already prefers
measured verification over trusting a library's own correctness (§ 12's
fault hooks exist for exactly this reason).

**B-2 — RULED (DECISIONS 144): reduces to the wrapper's own size and cold
start.** With no SDK bundled, there is no third-party bundle-size question
left to answer — only `nj-mcp`'s own size (the hand-rolled subset plus the
existing `src/core`/`src/commands` it calls into) and its cold-start time.
**Measure and report both**, the same way every other size/latency claim
in this project is a number, not an assumption; no target is set here
because there is no comparable existing artifact to set one against (§ 13's
comfort bar was itself a first measurement before it became a target).

## C. Tool surface

**Which commands become tools — RULED (DECISIONS 144, C-1).** The tool
list is exactly: `list`, `show`, `find`, `tree`, `new`, `set`, `note`,
`check`, `claim`, `release`, `archive`, `unarchive`, `doctor`. **`rm`
(including `--cascade`) is omitted entirely in v3.3** — not merely gated,
absent from `tools/list` regardless of the safety flag (§ E), on the same
reasoning the first draft gave for `--cascade` alone: a tool call is not
the visible, deliberate CLI step a destructive, hard-to-undo-by-inspection
deletion deserves. **`archive`/`unarchive` are offered, ungated**: both
are reversible (§ 11a exists precisely because an archive is not a
one-way door), unlike `rm`, so they do not need the same caution a
genuine deletion does. **`doctor --fix` exists only when the server was
started with `--allow-destructive`** (§ E) — it is the one tool on this
list whose effect is not trivially reversible by a second call the way
`archive`/`unarchive` are mutual inverses of each other.

**Input schemas — RULED (DECISIONS 144, C-2): generated from a flag table
shared with the CLI's own parser.** Each tool's JSON Schema comes from the
same per-command flag table the CLI's argument parser reads to answer "is
this flag known for this command" (§ 9) — not a hand-maintained parallel
schema file, which this project has already paid for the drift cost of
once (the `ac-17`/`ac-24` `COMMANDS` arrays that silently excluded
`unarchive`/`claim`/`release`/`check` until D128 swept them). **Moving the
CLI's own parser onto this shared table is therefore part of this work,
not a side effect of it** — and that move must leave the CLI's observable
behaviour **byte-identical**: same flags accepted, same validation, same
error codes, same everything a caller could observe. This is not merely
asserted; **the replay gate against `c7-baseline` proves it** (AC-36,
§ 15 below) — the exact mechanism this project already uses to catch any
other silent behavioural drift.

**Results — exactly the existing `--json` shapes, no second contract.** A
tool call's result **is** the object `nj --json` already returns for the
equivalent invocation — as the MCP result's `structuredContent` where the
SDK supports it, with a JSON-stringified text block as the accompanying
human-readable fallback. Nothing is renamed, nothing is re-shaped. This is
the central design constraint of the whole proposal: an agent that already
knows § 9's JSON contract from using the CLI directly needs to learn
nothing new to read an MCP tool's result.

**Errors — RULED (DECISIONS 144, C-3): `isError: true`, the unmodified
JSON body.** A command failure (`refused:claimed`, `invalid_value`, …) is
reported as an MCP tool error (`isError: true`), carrying the **same**
`{ok: false, error, hint?}` body as content — never silently folded into
a "successful" call whose content merely says `ok: false`, and the code
is **never lost**. This uses MCP's own error-signalling idiom (a client
can branch on `isError` without inspecting content first) while keeping
the closed code table (§ 9) exactly as useful as it is on the CLI.

**Batch writes.** `--id=A,B,C` maps to a single string-typed `id`
parameter, accepting a comma-joined list exactly as the CLI does — not a
JSON array. One less translation layer, one less shape that could
silently diverge from what `nj --id=A,B,C` itself accepts (§ 9 "Batch
writes"). The wrapper result shape is `{ok, results: […]}` exactly as a
batch CLI call already returns.

**The acting name — RULED (DECISIONS 144, C-4): a per-call `as` input
parameter.** `note`, `claim` and `release` each gain an `as` input,
defaulting to the server's own `NJ_AUTHOR` (from the launching
environment) when the caller omits it — the exact `--as`-outranks-
`NJ_AUTHOR` precedence § 9 already has, exposed per call instead of per
process, so one `nj-mcp` serving several conceptual actors over its
lifetime does not misattribute every note/claim to whichever actor the
server happened to be launched for. **Validation is the same `--as`
validation already has** (DECISIONS 119: non-empty after trimming, a
single line, no `:`) — an invalid `as` is `invalid_value`, nothing
written, exactly as an invalid `--as` is on the CLI; no new validation
rule is introduced for this new surface.

## D. Architecture — RULED (DECISIONS 144, D-1/D-2)

**One `nj` process per tool call.** `nj-mcp` is a thin
protocol/argument-translation layer: a tool call becomes exactly the
argument list the equivalent CLI invocation would have, run against
`dist/nj --json` as a child process, with its parsed stdout handed back as
the tool result. The alternative — importing `src/commands`/`src/core`
directly and calling them in-process — would be faster (no process-spawn
overhead per call) but needs those modules refactored first: today every
command module is CLI-shaped (parses `argv`, prints, calls `process.exit`),
not library-shaped (take structured input, return a value, never exit the
host process). That refactor touches every command and is its own
project-sized risk, independent of MCP.

Process-per-call buys three things at once: **zero duplicated logic**
(the JSON `nj-mcp` returns *is* `dist/nj --json`'s own output, byte for
byte, because it is the same binary, not a reimplementation of it),
**zero new concurrency model** (every tool call goes through § 12's
compare-before-write and § 12a's claim CAS exactly as any other concurrent
CLI invocation already does — nothing about `nj-mcp` existing weakens or
bypasses it, because nothing about it is a different code path), and
**perfect contract fidelity by construction**, which is the whole point of
§ C's "no second contract" rule. The cost is spawn latency per call.

**D-2: the budget is the per-call overhead over a direct CLI call, p50 ≤
50 ms.** Measured as the difference between a tool call's wall-clock time
and `dist/nj --json`'s own wall-clock time for the identical invocation,
median over a representative run — the overhead `nj-mcp` itself adds on
top of the CLI call it wraps, not the CLI call's own cost (which § 13
already measures and budgets separately).

## E. Safety — RULED (DECISIONS 144, E-1)

**A single `--allow-destructive` start flag, gating only `doctor --fix`.**
`rm` is not on the tool list at all (§ C-1), and `archive`/`unarchive` are
offered ungated (reversible, § C-1) — so of the candidates the first draft
weighed, only `doctor --fix` needs a gate at all. `doctor --fix` is
**absent from `tools/list`** unless `nj-mcp` is launched with
`--allow-destructive`. The gate is a launch-time decision the *operator's*
MCP client configuration makes, never something a tool call itself can
toggle — an agent that could flip its own safety gate would not have one.

**Path confinement.** No new mechanism is needed: `nj-mcp` is pinned to
one resolved backlog for its whole life (§ A), and every tool call's
`--id`/`--file` addressing goes through the exact same resolution and
refusal rules the CLI already enforces (§ 9) — there is no per-call
`--backlog` override to add a loophole with, because § A's ruling already
keeps that parameter off the per-call surface entirely.

## F. Testing

**A stdio driver, black box, like every other suite here, driven by the
real MCP SDK client (§ B).** A small harness in `test/` that launches
`dist/nj-mcp` as a child process and drives it through the **official MCP
SDK's client** (the test-only `devDependency` § B names), so compatibility
is checked against the real protocol library, not against the test's own
re-implementation of what a client should send. It asserts: `initialize`
declares the one pinned protocol version (§ B); the exposed tool list
matches § C/§ E exactly (`doctor --fix` absent unless `--allow-destructive`
was given, `rm` absent unconditionally); each tool's result, run against a
fixture, is **byte-identical** to `dist/nj --json`'s own output for the
equivalent CLI invocation (making § C-2's "no second contract" rule
directly testable, not just asserted in prose); error results carry
`isError: true` with the unmodified `{ok:false, error, hint?}` body; batch
writes and the `as` parameter (incl. its D119 validation) behave exactly
as § C describes; an unknown method and a malformed envelope get the
JSON-RPC error codes § B names, never a crash.

**The replay gate.** This project already replays a frozen call corpus
against each accepted baseline to catch silent drift (`oracle-frozen-N`,
`cN-baseline`). AC-36 (below) extends it: the C-2 flag-table move that the
CLI's own parser goes through must replay against `c7-baseline`
byte-identically — the exact mechanism that already catches any other
silent behavioural drift, applied to this refactor specifically. A
second, smaller extension — a handful of representative calls driven
through `nj-mcp` instead of the raw CLI, diffed against the same corpus's
CLI-direct results — catches an accidental transformation introduced at
the protocol layer that the CLI-only replay could never see.

**Performance.** Measure `nj-mcp`'s own size and cold-start time (§ B-2,
no target set) and its added per-call latency (§ D-2, p50 ≤ 50 ms over a
direct CLI call), on a quiet machine, the same before/after methodology
§ 13 already uses for `STATUS.md`'s cost.

## G. What stays out

- **MCP resources and prompts.** Only tools, this round. `list`/`show`/
  `find` already give an MCP client read access to everything a "resource"
  capability would expose; no concrete workflow has asked for subscription
  semantics a tool call cannot already serve.
- **Any transport but stdio.** No HTTP/SSE. A network-reachable transport
  implies a multi-client, multi-tenant story and an authentication layer
  this project's trust model was never built for (§ 6: names are labels,
  not identities; § 9: no registry, no authentication for the acting
  name). Stdio's "the client already trusts whatever spawned it" model is
  the only one consistent with that.
- **Authentication.** Same reasoning: the spawning process (the agent
  harness) is the trust boundary, exactly as it already is for the plain
  CLI.

### Touches — RULED (DECISIONS 144): "§ 17. MCP Interface"

§ 3 (ships a second artifact, `dist/nj-mcp`, alongside `dist/nj`), § 16
(the "MCP wrapper" line is removed, now addressed), a **new § 17. MCP
Interface**, naming the tool surface, the hand-rolled protocol subset and
its pinned version (§ B), the schema-generation table shared with the CLI
parser (§ C-2), the error-mapping rule (§ C-3) and the safety gate (§ E).
No existing section's *meaning* changes — `dist/nj` keeps every flag,
shape and exit code it has — but § 9's own text may gain a cross-reference
once the CLI parser moves onto the shared flag table (§ C-2), since that
table becomes something § 9 can point at instead of only describe in
prose.

No existing acceptance criterion changes. New ones, numbered after AC-31:

32. **MCP tool surface.** `nj-mcp`'s `tools/list` names exactly `list`,
    `show`, `find`, `tree`, `new`, `set`, `note`, `check`, `claim`,
    `release`, `archive`, `unarchive`, `doctor`; `rm` is never present;
    `doctor --fix` is present only when the server was launched with
    `--allow-destructive`, absent otherwise.
33. **Result fidelity.** For every exposed tool, a `tools/call` result's
    content is byte-identical to `dist/nj --json`'s own output for the
    equivalent CLI invocation against the same fixture — success and
    failure alike, including `isError` reflecting exit 1/2 and the
    untouched `{ok, error, hint?}` body on failure.
34. **Backlog resolution and confinement.** `nj-mcp` resolves its backlog
    at startup by the same rules as the CLI (§ 4), serves only that
    backlog for its whole life, and takes no per-call backlog override.
35. **Batch and acting-name parity.** A tool call with a comma-joined `id`
    produces the same `{ok, results}` wrapper a CLI batch write would; an
    `as` parameter on `note`/`claim`/`release` outranks the server's own
    `NJ_AUTHOR`, validated exactly as `--as` is (D119), exactly as `--as`
    outranks it on the CLI.
36. **CLI behaviour is unchanged by the flag-table move (C-2).** Moving
    the CLI's own argument parser onto the shared flag table that
    `nj-mcp`'s schemas are also generated from changes no observable CLI
    behaviour: replayed against `c7-baseline`, the CLI produces
    byte-identical output, call for call, before and after the move.

- **C-2 RULED:** MCP input schemas are generated from a flag table shared
