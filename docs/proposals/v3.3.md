required to be byte-identical in its observable behaviour, proven by the
replay gate against `c7`, not merely asserted.

---

## Motivation

An MCP client (an agent's own harness) that wants to work a NanoJira
backlog today has one option: shell out to `nj`, parse stdout, branch on
exit codes and `--json` fields by hand. That already works — it is the
same contract every test in this project drives — but MCP gives agents a
more native integration: declared tool schemas, structured results, and
(depending on the client) better tool-call ergonomics than freeform shell
invocation. An MCP wrapper is a second **front end** on the exact same
backend: it must not become a second, looser contract that drifts from the
one § 9 already guarantees.

## A. Shape

```
dist/nj-mcp [--backlog=<path>]
```

A **separate entry point**, its own bundled executable (parallel to
`dist/nj`), speaking MCP over stdio: the MCP client spawns it as a child
process (the standard local-server pattern — the same relationship a test
in this project already has with `dist/nj` itself) and communicates via
newline-framed JSON-RPC on stdin/stdout, per the MCP spec's stdio
transport. Nothing on stdout is ever human prose or a startup banner —
stdio carries protocol frames only, the same discipline § 9 already holds
for `--json`'s stdout purity, just absolute instead of conditional on a
flag.

**Backlog resolution — RULED (DECISIONS 144, A-1): identical to today,
once, at startup.** `nj-mcp` resolves its backlog exactly the way every
command does today (§ 4: `--backlog`, then `NJ_BACKLOG`, then the nearest
`.njrc`, then a `backlog/` folder, searched from the process's cwd upward)
and serves **that one backlog** for the life of the process. The
alternative — a `backlog` parameter on every tool call, so one server could serve many
backlogs — is rejected: it would mean re-running the whole location search
(and the ownership-sensitive `.njrc` machinery, § 4) on every call instead
of once at startup, and it does not match how an MCP client is normally
configured (one server process per project root, the same model
filesystem- and git-flavoured MCP servers already use). A caller who
genuinely wants two backlogs runs two `nj-mcp` processes, exactly as they
would run `nj` from two different working directories today.

**Confinement is mechanical, not incidental — RULED (DECISIONS 145, item
b).** The review asked whether a spawned child re-runs § 4's own search
from its own cwd/environment (which could, in principle, land on a
*different* backlog than the one `nj-mcp` resolved at startup, if
anything in the search path changed in between — a `.njrc` edited, a
symlink swapped, even the swap race this project just spent two rounds
hardening against). It does not: **every spawned `dist/nj` child is
given `--backlog=<the server's own resolved path>` explicitly** (§ D),
the one flag that already stops the search before it starts (§ 4). The
"one backlog for the life of the process" guarantee above is therefore
enforced by what argument list `nj-mcp` builds for every call, not by
hoping the search re-resolves the same way twice.

## B. Dependencies — RULED (DECISIONS 144, B-1), deviating from the Oracle's recommendation

`nj` today ships as one bundled file with **no runtime dependency and no
`node_modules`** (`package.json`, `tools/bundle.js`; DECISIONS 83: build
tooling may use its own libraries, the runtime artifact may not). The
Oracle's first draft recommended bundling the official
`@modelcontextprotocol/sdk` the way `esbuild` itself is already bundled
away as a `devDependency`. **The lead ruled otherwise: `nj-mcp` hand-rolls
its own small stdio JSON-RPC/MCP subset, genuinely zero new dependencies,
even at build time** — nj's defining property is one bundled file with no
dependency tree at all, and the SDK would add a real dependency tree for
what is, in protocol terms, a few hundred lines. Bundling it away still
leaves that tree sitting in `package-lock.json`, in every future audit,
and in every future "what does this pull in" question — a cost the
one-file property was specifically designed to avoid, not merely to hide.

**`nj-mcp` is a dual-era server — RULED (DECISIONS 145), after the
Verifier's review (`bb7bd86`) fetched the currently-published MCP spec
(revision `2026-07-28`) and found the proposal's text described an older
versioning model.** That spec, read live for this ruling (not from
training-cutoff memory — it post-dates it), replaced the single
session-wide `initialize` handshake with per-request versioning: every
request now declares its protocol version in its own `_meta`, and the
spec names three tiers — **modern** (`2026-07-28` and later, per-request
`_meta` versioning, no handshake), **legacy** (`2025-11-25` and earlier,
the `initialize` handshake this proposal already described), and
**dual-era** (an implementation speaking both). The spec's own
compatibility matrix lists a **modern-only client against a legacy-only
server as "Fails."** — the exact combination the first draft's § B
would have left unsupported had it shipped unchanged.

**`nj-mcp` answers both eras, pinned to one named revision each:
`2026-07-28` (modern) and `2025-11-25` (legacy)** — the latest revision
on each side of the spec's own terminology cutoff. This costs a little
more protocol code than the legacy-only subset the first draft described,
but does not shut out clients as they move to the modern era; a
modern-only client is exactly the population the compatibility matrix
says a legacy-only `nj-mcp` would have failed outright.

**What the dual-era subset covers, exactly:**

- **`server/discover` — implemented, not merely left to the unknown-method
  fallthrough.** The spec: "Servers **MUST** implement
  [`server/discover`](/specification/2026-07-28/server/discover)." A
  request names it as the method, carrying `_meta` only (no body
  parameters); `nj-mcp`'s response is a `DiscoverResult`:
  `{resultType: "complete", supportedVersions: ["2026-07-28",
  "2025-11-25"], capabilities: {tools: {}}, _meta:
  {"io.modelcontextprotocol/serverInfo": {name: "nj-mcp", version:
  "<nj-mcp's own version>"}}}` — `capabilities` names only `tools`
  (§ G already excludes resources/prompts/logging; `serverInfo` is
  descriptive only, per the spec's own note that it is "not verified by
  the protocol" and must not drive client behaviour). This single,
  correctly-answered method is what makes `nj-mcp` interoperate with a
  dual-era client's own stdio backward-compatibility probe (the spec's
  compatibility matrix, "Dual-era client, Modern server: Works — the
  stdio probe returns a `DiscoverResult`"), rather than relying on the
  weaker "any unknown-method error looks legacy enough" fallback the
  first draft's design would have produced by accident.
- **Era detection is per-request, exactly as the spec describes it**:
  "A request carrying modern per-request `_meta` is served statelessly
  according to this revision. An `initialize` request selects legacy
  semantics." `nj-mcp` needs no separate detection step — the two eras
  are simply two different request shapes it recognises: a request
  (`server/discover`, `tools/list`, `tools/call`) whose `_meta` carries
  `io.modelcontextprotocol/protocolVersion` is modern; a literal
  `initialize` request (no such `_meta` key) is legacy. A single running
  `nj-mcp` process may serve both kinds of request across its lifetime —
  the spec explicitly permits this ("A dual-era server **MAY** serve
  both eras concurrently on the same endpoint or process"), though in
  practice one client talks one era for the process's whole life.
- **Methods, total:** `server/discover`, `initialize`, `tools/list`,
  `tools/call`. Nothing else — no `resources/*`, `prompts/*`,
  `completion/*`, `logging/*` (§ G).
- **An unsupported protocol version (modern path only)** — a request
  whose `_meta` names a version `nj-mcp` does not implement — gets the
  spec's own `UnsupportedProtocolVersionError`, JSON-RPC code `-32022`,
  `data: {supported: ["2026-07-28", "2025-11-25"], requested:
  "<whatever was asked>"}`. The client is expected to retry with one of
  the listed `supported` versions; `nj-mcp` does nothing more
  elaborate than that one response.
- **Legacy `initialize`: unchanged from the first draft, now dated.**
  `initialize`'s response declares exactly `2025-11-25` and the
  `capabilities` object (`{tools: {}}`, same as `server/discover`'s —
  the review flagged this as a silent gap in the first draft; it is not
  silent here). A version mismatch on the legacy path is still the
  client's decision: it sees the declared revision in the response and
  disconnects if it cannot work with it — `nj-mcp` does not special-case
  a legacy mismatch itself, the spec gives legacy clients no
  fall-forward mechanism to react to anyway.
- **Required legacy notifications, unchanged:**
  `notifications/initialized` (accepted, ignored — `nj-mcp` has no
  session state that depends on it, since every tool call is already a
  fresh `nj` process, § D) and `notifications/cancelled` (accepted, a
  no-op — confirmed spec-compliant by the review: "Servers... **SHOULD**
  not send a response for the cancelled request" is a SHOULD, not a
  MUST, and the baseline protocol already tolerates a server finishing
  anyway; `nj-mcp`'s own reason — killing a write mid-flight is exactly
  the half-done state § 12's compare-before-write exists to prevent — is
  additional justification, not a requirement).
- **An unknown method, in either era** (anything outside the four
  methods above, or a malformed JSON-RPC envelope) gets the standard
  JSON-RPC error object: `-32601` ("Method not found") for an unknown
  method, `-32700`/`-32600` for a parse/invalid-request failure — never
  a crash, never a silently dropped request.
- **`-32602` (Invalid params) vs. a tool result with `isError` —
  RULED (DECISIONS 145, item d):** a `tools/call` whose `arguments`
  fail the tool's own declared JSON Schema (a required field missing, a
  field of the wrong type) is rejected **before any `dist/nj` child is
  spawned**, as a JSON-RPC-level `-32602` error — this is structural
  malformation of the *call itself*, the same class of problem
  `-32700`/`-32600` already answer for the envelope one level up. A call
  that **passes** schema validation but whose content the CLI itself
  then rejects (`invalid_value` for a bad `--status`, `refused:archived`,
  `not_found`, …) is never a protocol-level error — it surfaces exactly
  as § C-3 already describes, a tool result with `isError: true` and the
  unmodified `{ok: false, error, hint?}` body. The split is: **shape**
  failures are `-32602`, **content** failures are `isError` — the same
  CLI-shaped reason `missing_argument`/`unknown_field` on the CLI itself
  precede every semantic check (§ 9), just split across the protocol
  boundary instead of inside one process.

**Compatibility risk is answered by tests exercising both eras, not by
the SDK's runtime presence**: the oracle drives `dist/nj-mcp` using the
**official MCP SDK's client**, added as a `devDependency` for tests only,
bundled into nothing, never shipped (the same `devDependency`-but-not-
shipped treatment `esbuild`/`typescript` already get, § 13's comfort-bar
precedent for "build tooling may use libraries the runtime may not"). The
SDK client's own dual-era support (probing `server/discover`, falling
back to `initialize` when appropriate) is exactly the real-client
behaviour § F's harness needs to drive both paths — a from-scratch
hand-rolled server benefits more from this than a bundled-SDK server
would have, since there is no library correctness to lean on; this
project already prefers measured verification over trusting a library's
own correctness (§ 12's fault hooks exist for exactly this reason).

**B-2 — RULED (DECISIONS 144): reduces to the wrapper's own size and cold
start.** With no SDK bundled, there is no third-party bundle-size question
left to answer — only `nj-mcp`'s own size (the hand-rolled subset plus the
existing `src/core`/`src/commands` it calls into) and its cold-start time.
**Measure and report both**, the same way every other size/latency claim
in this project is a number, not an assumption; no target is set here
because there is no comparable existing artifact to set one against (§ 13's
comfort bar was itself a first measurement before it became a target).

## C. Tool surface

**Which commands become tools — RULED (DECISIONS 144, C-1).** The tool
list is exactly: `list`, `show`, `find`, `tree`, `new`, `set`, `note`,
`check`, `claim`, `release`, `archive`, `unarchive`, `doctor`. **`rm`
(including `--cascade`) is omitted entirely in v3.3** — not merely gated,
absent from `tools/list` regardless of the safety flag (§ E), on the same
reasoning the first draft gave for `--cascade` alone: a tool call is not
the visible, deliberate CLI step a destructive, hard-to-undo-by-inspection
deletion deserves. **`archive`/`unarchive` are offered, ungated**: both
are reversible (§ 11a exists precisely because an archive is not a
one-way door), unlike `rm`, so they do not need the same caution a
genuine deletion does. **`doctor --fix` exists only when the server was
started with `--allow-destructive`** (§ E) — it is the one tool on this
list whose effect is not trivially reversible by a second call the way
`archive`/`unarchive` are mutual inverses of each other.

**Input schemas — RULED (DECISIONS 144, C-2): generated from a flag table
shared with the CLI's own parser.** Each tool's JSON Schema comes from the
same per-command flag table the CLI's argument parser reads to answer "is
this flag known for this command" (§ 9) — not a hand-maintained parallel
schema file, which this project has already paid for the drift cost of
once (the `ac-17`/`ac-24` `COMMANDS` arrays that silently excluded
`unarchive`/`claim`/`release`/`check` until D128 swept them). **Moving the
CLI's own parser onto this shared table is therefore part of this work,
not a side effect of it** — and that move must leave the CLI's observable
behaviour **byte-identical**: same flags accepted, same validation, same
error codes, same everything a caller could observe. This is not merely
asserted; **the replay gate against `c7-baseline` proves it** (AC-36,
§ 15 below) — the exact mechanism this project already uses to catch any
other silent behavioural drift.

**The generator reads the per-command table only — RULED (DECISIONS 145,
item a).** `src/core/args.ts` already separates "global" controls
(`--backlog`, `--json`, and the rest of § 9's control-flag list) from
each command's own flag table: `--backlog` is injected into validation
through a module-level `GLOBAL_CONTROLS` constant, combined with a
command's table only inside `checkFlags` itself, never a member of the
per-command table proper. **The schema generator reads strictly that
per-command table — never `GLOBAL_CONTROLS`** — so `--backlog` is
excluded *by construction*, not by a special-cased filter someone has to
remember to keep in sync. `--json` is excluded the same way, for a
different, simpler reason: it is meaningless for a tool whose result
(§ C) is always structured content, never a human-readable toggle. This
removes the one way § C-2's own "generate from the CLI's own validation
table" design could have silently reopened § A's per-call `backlog`
rejection, had an implementer instead read it as "every flag `checkFlags`
would accept" rather than strictly the per-command table.

**AC (new, § 15 below): no generated tool schema names a `backlog`
field.** Checked mechanically against every tool's generated schema, not
asserted from the source-separation argument above alone — the same
"don't just reason about it, test it" discipline this project already
applies everywhere else. `--file`, where a command already has it,
**does** remain in that tool's schema (it is a legitimate per-command
field, already confined to the backlog by `resolveTarget`'s own lookup
into the already-scanned element set, never an arbitrary-path primitive
— confirmed directly in `src/core/context.ts`, not merely asserted): the
AC is about the absence of a *new* escape hatch, not about narrowing
`--file`'s existing, already-confined behaviour.

**Results — exactly the existing `--json` shapes, no second contract.** A
tool call's result **is** the object `nj --json` already returns for the
equivalent invocation — placed in the MCP result's `structuredContent`
field (the hand-rolled server, § B, sets this itself; there is no SDK on
the server side to defer to), with a JSON-stringified text block as the
accompanying human-readable fallback. Nothing is renamed, nothing is
re-shaped. This is
the central design constraint of the whole proposal: an agent that already
knows § 9's JSON contract from using the CLI directly needs to learn
nothing new to read an MCP tool's result.

**Errors — RULED (DECISIONS 144, C-3): `isError: true`, the unmodified
JSON body.** A command failure (`refused:claimed`, `invalid_value`, …) is
reported as an MCP tool error (`isError: true`), carrying the **same**
`{ok: false, error, hint?}` body as content — never silently folded into
a "successful" call whose content merely says `ok: false`, and the code
is **never lost**. This uses MCP's own error-signalling idiom (a client
can branch on `isError` without inspecting content first) while keeping
the closed code table (§ 9) exactly as useful as it is on the CLI.

**Batch writes.** `--id=A,B,C` maps to a single string-typed `id`
parameter, accepting a comma-joined list exactly as the CLI does — not a
JSON array. One less translation layer, one less shape that could
silently diverge from what `nj --id=A,B,C` itself accepts (§ 9 "Batch
writes"). The wrapper result shape is `{ok, results: […]}` exactly as a
batch CLI call already returns.

**The acting name — RULED (DECISIONS 144, C-4): a per-call `as` input
parameter.** `note`, `claim` and `release` each gain an `as` input,
defaulting to the server's own `NJ_AUTHOR` (from the launching
environment) when the caller omits it — the exact `--as`-outranks-
`NJ_AUTHOR` precedence § 9 already has, exposed per call instead of per
process, so one `nj-mcp` serving several conceptual actors over its
lifetime does not misattribute every note/claim to whichever actor the
server happened to be launched for. **Validation is the same `--as`
validation already has** (DECISIONS 119: non-empty after trimming, a
single line, no `:`) — an invalid `as` is `invalid_value`, nothing
written, exactly as an invalid `--as` is on the CLI; no new validation
rule is introduced for this new surface.

## D. Architecture — RULED (DECISIONS 144, D-1/D-2)

**One `nj` process per tool call.** `nj-mcp` is a thin
protocol/argument-translation layer: a tool call becomes exactly the
argument list the equivalent CLI invocation would have, **plus
`--backlog=<the server's own resolved path>` (§ A, DECISIONS 145 item
b), always explicit, never inherited from the child's own cwd/environment
search** — run against `dist/nj --json` as a child process, with its
parsed stdout handed back as the tool result. The alternative — importing
`src/commands`/`src/core`
directly and calling them in-process — would be faster (no process-spawn
overhead per call) but needs those modules refactored first: today every
command module is CLI-shaped (parses `argv`, prints, calls `process.exit`),
not library-shaped (take structured input, return a value, never exit the
host process). That refactor touches every command and is its own
project-sized risk, independent of MCP.

Process-per-call buys three things at once: **zero duplicated logic**
(the JSON `nj-mcp` returns *is* `dist/nj --json`'s own output, byte for
byte, because it is the same binary, not a reimplementation of it),
**zero new concurrency model** (every tool call goes through § 12's
compare-before-write and § 12a's claim CAS exactly as any other concurrent
CLI invocation already does — nothing about `nj-mcp` existing weakens or
bypasses it, because nothing about it is a different code path), and
**perfect contract fidelity by construction**, which is the whole point of
§ C's "no second contract" rule. The cost is spawn latency per call.

**D-2: the budget is the per-call overhead over a direct CLI call, p50 ≤
50 ms.** Measured as the difference between a tool call's wall-clock time
and `dist/nj --json`'s own wall-clock time for the identical invocation,
median over a representative run — the overhead `nj-mcp` itself adds on
top of the CLI call it wraps, not the CLI call's own cost (which § 13
already measures and budgets separately).

## E. Safety — RULED (DECISIONS 144, E-1)

**A single `--allow-destructive` start flag, gating only `doctor --fix`.**
`rm` is not on the tool list at all (§ C-1), and `archive`/`unarchive` are
offered ungated (reversible, § C-1) — so of the candidates the first draft
weighed, only `doctor --fix` needs a gate at all. `doctor --fix` is
**absent from `tools/list`** unless `nj-mcp` is launched with
`--allow-destructive`. The gate is a launch-time decision the *operator's*
MCP client configuration makes, never something a tool call itself can
toggle — an agent that could flip its own safety gate would not have one.

**Path confinement.** No new mechanism is needed: `nj-mcp` is pinned to
one resolved backlog for its whole life (§ A), and every tool call's
`--id`/`--file` addressing goes through the exact same resolution and
refusal rules the CLI already enforces (§ 9) — there is no per-call
`--backlog` override to add a loophole with, because § A's ruling already
keeps that parameter off the per-call surface entirely.

## F. Testing

**A stdio driver, black box, like every other suite here, driven by the
real MCP SDK client (§ B), exercising both eras.** A small harness in
`test/` that launches `dist/nj-mcp` as a child process and drives it
through the **official MCP SDK's client** (the test-only `devDependency`
§ B names), so compatibility is checked against the real protocol
library, not against the test's own re-implementation of what a client
should send. The SDK client's own dual-era probing is what actually
exercises both paths: once with it defaulting to a modern-first probe
(`server/discover` returns a real `DiscoverResult` naming both pinned
versions, § B), once forced onto the legacy `initialize` handshake. It
asserts: `server/discover`'s `DiscoverResult` and `initialize`'s response
each declare the right revision and the same `capabilities: {tools: {}}`
(§ B); an unsupported version on the modern path gets
`UnsupportedProtocolVersionError` (`-32022`) naming both supported
versions; the exposed tool list matches § C/§ E exactly (`doctor --fix`
absent unless `--allow-destructive` was given, `rm` absent
unconditionally, no tool schema names a `backlog` field, § C-2); each
tool's result, run against a fixture, is **byte-identical** to `dist/nj
--json`'s own output for the equivalent CLI invocation (making § C-2's
"no second contract" rule directly testable, not just asserted in
prose); a malformed `tools/call` argument gets `-32602` before any
`dist/nj` child is spawned, while a schema-valid call the CLI itself
rejects surfaces as `isError: true` with the unmodified `{ok:false,
error, hint?}` body (§ B); batch writes and the `as` parameter (incl.
its D119 validation) behave exactly as § C describes; an unknown method
and a malformed envelope get the JSON-RPC error codes § B names, never a
crash.

**Dependency-freedom, mirroring AC-15 — new AC (DECISIONS 145, item c).**
`test/ac/ac-15-no-dependencies.js` proves `dist/nj` ships with zero
runtime dependencies by copying it **alone** into a bare directory (no
`node_modules`) and confirming it still runs. `dist/nj-mcp` makes the
identical claim (§ B: "genuinely zero new dependencies, even at build
time") but needs the identical proof, not an inference from § B's prose:
copy `dist/nj-mcp` alone into a bare directory and confirm it starts and
completes both an `initialize`/`tools/list` round trip (legacy) and a
`server/discover`/`tools/list` round trip (modern) — exactly AC-15's own
methodology, extended to assert the new binary answers both eras it
claims to speak, not merely that it starts.

**The replay gate.** This project already replays a frozen call corpus
against each accepted baseline to catch silent drift (`oracle-frozen-N`,
`cN-baseline`). AC-36 (below) extends it: the C-2 flag-table move that the
CLI's own parser goes through must replay against `c7-baseline`
byte-identically — the exact mechanism that already catches any other
silent behavioural drift, applied to this refactor specifically. A
second, smaller extension — a handful of representative calls driven
through `nj-mcp` instead of the raw CLI, diffed against the same corpus's
CLI-direct results — catches an accidental transformation introduced at
the protocol layer that the CLI-only replay could never see.

**Performance.** Measure `nj-mcp`'s own size and cold-start time (§ B-2,
no target set) and its added per-call latency (§ D-2, p50 ≤ 50 ms over a
direct CLI call), on a quiet machine, the same before/after methodology
§ 13 already uses for `STATUS.md`'s cost.

## G. What stays out

- **MCP resources and prompts.** Only tools, this round. `list`/`show`/
  `find` already give an MCP client read access to everything a "resource"
  capability would expose; no concrete workflow has asked for subscription
  semantics a tool call cannot already serve.
- **Any transport but stdio.** No HTTP/SSE. A network-reachable transport
  implies a multi-client, multi-tenant story and an authentication layer
  this project's trust model was never built for (§ 6: names are labels,
  not identities; § 9: no registry, no authentication for the acting
  name). Stdio's "the client already trusts whatever spawned it" model is
  the only one consistent with that.
- **Authentication.** Same reasoning: the spawning process (the agent
  harness) is the trust boundary, exactly as it already is for the plain
  CLI.

Interface**, naming the tool surface, the dual-era protocol subset and
its two pinned revisions (§ B), the `server/discover`/`initialize`
handshakes and the `-32022`/`-32602` error cases, the schema-generation
table shared with the CLI parser and its `--backlog`/`--json` exclusion
(§ C-2), the error-mapping rule (§ C-3) and the safety gate (§ E). No
existing section's *meaning* changes — `dist/nj` keeps every flag, shape
and exit code it has — but § 9's own text may gain a cross-reference
once the CLI parser moves onto the shared flag table (§ C-2), since that
table becomes something § 9 can point at instead of only describe in
prose.

No existing acceptance criterion changes. New ones, numbered after AC-31:

32. **MCP tool surface.** `nj-mcp`'s `tools/list` names exactly `list`,
    `show`, `find`, `tree`, `new`, `set`, `note`, `check`, `claim`,
    `release`, `archive`, `unarchive`, `doctor`; `rm` is never present;
    `doctor --fix` is present only when the server was launched with
    `--allow-destructive`, absent otherwise.
33. **Result fidelity.** For every exposed tool, a `tools/call` result's
    content is byte-identical to `dist/nj --json`'s own output for the
    equivalent CLI invocation against the same fixture — success and
    failure alike, including `isError` reflecting exit 1/2 and the
    untouched `{ok, error, hint?}` body on failure.
34. **Backlog resolution and confinement.** `nj-mcp` resolves its backlog
    at startup by the same rules as the CLI (§ 4), serves only that
    backlog for its whole life, and takes no per-call backlog override.
    Every spawned `dist/nj` child is given `--backlog=<that resolved
    path>` explicitly (DECISIONS 145 item b) — confirmed by inspecting
    each child's own argument list, not merely its result. No generated
    tool schema names a `backlog` field (DECISIONS 145 item a), checked
    against every tool's schema, not inferred from the generator's
    source code alone.
35. **Batch and acting-name parity.** A tool call with a comma-joined `id`
    produces the same `{ok, results}` wrapper a CLI batch write would; an
    `as` parameter on `note`/`claim`/`release` outranks the server's own
    `NJ_AUTHOR`, validated exactly as `--as` is (D119), exactly as `--as`
    outranks it on the CLI.
36. **CLI behaviour is unchanged by the flag-table move (C-2).** Moving
    the CLI's own argument parser onto the shared flag table that
    `nj-mcp`'s schemas are also generated from changes no observable CLI
    behaviour: replayed against `c7-baseline`, the CLI produces
    byte-identical output, call for call, before and after the move.
37. **Dual-era protocol handshake (DECISIONS 145).** `server/discover`
    returns a `DiscoverResult` naming `supportedVersions: ["2026-07-28",
    "2025-11-25"]` and `capabilities: {tools: {}}`; `initialize`'s
    response declares `2025-11-25` and the same `capabilities` object. A
    request on the modern path naming an unsupported version gets
    `UnsupportedProtocolVersionError` (`-32022`) listing both supported
    versions. A malformed `tools/call` argument (fails the tool's own
    schema) is rejected `-32602` before any `dist/nj` child is spawned;
    a schema-valid call the CLI itself then rejects surfaces as a tool
    result, `isError: true`, the unmodified `{ok, error, hint?}` body
    (never `-32602`). An unknown method, in either era, is `-32601`.
38. **`dist/nj-mcp` ships with zero runtime dependencies, mirroring
    AC-15.** Copied alone into a bare directory with no `node_modules`,
    `dist/nj-mcp` starts and completes both an `initialize`/`tools/list`
    round trip (legacy) and a `server/discover`/`tools/list` round trip
    (modern).

## Open questions — all ruled (DECISIONS 144/145)

Every one of the first draft's (`f8a08db`) open questions is now **RULED**
(DECISIONS 144); the independent review (`bb7bd86`) then found one
protocol-era gap and three confinement/testability gaps, folded in as
DECISIONS 145. Collected here only as an index back to each section's
full reasoning.

- **A-1 RULED:** one backlog per server process, resolved once at startup
  by the existing rules (§ 4). **Also RULED (DECISIONS 145, item b):**
  every spawned child is given `--backlog=<that resolved path>`
  explicitly — confinement is mechanical, not a re-resolved search.
- **B-1 RULED, deviating from the Oracle's recommendation:** hand-roll the
  stdio JSON-RPC/MCP subset (`server/discover`, `initialize`,
  `tools/list`, `tools/call`, the required notifications), genuinely
  zero new dependencies; the official SDK's **client** is a test-only
  `devDependency`, never shipped.
- **B-2 RULED:** reduces to `nj-mcp`'s own size and cold start — measure
  and report, no target set.
- **Protocol era RULED (DECISIONS 145):** `nj-mcp` is **dual-era** —
  `server/discover` is actually implemented (not left to the
  unknown-method fallthrough), pinned revisions `2026-07-28` (modern) and
  `2025-11-25` (legacy); an unsupported modern-path version gets
  `UnsupportedProtocolVersionError` (`-32022`); `-32602` (schema-invalid
  `tools/call` arguments) is distinct from a schema-valid call the CLI
  itself rejects (`isError: true`); both handshakes declare
  `capabilities: {tools: {}}`.
- **C-1 RULED:** tools are `list`, `show`, `find`, `tree`, `new`, `set`,
  `note`, `check`, `claim`, `release`, `archive`, `unarchive`, `doctor`.
  `rm` (incl. `--cascade`) is omitted entirely. `archive`/`unarchive` are
  offered ungated (reversible). `doctor --fix` exists only behind
  `--allow-destructive`.
- **C-2 RULED:** MCP input schemas are generated from a flag table shared
  with the CLI parser; moving the CLI onto that table must keep CLI
  behaviour byte-identical, proven by the replay gate against
  `c7-baseline` (AC-36). **Also RULED (DECISIONS 145, item a):** the
  generator reads strictly the per-command table, never
  `GLOBAL_CONTROLS` (`--backlog`) or `--json`; an AC asserts no generated
  schema names a `backlog` field (AC-34).
- **C-3 RULED:** a failure is a tool result with `isError: true` and the
  unmodified `{ok, error, hint?}` body; the code is never lost.
- **C-4 RULED:** the acting name is a per-call `as` parameter, defaulting
  to the server's `NJ_AUTHOR`, validated exactly as `--as` is (D119).
- **D-1 RULED:** process-per-call — the server spawns `dist/nj --json`
  for each tool call, so there is no duplicated logic and § 12 holds by
  construction.
- **D-2 RULED:** measured; the budget is the per-call overhead over a
  direct CLI call (p50) ≤ 50 ms.
- **E-1 RULED:** a single `--allow-destructive` start flag, gating only
  `doctor --fix`.
- **Dependency-freedom for `dist/nj-mcp` RULED (DECISIONS 145, item c):**
  a new AC mirrors AC-15's own methodology — copied alone, no
  `node_modules`, starts and answers both eras (AC-38).
- **Section name RULED:** "§ 17. MCP Interface".
