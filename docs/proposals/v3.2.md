## A. `nj check` — tick or untick a checkbox in the body

**Promoted to the spec (v3.2)** (DECISIONS 126): see `SPECIFICATION.md`
§ 10a (the command section), § 7 (the fourth sanctioned body exception, the
stated fence-awareness exception), § 9 (command list, closed failure set
gains `ambiguous_target`, JSON shape), § 4 (`STATUS.md` write list), § 12
(compare-before-write and `--force` lists), § 15 AC-28, § 16 (item
removed). Tests follow in `test/ac/ac-28-check.js`.

### Motivation

Acceptance criteria and sub-tasks inside a body are Markdown checkboxes
(`- [ ]` / `- [x]`, § 7's own example). Today ticking one means a hand edit
or a `--acceptance=<full text>` rewrite of the whole section — both bypass
`nj`'s write discipline (no compare-before-write, no `updated` refresh, and
for the full-rewrite path, no way to flip one box without reproducing every
other line byte-for-byte). `nj check` is the dedicated, guarded writer for
exactly this one edit: flip one box, touch nothing else.

### Interface

```
nj check --id=TSK-007 --text="at least 8 characters" [--on | --off] [--force] [--json]
nj check --id=TSK-007 --item=3 [--on | --off]  [--force] [--json]
```

(`--file=<path>` instead of `--id`, and `--backlog`, as for every write.)

### Addressing a checkbox — RULED (DECISIONS 123)

**`--text` is primary, `--item` the fallback; exactly one of the two is
required** — neither given is `missing_argument`, both given is
`invalid_value` (by analogy with `--description`/`--description-file`'s
mutual exclusivity, § 9).

- **`--text=<substring>`** — the **countable** checkbox (below) whose line,
  with the list marker and the `[ ]`/`[x]`/`[X]` box stripped, contains
  `<substring>` (plain substring, not a regex, matched the same way `nj
  find`'s `--text`/body search is, § C).
- **`--item=<n>`** — the *n*-th **countable** checkbox, 1-based, in document
  order (top to bottom, depth-first through nested lists).

"Countable" is defined once, by the scope rules directly below, so `--item`
and `--text` always address the same set — an `--item=2` found by counting
is the checkbox `--text` would also be willing to match.

**Zero matches or several are two distinct, named failure codes** — never
guessed at (§ 14's own instinct: "ambiguity is reported, not guessed"):

| Condition | Code |
|---|---|
| `--text` matches no countable checkbox, or `--item` is out of range (< 1 or > the count) | `not_found` |
| `--text` matches two or more countable checkboxes | `ambiguous_target` (new, additive) |

`not_found` reuses the existing code (consistent with `--parent`/
`--depends-on` naming nothing, § 9); `ambiguous_target` is new because
nothing in the closed set means "more than one matched" — `invalid_target`
is reserved for "wrong type" (§ 9) and would be a misleading reuse here.
`--item` can never be ambiguous (an index names at most one line), so only
`--text` can produce `ambiguous_target`.

### Scope of the scan — RULED (DECISIONS 123)

- **`## Notes` is excluded.** Checkboxes under every other section — `##
  Description`, `## Acceptance Criteria`, an unknown section — are in
  scope; `## Notes` (§ 10: an append-only audit trail of **past**
  decisions) is not. One addressing scheme, no `--section=` flag, and the
  one section that is semantically "already happened" stays out of reach.
- **Fence-aware matching is a deliberate, stated exception to § 7.** § 7
  states that section-heading matching is "line-based and not
  fenced-code-aware... deliberately out of scope for round one" — that rule
  stands for section writes. `nj check` is different in kind: it walks the
  **entire** body for a checkbox-shaped line (below) that can legitimately
  appear inside documentation-as-code, where a section write only ever acts
  on a region the caller named by heading. `nj check` therefore **does**
  track fence state (` ``` ` and `~~~`, either length-3-or-more, matched at
  the start of a line after optional leading whitespace, closed by a
  matching or longer fence of the same character) line by line and never
  counts or matches a checkbox-shaped line while inside one. This is the
  one place in the spec where fence-awareness exists; § 7's general rule is
  otherwise unchanged.

### What counts as a checkbox — RULED (DECISIONS 125), stated normatively

Stated as a rule, not shown only by example (the review's finding): a line
is a **checkbox** when, after optional leading whitespace (indentation —
nested list items count the same as top-level ones), it starts with one of
the list markers CommonMark recognises — the bullets `-`, `*`, `+`, or an
ordered marker `<digits>.` or `<digits>)` (e.g. `1.`, `1)`) — followed by one
space and `[ ]`, `[x]` or `[X]`. **Reading:** `[x]` and `[X]` both count as
**ticked**; only `[ ]` counts as **unticked** — so an already-uppercase
`[X]` (a plausible hand edit) is "already ticked" for counting, for
`--text`/`--item` matching, and for `--off`'s no-op check (rule 3, below).
**Writing:** ticking always writes `[x]` (lowercase); unticking always
writes `[ ]` — regardless of which of `[x]`/`[X]` was read, the write side
never produces `[X]`.

### Rules

1. Refused before anything is written: an archived element
   (`refused:archived`); `--id`/`--file` together (`invalid_target`, § 9); X
   itself an unreadable stub (`refused:unreadable`, this element only —
   same reasoning as `nj claim`'s step 1, § 12a: `nj check` moves nothing,
   so § 9's backlog-wide stub guard for `rm`/`archive` does not apply).
2. Resolve the target checkbox (above): `not_found` or `ambiguous_target`
   as the table above states.
3. **A no-op is not refused.** `--on` on an already-ticked box, or `--off`
   on an already-empty one, exits 0 and writes nothing (`changed: []`) —
   the same idempotent-no-write shape as `nj release` on an unclaimed
   element (§ 12a), not `nj claim`'s re-assert-with-a-new-entry shape,
   because a checkbox carries no history to re-affirm.
4. The write flips exactly the bracket content (`[ ]`↔`[x]`, per "What
   counts as a checkbox" above) and nothing else on the line — not the
   line's leading whitespace or list marker, not trailing content after
   the `]`. `updated` is refreshed; the atomic write and compare-before-write
   rules (§ 12) apply. **`--force` extends to `check`** (DECISIONS 123):
   § 12's "`--force` overrides a parallel change on `set` and `note`" now
   reads "`set`, `note` and `check`" — a checkbox flip is a narrow,
   single-element edit with the same residual-window shape those two
   already have, not a bulk move like `archive`/`unarchive`.
5. A note **does not** satisfy or un-satisfy completeness by itself: ticking
   every box in `## Acceptance Criteria` does not change whether the section
   is "present and non-empty" (§ 7) — completeness and checkbox state are
   independent, same as `status` and `_problems` are independent today.
6. `changed: ["body"]`, the same marker `nj note` uses (§ 10) — a checkbox
   flip, like a note, is a body edit that is not a section-role write.

### Output

`{ok, id, changed: ["body"] | [], entry: {…, _problems}, _problems}` — the
§ 9 write-result shape, nothing new. Human output repeats the toggled line:
`TSK-007: [x] Password at least 8 characters`.

### Touches

§ 6 (none — no new frontmatter field), § 7 ("Body": a fourth sanctioned
exception to byte-for-byte, alongside H1 sync, `nj note`, and section-role
writes; the one stated exception to "not fenced-code-aware"), § 9 (one
verb, `ambiguous_target` added to the closed set), § 12 (compare-before-write
and `--force` lists gain `check`), § 16 (item removed).

### Acceptance criterion

28. **Check.** A checkbox is any `-`/`*`/`+`/`<digits>.`/`<digits>)`-marked
    list item, at any indentation, followed by `[ ]`, `[x]` or `[X]`; `[x]`
    and `[X]` both count as ticked on read, only `[ ]` as unticked, and a
    write always produces `[x]` (tick) or `[ ]` (untick), never `[X]`.
    `nj check --id=TSK-007 --text=<substring>` and `--item=<n>` each
    address the same checkbox when there is exactly one countable match;
    `--on` an unticked box and `--off` a ticked one each flip exactly that
    line's bracket content and nothing else, byte-for-byte, with `updated`
    refreshed; `--on` already-on and `--off` already-off each exit 0 with
    `changed: []` and change no byte. A checkbox inside `## Notes`, or
    inside a fenced code block, is never counted or matched — neither
    addresses it and neither index includes it. `--text` matching no
    countable checkbox, or `--item` out of range, is `not_found` (the same
    code `--parent`/`--depends-on`/`--file` already reuse for "names
    nothing", § 9); `--text` matching two or more is `ambiguous_target`.
    `check` on an archived element is `refused:archived`, on an unreadable
    stub `refused:unreadable`, and `--id`+`--file` together is
    `invalid_target`, each exiting 1 and changing nothing.
    `NJ_FAULT=before-rename` leaves the file at its previous revision; a
    parallel edit aborts with `changed_in_parallel` unless `--force`.

## B. Stale claims — visible age, an advisory `doctor` warning

### Motivation

§ 12 "Claims" is deliberately not a lock: a crashed agent's claim never
blocks anyone, recoverable with one explicit `--steal`. But recovery still
needs a **signal** — nothing today tells a human or another agent that a
claim is old enough to be suspicious. `_claim` already carries `since` (the
claim's own timestamp); this proposal makes staleness a first-class,
advisory-only observation on top of data that already exists.

### Claim age: no new JSON field — RULED (DECISIONS 123)

`_claim` is `{"by": "<name>", "since": "<ISO-8601>"}` today (§ 9, § 12
"Claims"). "Age" is `now − since`; it has no state of its own and goes stale
the instant it is computed, unlike every other field this spec derives
(`_problems`, `_claim` itself) which describe a **condition**, not a
continuously-moving value.

**No new field.** A caller that wants age computes `now − _claim.since`
itself — `since` already carries the claim time, so nothing is missing. The
place staleness *is* worth a stored, derived signal is `doctor` (below),
because `doctor`'s job is exactly "flag conditions", not "report raw
numbers".

Human `list`/`show` output MAY render a relative-time phrase ("claimed by
alice, 3d ago") for readability — prose, not a JSON contract, left to the
implementation's taste, the same way § 9's "Feedback after writes" pins the
*shape* of human output but not every sentence.

### `doctor` finding: `claim:stale`

New code, additive, in § 7's closed table:

| Code | Produced by | Doctor | Blocks `--ready` |
|---|---|---|---|
| `claim:stale` | the element is claimed and `now − _claim.since` exceeds the configured threshold | warning | no |

**Advisory only — this does not touch `--ready` or exclusivity.** § 12's
opening principle ("a claim is not a lock") governs: `claim:stale` never
auto-releases, never auto-steals, and condition 5 of `--ready` (§ 9)
is unchanged — a stale claim still hides the element from every other
acting name's `--ready`, exactly as a fresh one does. The only consumer of
this code is `doctor`; it is the same kind of signal `claim:mismatch`/
`claim:orphaned` already are — reported, acted on by a human or agent
choosing to `--steal`, never acted on by `nj` itself.

**`now` is `NJ_NOW` when set** (DECISIONS 125), exactly as § 12 already
pins it for every other timestamp-sensitive behaviour in the spec: the
staleness comparison `doctor`/`list`/`show` make is `NJ_NOW − _claim.since`
when `NJ_NOW` is given, real wall-clock time otherwise. Without this, AC-29
could not be written as a byte-deterministic test the way every other
criterion in this spec is — a test would otherwise need either real
wall-clock waiting or a claim timestamp picked "far enough in the past
relative to real `Date.now()`", exactly the un-pinned-clock problem
`NJ_NOW` exists to eliminate.

### Threshold: where configured, what default — RULED (DECISIONS 123)

`.nanojira/config.json` gains an optional top-level key:

```json
"claims": { "staleAfterHours": 24 }
```

A plain integer, **hours**. Default when the key or the whole `claims` block
is absent: **24**. **`0` disables the check** — no backlog ever reports
`claim:stale` — rather than meaning "stale after zero hours", the same
"a `false`-shaped value turns the feature off" reading `layout.statusFile:
false` already uses. Validated like every other config value (§ 5): a
non-integer or negative value is `config:invalid`.

**An unknown key inside `claims` is `config:invalid`** (DECISIONS 125),
following § 5's own precedent for `layout`/`layout.folders` exactly ("an
unknown key inside `layout` or `layout.folders` is invalid — a typo must
not silently fall back to a default") — `claims` is the same shape of
optional, nested object with one currently-defined key, and gets the same
typo-safety.

### Touches

§ 5 (new optional `claims.staleAfterHours` key), § 7 (`claim:stale`), § 9
(none — `_claim`'s shape is unchanged per the recommendation above), § 12
("Claims": `claim:stale` referenced as advisory, consistent with "a claim is
not a lock"), § 14 (checked list gains `claim:stale`; `doctor --fix` does
**not** touch it — there is nothing to repair, only to report, same as
`claim:mismatch`).

### Acceptance criterion

29. **Stale claims.** An element claimed more than `claims.staleAfterHours`
    (default 24) ago reports `claim:stale` (warning, never blocks
    `--ready`) on every read (`list`, `show`, `doctor`); one claimed less
    than the threshold ago does not. `doctor --fix` leaves `claim:stale`
    untouched — no auto-release, no auto-steal, the claim and its `assignee`
    mirror are unchanged byte-for-byte. `claims.staleAfterHours: 0` turns
    the finding off entirely, even for a claim far older than the
    un-configured default. A backlog with no `claims` config key behaves
    exactly as the 24-hour default. `--ready` condition 5 (§ 9) is
    unaffected by staleness in either direction.

## C. `nj find "<text>"` — search over title, body and notes

### Motivation

`list`'s filters (`--status`, `--tag`, `--assignee`, …) match structured
fields. Finding "the task that mentions rate limiting" today means reading
every file by hand or shelling out to `grep` outside `nj` — which does not
know about the archive, `--ready`, or any of `nj`'s own filters. `nj find`
is a read, like `list`, over the same already-loaded element data, with one
more predicate: a text match.

### Interface

```
nj find "<text>" [--status=…] [--type=…] [--tag=…] [--parent=…] [--assignee=…]
                  [--all] [--case-sensitive] [--json]
```

A read: no `--id`/`--file` (it searches, it does not address one element),
combines with every `list` filter already in § 9 (`--status`, `--type`,
`--tag`, `--parent`, `--assignee`) the same way they combine with each
other today — AND, not OR. `--all` includes the archive (§ 11), same
meaning as everywhere else it appears.

### What is matched — RULED (DECISIONS 123)

- **Fields: title, body and notes** (the body already includes `## Notes`
  as one block, § 7, so this is one read, not three) — "find the task where
  someone noted a workaround" is a real use case, and excluding notes would
  need a second parse pass over text `nj` has already loaded for nothing.
  This is a *read* matching past decisions, not a *write* touching them
  (§ A's `## Notes` exclusion is about writes, and does not apply here).
- **Match kind:** plain substring, not a regex and not a word-boundary
  match — consistent with `--text` in § A, and dependency-free (no regex
  engine beyond what a substring search already is). A `--word` mode is not
  in this round.
- **Case-insensitive by default**, `--case-sensitive` opts into exact-case
  matching. **The folding method is Unicode simple case folding as
  JavaScript's `String.prototype.toLowerCase()` implements it, applied to
  both the needle and the haystack before comparison — never
  `toLocaleLowerCase()`.** `toLowerCase()` is locale-independent (the same
  bytes fold the same way regardless of the host's configured locale),
  matching this project's existing determinism discipline (`NJ_NOW`
  pinning, § 12; no hidden environment dependence); `toLocaleLowerCase()`
  would make a search's results depend on an environment variable `nj`
  does not otherwise read anywhere, for every other command.

### Output

Same read shape as `list` (§ 9 JSON interface): `{backlog, counts, entries:
[{…, _problems, _claim}]}`, filtered to matching entries, in `list`'s sort
order (§ 9: priority descending, then `id` ascending — relevance ranking is
explicitly out of scope, the same way `list --ready`'s order is the
backlog's order, not a ranked one). **No `_match` field this round**
(DECISIONS 123): the JSON shape is exactly `list`'s, nothing added. Human
output adds one line of match context per hit — the first line of the body
containing the match, truncated — the way `grep` shows the matching line,
not the whole file; this is prose, not a JSON contract. A caller that wants
more than "yes/no, and where roughly" already has `nj show`.

### Performance

Reuses the existing full-scan read path (§ 13): bodies are already parsed
for completeness/title/section checks, so `nj find` adds one substring scan
over text `nj` has already loaded, not a new read. The § 13 trigger ("implement
the index when backlogs approach ~12,000–15,000 elements") is unchanged by
this feature; `nj find` does not change when that trigger is crossed, since
it is the same O(n) scan every other command already does. No new
measurement is owed by this proposal; § E(3) below is the pre-existing,
separately-tracked gap.

### Touches

§ 9 (one verb, filters reused, JSON shape identical to `list`'s), § 13
(a sentence noting `find` shares the scan path, no new cost model), § 16
(item removed, "full-text search over the body").

### Acceptance criterion

30. **Find.** `nj find "<text>"` returns every element whose title or body
    (including `## Notes`) contains `<text>` as a substring, case-insensitive
    by default (`toLowerCase()` folding on both sides) and exact with
    `--case-sensitive`; combines with `--status`/`--type`/`--tag`/
    `--parent`/`--assignee` as an AND; archived elements are excluded
    without `--all` and included with it, same as `list`. The JSON shape
    matches `list`'s read shape exactly, no `_match` field. A search
    matching nothing returns `entries: []`, exit 0 (a read never fails on
    "no results" — same as an empty `list --status=doing`).

## D. Batch writes — `--id=A,B,C`

### Motivation

An agent that finishes three tasks in the same batch runs `nj set
--status=done` three times today. `--id=A,B,C` lets one invocation apply
the same field map or action to several elements, with one atomicity story
instead of three independent ones the caller has to reconcile by hand.

### Which commands — RULED (DECISIONS 123)

**`set`, `note`, `check` (§ A), `claim`, `release` only** — the writes that
take a field map or a single fixed action per element, applied identically
to each ID. **Not** `rm`, `archive`, `unarchive`: those already have their
own multi-element semantics (`rm --cascade`, `archive`'s subtree, § 11a's
archived-subtree gathering) built around **one** addressed root, and
layering `--id=A,B,C` on top would mean "N independent subtree operations",
no better than N invocations — unlike `set --id=A,B,C --status=done`, where
the point is "the same one-line field map, N times, atomically reported
together".

### Atomicity and partial failure — RULED (DECISIONS 123)

**Every ID is resolved and validated before anything is written.** One pass
over the backlog resolves and checks every ID in the batch — this is
**preflight** — covering exactly the conditions each targeted command
already refuses *before anything is written*, for a single element, today:

- addressing: each ID resolves to exactly one element (`not_found`,
  `duplicate_id` without `--file`); for `check`, its `--text`/`--item`
  resolves to exactly one countable checkbox (`not_found`,
  `ambiguous_target`, § A);
- input validity: known fields, valid values (`unknown_field`,
  `missing_argument`, `missing_value`, `invalid_value`); a missing or
  invalid acting name for `claim`/`release` (`missing_argument`,
  `invalid_env`, `invalid_value`, § 9 "The acting name");
  `--id=A,B,C` with `--file` (`invalid_target`, below); **`--id=A,A` (the
  same ID named twice, checked after trimming whitespace) is `invalid_value`
  — an argument error, not a per-ID one, since "resolved and validated"
  already implies every named ID is distinct** (DECISIONS 125: the cheapest,
  least surprising reading of a repeated name, and the only one of the
  three plausible readings — process it twice, silently dedupe, or reject
  — that avoids a spurious `changed_in_parallel` on the second occurrence
  racing against the first occurrence's own just-completed write within
  the same batch);
- each command's own existing refusal-before-anything-is-written
  conditions: an archived element (`refused:archived`), an unreadable stub
  (`refused:unreadable`) — the same preconditions § 12a step 1 lists for
  `nj claim` and § A step 1 lists for `nj check`, now checked once per ID
  up front instead of once per invocation.

**An unknown ID or any failure above aborts the *whole* batch: nothing is
written, for any ID**, reported per ID (below) so the caller knows exactly
which one(s) failed preflight.

**Per-ID runtime failures do not stop the others.** Once preflight passes
for every ID, each one's actual write proceeds through that command's own
existing live-state mechanism — compare-before-write (§ 12), `nj claim`'s
read-decide-`link()` loop (§ 12a) — exactly as a single invocation would.
Anything that mechanism can produce *because the backlog moved between
preflight and this ID's turn to write* is a **runtime** failure, specific
to that one ID: `changed_in_parallel`, `refused:claimed` (a competing claim
landed first), `claim:mismatch`-producing write failures, any `fault:<hook>`
firing, an `io_error`. A runtime failure on one ID is reported for that ID
and does **not** abort or skip the remaining IDs — a batch is not a
transaction across its members, only within each one, so one ID's bad luck
does not punish the others for a problem that is specific to it.

**Exit code: 1 if any ID failed (preflight or runtime), 0 only if every ID
succeeded** — the same binary `0`/`1` the rest of § 9 uses; there is no
third "partially succeeded" exit code.

### `--file` and compare-before-write

`--id=A,B,C` and `--file=<path>` are mutually exclusive the same way `--id`
and `--file` already are for a single element (§ 9, `invalid_target`):
`--file` addresses exactly one element unambiguously, which is the opposite
problem batch writes solve. Each ID in the batch goes through
compare-before-write independently (above); `--force` applies to the whole
batch, overriding a parallel change on every ID it would otherwise have
hit, consistent with `--force`'s existing "exactly one meaning" rule (§ 9).

### Output — RULED (DECISIONS 123): the wrapper shape, pinned exactly

**`--id=A,B,C` (two or more comma-separated IDs) triggers the wrapper
below; a single `--id=A` (no comma) is unaffected and keeps today's
unwrapped § 9 write-result shape exactly — the wrapper does not apply to a
feature it has nothing to do with.**

```json
{
  "ok": false,
  "results": [
    { "id": "TSK-001", "ok": true, "changed": ["status"],
      "entry": { "…": "…" }, "_problems": [] },
    { "id": "TSK-002", "ok": false, "error": "refused:claimed",
      "hint": "use --steal=<holder>" }
  ]
}
```

(The example's failure is a **runtime** one, `refused:claimed` — a
*preflight* failure such as `refused:archived` can never appear next to a
successful sibling: preflight aborts the whole batch before anything is
written, so a batch that has any successful entry at all has, by
construction, no preflight failures in it. Fixed per DECISIONS 125: the
first draft's example paired `refused:archived` — a preflight code — with a
written sibling, which cannot happen.)

- **Top level:** exactly `{ok, results}`. `ok` is `true` **iff every**
  `results[i].ok` **is `true`** — it mirrors the exit code and nothing
  else is added at the top level (no batch-wide `_problems`; each result
  already carries its own).
- **`results`** is an array, one entry per ID, **in the order `--id` named
  them** — not sorted, not grouped by outcome, so a caller can zip it
  against the `--id=A,B,C` list it sent.
- **Each entry whose write succeeded** is exactly that command's own
  single-element write-result shape (§ 9's table / § 12a's `claim`/
  `release` row) **plus the leading `id` key**: `{id, ok: true, changed,
  entry, _problems}` for `set`/`note`/`check`; `{id, ok: true, changed,
  entry, _problems, claim, stolen_from?, previous_assignee?}` for `claim`;
  `{id, ok: true, changed: ["claim"], entry, _problems}` for `release`.
- **Each entry whose write failed** (preflight or runtime, no distinction
  in the shape — only in *when* the failure was found, § above) is `{id,
  ok: false, error: "<code>", hint: "…"}` — **`hint` is optional, exactly
  as it is in § 9's generic single-write failure shape** (DECISIONS 125):
  a failed batch ID is exactly where an agent most wants the recovery hint
  a single-element failure would have carried (`refused:claimed`'s "use
  `--steal=<holder>`", `exists`'s "move or delete it, then unarchive
  again"), so dropping it here would be a batch-specific regression, not a
  simplification.
- This is a genuinely new top-level shape, not an overload of the
  single-write one: an agent's existing `ok`/`changed`/`error`/`hint`
  branching on a single `nj set --id=TSK-001` continues to see exactly what
  it sees today, because that path never produces a `results` array.

### `STATUS.md` — RULED (DECISIONS 125): regenerated once per batch

A batch regenerates `STATUS.md` (§ 4) **at most once, after every ID's
write phase has finished** — never once per ID. If every ID in the batch
failed (whether at preflight or because every individual write failed at
runtime), nothing was written and `STATUS.md` is **not** touched at all,
the same "only after a successful write" rule § 4 already states for a
single command. This both avoids N regenerations of a feature whose whole
point is doing N things in one call instead of N calls (§ 13 already
measures a ~12–14% cost per single-write regeneration, so N of them would
compound linearly with batch size), and matches the batch's own "one
atomicity story" framing: a `STATUS.md` that settles once, after the whole
batch, is a more honest single "atomic report" than one that flickers
through N intermediate states no caller ever observes.

### Touches

§ 4 (`STATUS.md` regeneration: once per batch, not once per ID), § 9 (one
addressing mode across `set`/`note`/`check`/`claim`/`release`, new batch
JSON shape, `invalid_target` extended to `--id=A,B,C` + `--file`,
`invalid_value` extended to a repeated ID), § 12 (restates that per-ID
atomicity is unchanged — no new mechanism, just N uses of the existing
one), § 16 (item removed).

### Acceptance criterion

31. **Batch writes.** `--id=A,B,C` on `set`, `note`, `check`, `claim` or
    `release` applies the same field map or action to all named IDs. A
    preflight failure on any one ID (unknown ID, a repeated ID —
    `invalid_value` — ambiguous `check` target, invalid field value,
    missing/invalid acting name, an archived element, an unreadable stub)
    aborts the **whole** batch — nothing is written for any ID, and
    `STATUS.md` is not regenerated — and is reported for the ID(s) that
    failed. Once preflight passes for every ID, each one writes
    independently: a `--force`-less parallel edit on one ID during the
    write phase fails only that ID with `changed_in_parallel`, a competing
    claim is `refused:claimed` only for that ID, and every other ID still
    succeeds; `STATUS.md` is regenerated once, after every ID's write phase
    has finished, provided at least one ID was actually written. Exit 0
    only when every ID succeeded, 1 otherwise. `--id=A,B,C` with `--file`
    is `invalid_target`. The JSON shape is exactly `{ok, results: [{id, ok,
    …}]}`, `results` in the order `--id` named the elements, each entry the
    single-write §9/§12a shape for its command plus `id` — failures
    optionally carry `hint`, exactly as a single write's failure shape
    does; a single `--id=A` (no comma) is unaffected and keeps today's
    unwrapped shape.

## E. Closing three known gaps

Not new features — three items DECISIONS 108/109/117 already named and
deferred. Each gets its own fix, not a shared mechanism; grouped here only
because the user released them together (DECISIONS 122).

### E.1 — A deterministic `NJ_FAULT` hook for the `.njrc` swap race

DECISIONS 108: "a deterministic hook for the `.njrc` swap race; the suite's
timing-based leg rarely lands a hit when `nj` runs under a Node parent."
TSK-029 T1 closed the race itself (one file descriptor: `lstat` for the link
owner, then `open(O_RDONLY|O_NONBLOCK)`, `fstat`, read) but left the **test**
timing-based, so the suite can claim "0 bypasses in N runs" but never "this
specific window is provably closed."

**RULED (DECISIONS 123): documented in § 4, beside the `.njrc` rule — not
§ 12 — because this hook sits in the read-time ownership check, not the
write path the other three hooks share; it only resembles them in shape**
(poll, timeout, deterministic injection point).

A fourth `NJ_FAULT` value, **`njrc-swap`**, fires between the ownership
`lstat` and the `open()` (§ 4's `.njrc`-reading path only). **The go-marker
lives in the `.njrc` file's own directory** —
`<dir containing the reached .njrc>/.nj-fault-go` — the same filename
`before-compare` uses, relative to the one path this hook already knows at
the point it fires (no backlog is resolved yet; the `.njrc` being checked
is). Poll up to 10 s (consistent with `before-compare`'s timeout), then
proceed with whatever is at that path by then. Test-only injection point,
same disclaimer § 4/§ 12 already carry for the other hooks ("verification
hook, not a feature").

### E.2 — `doctor --fix` cleans a stray `.ids/` left by a crashed step 0 (G1)

DECISIONS 108: "G1, accepted as a known gap: a crash between the two
renames leaves a stray `.ids/` with the original tombstones; harmless (it
only doubles never-reuse), not cleaned up." § 14 step 0 renames
`.nanojira.json` → `.nanojira/config.json` and `.ids/` → `.nanojira/ids/`;
a crash between the two renames can leave either migrated and the other
not, and specifically can leave a stray v2-shaped `.ids/` sitting next to
an already-migrated `.nanojira/ids/`.

`doctor --fix` step 0, on a backlog that is **already** v3 (not
`backlog:legacy_layout`) but still carries a top-level `.ids/` directory,
removes it — but **only** when every tombstone name in it is already
present in `.nanojira/ids/` (never discard a tombstone that exists nowhere
else; "never reuse" is the one invariant § 8 cannot compromise on). A
`.ids/` with a tombstone not mirrored in `.nanojira/ids/` is left alone.

**RULED (DECISIONS 123): a `--fix` note only, no new problem code.** The
leftover is harmless by DECISIONS 108's own words, and `backlog:` problem
codes today all describe *current* defects the backlog has, not one-time
migration residue that `--fix` already knows how to resolve the moment it
is pointed at the backlog.

### E.3 — The § 13 absolute performance bars, on a quiet machine

DECISIONS 109: "the absolute § 13 perf bars were never re-measured on a
quiet machine (A/B against each previous step showed no regression)." This
is **process, not product**: no spec text changes, no new behaviour — it is
the lead (or whoever has a genuinely idle machine) running `npm run perf`
and recording the real numbers against § 13's existing comfort bar (median
≤ 250 ms, worst ≤ 500 ms) and trigger (~12,000–15,000 elements). Nothing in
`docs/`, `test/` or `src/` is touched by this proposal for E.3; it is listed
here only so DECISIONS 122's full scope is visible in one place, and so § 13
gets a one-line pointer once the measurement exists. No open question: this
is a scheduling item, not a design one.

### Touches

§ 4 (E.1: the `.njrc`-reading path gains the `njrc-swap` fault hook and its
go-marker rule), § 8 (E.2: the "never reuse" invariant is restated, not
changed), § 14 (E.2: step 0 gains the stray-`.ids/` cleanup, bounded by the
"only if mirrored" condition above), § 13 (E.3: a pointer to the
measurement once it exists, no new text now).

No new acceptance criterion: these are fixes to existing, already-numbered
criteria's coverage (E.1 strengthens the determinism of AC-21/AC-22's
`.njrc` legs; E.2 strengthens AC-24's legacy-migration coverage; E.3 is not
criterion-shaped at all).

## Open questions — all ruled (DECISIONS 123)

Every one of the first draft's (`5fe6af5`) open questions is now **RULED**;
collected here only as an index back to each section's full reasoning.

- **A-1 RULED:** `--text` (primary, substring on the item text) and
  `--item=<n>` (1-based among countable checkboxes), exactly one required.
  Zero matches → `not_found`; several → `ambiguous_target` (new, additive).
- **A-2 RULED:** `## Notes` is excluded from `nj check`'s scan.
- **A-3 RULED:** fence-aware checkbox matching is a deliberate, stated
  exception to § 7's general fenced-code rule.
- **A-4 RULED:** `--force` extends to `check`, alongside `set`/`note`.
- **B-1 RULED:** no new `_claim` field — `since` already carries the claim
  time; age is reader-computed.
- **B-2 RULED:** `claims.staleAfterHours` in `.nanojira/config.json`,
  default **24**, unit **hours**, **`0` disables** the warning entirely.
- **C-1 RULED:** title, body **and notes** are searched.
- **C-2 RULED:** case-insensitive by default, folding via
  `String.prototype.toLowerCase()` (never `toLocaleLowerCase()`).
- **C-3 RULED:** no `_match` field this round.
- **D-1 RULED:** `--id=A,B,C` on `set`, `note`, `check`, `claim`, `release`
  only — not `rm`/`archive`/`unarchive`.
- **D-2 RULED:** every ID is resolved and validated before anything is
  written (preflight; an unknown ID or invalid input aborts the whole
  batch, nothing written); per-ID runtime failures (`changed_in_parallel`,
  `refused:claimed`, a fault hook, …) do not stop the others.
- **D-3 RULED:** the wrapper shape is pinned exactly: `{ok, results:
  [{id, ok, …}]}`, triggered only by two-or-more comma-separated IDs; a
  single `--id=A` is unaffected.
- **E.1 RULED:** `NJ_FAULT=njrc-swap`, documented in § 4 beside the `.njrc`
  rule; its go-marker lives in the directory of the `.njrc` being checked.
- **E.2 RULED:** a `--fix` note only for the stray `.ids/` leftover, no new
  problem code.

## Review fixes, folded in (DECISIONS 125)

`docs/review/v3.2-proposal.md` (`717fd84`, "needs changes — text only")
found seven precision gaps and confirmed one existing choice; all eight are
now in the text above, indexed here:

- **§ D's example** now pairs a successful write with a genuine *runtime*
  failure (`refused:claimed`), not `refused:archived` — a preflight code,
  which could never appear next to a written sibling in the same batch.
- **`STATUS.md`** is regenerated once per batch, after every ID's write
  phase, only if at least one ID was actually written.
- **A repeated ID** (`--id=A,A`, checked after trimming) is `invalid_value`
  in preflight.
- **Per-ID failure entries** carry `hint` as an optional field, the same
  way § 9's single-write failure shape already does.
- **Claim-age staleness** is computed against `NJ_NOW` when set, matching
  § 12's existing clock-pinning discipline.
- **An unknown key inside `claims`** is `config:invalid`, following § 5's
  `layout` precedent exactly.
- **Checkbox markers** are now stated as a rule, not shown only by example:
  the five CommonMark list markers, nested items counted, `[x]`/`[X]` both
  read as ticked, only `[x]`/`[ ]` ever written.
- **`not_found` for a zero-match `nj check`** is confirmed, not changed —
  `nj` already reuses `not_found` for several conceptually distinct "the
  referenced thing isn't there" cases (`--parent`/`--depends-on`/`--file`
  naming nothing, an unreadable `--description-file`, an unresolved `--id`
  itself), so this is consistent with established practice, not a new kind
  of ambiguity.
