## 0. One identity: `NJ_AUTHOR`

**Promoted to the spec (v3.1), scoped to § A** (DECISIONS 110): `nj note`
is the only command that uses `NJ_AUTHOR` so far — see `SPECIFICATION.md`
§ 10. The `--as` flag branch below is not yet in the spec; it arrives with
`nj claim`/`nj release` (§ C).

The three features share one notion of *who is acting*. It is defined once,
here, and used by § 10 (note signing) and by `nj claim` (the claimant).

**The acting name** of an invocation is, in this order:

1. the value of an explicit flag where the command has one (`--as=<name>`,
   `nj claim` / `nj release` only);
2. `NJ_AUTHOR=<name>` from the environment;
3. none.

An empty `NJ_AUTHOR` counts as **unset** — the same rule as an empty
`NJ_BACKLOG` (DECISIONS 89).

**A name is valid** when, after dropping leading and trailing whitespace, it
is non-empty, is a single line, and contains no `:`. The colon is excluded
because a note line is `- <timestamp> <author>: <text>` (§ 10): a name with a
colon would make the author/text boundary unreadable for humans and for any
tool that parses notes. The trimmed value is used.

An invalid name is a hard error, nothing written, on a command that **needs**
the acting name — `nj note`, and `nj claim` / `nj release` without `--as`:
`NJ_AUTHOR` → exit 1, **`invalid_env`**; `--as` → exit 1, **`invalid_value`**.
An `--as` flag outranks the environment, so a malformed `NJ_AUTHOR` does not
fail a command that was given `--as`. **Reads never fail on it:** `list
--ready` (condition 5 below) treats an invalid `NJ_AUTHOR` as no name.
This pins `invalid_env`, until now one of § 9's *reserved* codes, to its first
spec-named path.

Names are labels, not identities: there is no registry, no authentication,
and two agents that choose the same name are the same claimant. This is the
same trust model `assignee` has today (§ 6: "free text, no registry").

## A. `NJ_AUTHOR` — who signs a note

**Promoted to the spec (v3.1)** (DECISIONS 110): see `SPECIFICATION.md` § 10
(note signing), § 9 (failure code), § 15 AC-25. AC-25 is reactivated in
`test/ac/`.

### Motivation

§ 10 signs every note with the element's `assignee`, else `?`. Agents that
review, verify or comment on an element they are not assigned to therefore
sign as the assignee — a false attribution in the one place the spec calls
"the project memory". § 16 lists the override as deferred.

### Interface and rules (amends § 10)

Replace the `<author>` rule of § 10 by:

- Line format: `- <ISO-8601 UTC> <author>: <text>`. `<author>` is the acting
  name (§ 0) if there is one, else the element's `assignee` if set, else `?`.

and add:

- An invalid `NJ_AUTHOR` makes `nj note` exit 1 with `invalid_env` and write
  nothing. Other writes (`new`, `set`, …) do not use the acting name and
  ignore `NJ_AUTHOR`; reads never fail on it (§ 0).
- `NJ_AUTHOR` changes only the note line. It never sets or changes
  `assignee`.

### Touches

§ 10 (author rule), § 9 "Failure codes — spec-named paths" (one row), § 16
(item removed).

| Condition | Code | Stated in |
|---|---|---|
| `NJ_AUTHOR` is not a valid name, on a command that uses it | `invalid_env` | § 0 of this proposal, § 10 |

### Acceptance criterion

25. **Note author.** With `NJ_AUTHOR` set, `nj note` signs with it — whether
    or not the element has an `assignee` — and the note line is otherwise
    byte-identical to § 10's; the value is trimmed. Unset or empty, the
    signer is the `assignee`, else `?`, exactly as in v3. A value that is
    whitespace-only, multi-line or contains `:` exits 1 with `invalid_env`
    and leaves the file byte-identical, while `list`/`show`/`set` under the
    same environment behave as without it. `NJ_AUTHOR` never changes
    `assignee`.

### Open questions — ruled by the lead (2026-09-28)

- **A-1 Whitespace-only `NJ_AUTHOR` — RULED: invalid.** Empty means "not set" (the D89 precedent), but a value of spaces
  is almost certainly a templating bug in an agent's environment, and signing
  it as the assignee would hide the bug in the project memory.
- **A-2 Should `nj new` record a creator?** Out of scope, not ruled; it
  would be a new frontmatter field. Recommendation: not now — `created` plus git history
  answer it, and § 6 excludes history fields on purpose.

## B. `nj unarchive` — the inverse of `nj archive`

**Promoted to the spec (v3.1)** (DECISIONS 110/112): see `SPECIFICATION.md`
§ 11a (rules, refusals, output), § 11 (pointer to § 11a), § 9 (command list,
read-only rule, JSON shape, failure codes), § 4 (`STATUS.md` write list),
§ 12 (compare-before-write, `--force`), § 15 AC-26, § 16 (item removed).
AC-26 is reactivated in `test/ac/`.

### Motivation

Archiving is final today: § 9 makes archived elements read-only "until
`nj unarchive` exists", and § 11 defers it. A finished epic that turns out
not to be finished can only be revived by hand — moving files, deleting the
`archived:` line — which is exactly the manual path that produces
`archive:split` and `layout:misplaced`.

### Interface

```
nj unarchive --id=EPIC-001      (or --file=<path>, § 9)   [--json] [--backlog=<path>]
```

Known flags: `--id`, `--file`, `--json`, `--backlog`. No `--force` (§ 12:
`--force` has one meaning and bulk moves do not take it).

### Rules (new § 11a, after § 11)

`nj unarchive --id=X` moves the archived element X and its **archived
subtree** — every descendant of X that lies below the archive folder — back to
their active places, and is in every respect the inverse of `nj archive`:

- **Placement** follows the configured layout (§ 4) at the time of the
  command, not the layout at archive time:
  - groups `type` and `flat`: each file moves to its active place — the
    folder of its type (`type`), or the backlog's top level (`flat`);
  - group `hierarchy`: the subtree's archived folder moves back as a whole,
    one `rename`, to the same relative place outside the archive folder
    (`archive/EPIC-001/TSK-003/` → `EPIC-001/TSK-003/`). Where the target
    folder already exists — the parent's folder, always present because the
    parent is active — it is merged into by the rules of § 11 (DECISIONS 90,
    94): one `rename` per entry, descending into existing folders, emptied
    source folders removed with `rmdir`, never a recursive delete.
  - Ancestor folders left empty in the archive by the move are removed with
    `rmdir` (names of ID shape only, as `doctor --fix` step 3 does).
- **Frontmatter:** the `archived` key is removed from every moved element and
  `updated` is refreshed. Nothing else changes — `status` stays what it was
  (`done`, by the § 11 precondition). Reopening is a separate, explicit
  `nj set --status=…`.
- **Order and atomicity** as `archive` (DECISIONS 91 B16): every file's
  frontmatter is rewritten in place first, through the guarded write of § 12
  (compare before write, no `--force`), then the moves happen. A crash
  between the two leaves files below the archive folder without `archived:`
  — archived by location (§ 4, DECISIONS 92 Q2), no finding; a second
  `nj unarchive` completes it. `NJ_FAULT=before-rename` fires before the
  first `rename`.
- **All move targets are verified before the first write.** A target is
  occupied only where a file already exists at a file's target path, or a
  file meets a folder (§ 11's rule); then `exists`, and nothing is written or
  moved.

**Refusals** — each moves and writes nothing:

- X is not archived (it lies outside the archive folder):
  `refused:not_archived`.
- X has a `parent` that is itself archived: `refused:parent_archived`. The
  result would be an active child under an archived parent — `archive:split`.
  Unarchive the parent instead; its archived subtree comes with it.
- Any `file:unreadable` stub exists in the backlog: `refused:unreadable` —
  § 9's rule for `rm` and `archive`, for the same reason (the subtree cannot
  be determined), evaluated before the target is resolved.
- Under `hierarchy`, X or a member of its archived subtree does not lie in
  X's archived folder, or a foreign element file does: `refused:misplaced`
  (DECISIONS 92 Q4), pointing at `nj doctor --fix`.
- X's `parent` chain does not resolve (`parent:dangling`, `parent:cycle`, or
  an ancestor with either) — the active place cannot be computed (DECISIONS
  91 B15): `refused:misplaced` as well, same pointer.

Descendants of X that are *not* archived are untouched; they already lie at
their active places.

**§ 9 amendment:** "Archived elements are **read-only**: `set`, `note`, `rm`
and `archive` refuse them; `nj unarchive` is the one write that accepts an
archived element." (Drop "in round one … until `nj unarchive` exists".)

**Output.** Same shape as `archive` (§ 9 table): `{ok, ids: […], changed:
["unarchived"], entries: […], _problems: […]}` — `ids` in the order the
elements were moved (top-down), `entries` the moved elements in their new
state. Human output mirrors `archive`'s. `STATUS.md` is regenerated (§ 4,
"after every successful write" gains `unarchive`).

### Touches

§ 4 (the STATUS.md write list), § 9 (command list, read-only rule, JSON
shapes table, failure codes), § 11 (new § 11a; "Un-archiving … is round two"
removed), § 12 (compare-before-write list gains `unarchive`, `--force` list
unchanged, fault hook coverage), § 14 (nothing: `doctor` already reports
every state a crashed unarchive can leave), § 16 (item removed).

New failure code, additive — `refused:<reason>` gains `not_archived`:

| Condition | Code | Stated in |
|---|---|---|
| `unarchive` on an element that is not archived | `refused:not_archived` | § 11a |
| `unarchive` under an archived parent | `refused:parent_archived` | § 11a |
| `unarchive` while an unreadable stub exists | `refused:unreadable` | § 11a, § 9 |
| `unarchive` of a subtree not lying in its own folder, or with an unresolvable chain (`hierarchy`) | `refused:misplaced` | § 11a |
| an `unarchive` target path is occupied | `exists` | § 11a |

No new problem code.

### Acceptance criterion

26. **Unarchive.** For each group (`type`, `hierarchy`, `flat`) and for
    renamed folders: `archive` followed by `unarchive` of the same element
    returns every file of the subtree to the path it had before the archive,
    byte-identical except for `updated`; the `archived` key is gone; `list`
    shows the elements again without `--all`; `STATUS.md` lists them; a
    following `doctor` is clean. Under `hierarchy`, unarchiving an epic whose
    child task was archived separately earlier brings both back (merge), and
    unarchiving a task under an active epic moves only the task's folder.
    Changing `group` between `archive` and `unarchive` places the files by
    the new layout. `refused:not_archived`, `refused:parent_archived`,
    `refused:unreadable`, `refused:misplaced` and `exists` each exit 1 and
    change no byte of the backlog. With `NJ_FAULT=before-compare` a parallel
    edit aborts with `changed_in_parallel`; with `NJ_FAULT=before-rename`
    nothing has moved and every file is its previous revision.

### Open questions — ruled by the lead (2026-09-28)

- **B-1 Subtree or single element — RULED: the archived subtree**, as
  specified — the exact inverse of `archive`, and the only reading that
  can never leave a descendant stranded in the archive by surprise.
  Unarchiving a task alone is already possible (`--id=TSK-…`); a flag to
  bring back an epic *without* its archived tasks (`--only`) can be added
  later if a real need appears.
- **B-2 Reopen in the same step — RULED: no `--status`.** An `--status=<s>` on `unarchive` would
  save one command, but it would make a move command also a field write with
  its own validation and `done:open_children` interplay. Recommendation: no;
  `unarchive` then `set --status`.
- **B-3 `archived` history — RULED: dropped.** Accepted as recommended — git holds the history (§ 11: "git remains the fine-grained
  history"); keeping a stale `archived:` on an active element would be a
  field whose meaning changed with the file's location, which D92 Q2 just
  ruled out.

## C. `nj claim` — exclusive claiming for parallel agents

**Revised 2026-10-03** to incorporate all seven required changes from the
independent concurrency review (`docs/review/claim-protocol.md`, `e10be45`;
DECISIONS 114) before promotion. Not yet promoted into `SPECIFICATION.md` —
promotion waits until B is accepted (DECISIONS 110), and the Verifier
re-checks this revision against the review's model (variant P3) first.

### Motivation

NanoJira's users are parallel agents (§ 1, AC-7). Today `assignee` is
advisory (§ 16): two agents that read `nj list --ready` at the same moment
both pick `TSK-007`, both `set --assignee=…`, and the second silently
overwrites the first — compare-before-write (§ 12) catches a parallel
*edit* only inside its own narrow window, and `--force` defeats it by design.
The tool that allocates IDs race-free (§ 8) cannot hand out work race-free.

### Principle: a claim is not a lock

§ 12 begins "No lock file. A lock left behind by a crash would be the classic
reason a tool eventually 'hangs'." A claim must honour that. It is therefore
defined as **exclusive only against another claim**:

- A claim never blocks a read, and never blocks a write — `set`, `note`,
  `rm`, `archive`, `doctor --fix` work on a claimed element exactly as on an
  unclaimed one. It blocks only a *competing `nj claim`*, and it hides the
  element from other agents' `--ready` (below).
- A claim left behind by a crashed agent therefore hangs nothing: every
  command keeps working, and the claim is taken over with one explicit
  `nj claim --steal=<holder>`, or cleaned by `doctor --fix` once the element
  is archived or gone (DECISIONS 114 point 6: merely `done` is not enough —
  a done-but-still-live element can still legitimately be claimed).

### Mechanism (new § 12 paragraph "Claims")

**The claim of an element is an append-only sequence of immutable entries**,
one directory per element:

```
<backlog>/.nanojira/claims/<ID>/1
<backlog>/.nanojira/claims/<ID>/2
…
```

Each entry is a file named by its **generation**, a positive decimal integer,
with exactly this content:

```
claimed\n<name>\n<ISO-8601 UTC>\n          (or)          released\n<name>\n<ISO-8601 UTC>\n
```

— the transition, the acting name that made it (§ 0), and its time (`NJ_NOW`
applies, § 12). **The claim state is the entry with the highest
generation**: `claimed <N>` means N holds the claim; `released`, no entry, or
no directory means the element is unclaimed.

**Every change of claim state is one compare-and-swap:** a process that has
read the state at generation *g* writes the new entry completely into a temp
file in the same directory (`.nj-tmp-<pid>-<rand>`, `fsync`, § 12), then
`link()`s it to the name *g+1* and removes the temp file. The first
transition creates the element's directory with `mkdir`; an existing one is
reused. `link` fails with
`EEXIST` when *g+1* exists, so of any number of processes that read
generation *g*, **exactly one** creates *g+1*; every other one learns that
the state moved on, re-reads, and decides again. This is the mechanism § 8
already trusts — exclusive creation, atomic on a local filesystem, no lock —
used as a compare-and-swap instead of a counter. Entries are written whole
before they get their name, so a reader never sees a half-written entry.

`link` can also fail with **`ENOENT`**: the temp file was removed out from
under it (a concurrent `doctor --fix` step 7 sweeping stray temp files — it
has no way to tell a claim's in-flight temp file from a genuinely abandoned
one, the same unguarded window every atomic write in the tool already has),
or the claim directory itself is gone (a concurrent `archive`/`rm`, below).
Both are treated exactly like `EEXIST`: **a retry round** — re-read (a
missing directory reads as unclaimed; `mkdir` recreates it on the next
attempt) and decide again, bounded by the same 100-round limit (DECISIONS
114 point 3, closing review scenarios S8/S9).

Two rules make the sequence safe:

- **Nothing is moved or deleted while the element is live.** Claim, steal,
  release and rollback only *append*. There is no moment in which the claim
  path is empty and a competitor could slip in — the defect of any
  read-then-unlink or move-aside design (see "Why a sequence", below).
  `doctor --fix` never prunes a live claim's entries (below) — that is what
  keeps this rule true.
- **Generations never restart while the element is live.** The highest
  entry is never deleted while the element is active, so a new transition is
  always *max+1*, and a process acting on a stale read always meets
  `EEXIST`, `ENOENT` (above), or a higher entry on its next read. (`archive`
  and `rm` remove the directory entirely; a stale process that appends
  afterwards meets `ENOENT`, retries, and finds the element gone.)

A successful `link()` is sufficient on its own; nothing is re-checked
afterward. An earlier draft of this mechanism added a **post-check** here —
list the directory again after a successful `link()`, to confirm nothing
higher had landed — to defend against live pruning of a still-claimable
directory. The independent review found that pruning unsafe (closing
scenario S6) and removed it below; with no pruning left to compete against a
fresh entry, the post-check has nothing to catch that `link()`'s own
success/`EEXIST`/`ENOENT` outcome hasn't already told the caller, so it is
dropped with it (DECISIONS 114 point 1) — one fewer special case, not a
patch.

The decision loop (read, decide, `link`, on `EEXIST` re-read) is bounded at
100 rounds, like ID allocation (§ 8); exhausting it exits 1 with
`changed_in_parallel`. In practice a round only repeats when another
process's transition landed first, and the re-read then decides the outcome.

The frontmatter mirrors the claim for humans and for git: a successful claim
writes `assignee: <name>` through the guarded write of § 12. **The claim
sequence is the truth for exclusivity; `assignee` is its mirror.** Claims are
local runtime state and are not committed (`.gitignore`, below), because a
claim coordinates processes sharing one working tree, and a claim made in
another clone cannot be honoured without a server (disclosed below).

**Why a sequence, not a single token file** (recorded so the design is not
simplified back). A single `claims/<ID>` created with `O_EXCL` makes the
*first* claim exclusive, but every *change* of holder then needs
compare-and-swap on it, and POSIX has none for a single name. Read-then-unlink
has a gap: two stealers both read holder H, the first unlinks and creates its
own token, the second unlinks that fresh token believing it is still H's —
two winners. Moving the token aside (`rename` to a private name) makes the
move exclusive, but leaves the claim path empty until the mover has decided:
a plain claimant can `O_EXCL`-create into that gap, and if the mover then has
to restore the token (its `--steal` named the wrong holder), the restore
meets `EEXIST` and the legitimately held claim is lost — destroyed by a
*failed* steal. An append-only sequence has no such gap: the claim path is
never empty once claimed, and each transition is one exclusive `link`.

### Interface

```
nj claim   --id=TSK-007 [--as=<name>] [--status=<s>] [--steal=<holder>] [--json]
nj release --id=TSK-007 [--as=<name>] [--json]
```

(`--file=<path>` instead of `--id`, and `--backlog`, as for every write.)
`release` is its own verb: § 9's "verb as a subcommand, not as a flag".

### Rules

**`nj claim`** — with the acting name N (§ 0; none → exit 1,
`missing_argument`, "claim needs a name: --as or NJ_AUTHOR"):

1. Refused before anything is written: an archived element
   (`refused:archived`); X itself an unreadable stub (`refused:unreadable` —
   only the addressed element: a claim reserves one element and moves
   nothing, so § 9's backlog-wide stub guard for `rm`/`archive` does not
   apply); a duplicate id without `--file` (`duplicate_id`); an invalid
   `--status` (`invalid_value`).
2. Read the state at generation *g* and decide:
   - unclaimed → append *g+1* `claimed N`;
   - `claimed N` → N holds it already: **re-assert** by appending *g+1*
     `claimed N` again — one real compare-and-swap, the same as every other
     transition (DECISIONS 114 point 4), not a bare read; this grows the
     sequence by one entry even though the holder does not change —
     `changed` is empty unless `--status` changes the status;
   - `claimed H`, H ≠ N → exit 1, **`refused:claimed`**, naming H and the
     claim time — unless `--steal=H` (below).
   On `EEXIST` or `ENOENT` (another transition landed first, or a concurrent
   sweep/removal — above) re-read and decide again: a racing claimant that
   won is now the holder, and N gets `refused:claimed`.
3. Write `assignee: N` (and `status`, when `--status` is given) in one
   guarded write. If that write fails (`changed_in_parallel`, a fault hook,
   any I/O error), the **rollback restores what this invocation read**
   (DECISIONS 114 point 2, 115): it is **not** always a bare `released N`.
   - **A plain claim** read `unclaimed` (or a `released` entry), so its
     rollback appends `released N` — restoring exactly that.
   - **A re-assertion** read its own prior `claimed N`, so its rollback
     restores `claimed N` — appending `claimed N` again, not `released N`. A
     failed mirror write on a re-assertion must **not** give up a claim N
     already held before the command ran; in effect, a re-assertion's
     rollback has nothing to undo (DECISIONS 115).
   - Either way, if the rollback append itself meets a higher generation
     (`EEXIST` — a stealer took the claim in between), it is abandoned: the
     newer holder is the holder.
   - **A steal is never rolled back.** Once a steal's own `link()` has
     succeeded it is final (DECISIONS 114 point 5, closing review scenario
     S3): a mirror-write failure afterward is reported as `claim:mismatch`
     (below) and N remains the holder on the chain, rather than guessing
     whether some later transition has already relied on the steal having
     landed.
   The command exits 1 with the write's code either way. A plain claim
   either holds with its mirror, or is released again; a re-assertion either
   holds with its mirror, or keeps holding without it (its rollback restores
   the claim it already had, not a release); a steal either holds with its
   mirror, or holds without it; a crash between any append and its write
   likewise leaves `claimed N` without the mirror —
   `claim:mismatch`, below.

`--status=<s>` lets an agent claim and start in one write
(`nj claim --id=TSK-007 --status=doing`), validated as for `nj set`
(`invalid_value`; the parent rule of § 9 applies unchanged).

**Stealing.** `--steal=H` takes over a claim held by H — the only way to
recover from a crashed claimant, and deliberately explicit: the stealer must
name the holder it replaces. With the state read at *g*:

- `claimed H` → append *g+1* `claimed N`. On `EEXIST` or `ENOENT` (above),
  re-read: whatever landed first (another stealer, H's own release, a
  claimant after that release) is decided again from the new state — a
  steal from H succeeds only while H is still the holder.
- `claimed X`, X ≠ H → `refused:claimed`, naming X. Nothing is appended: a
  steal that names the wrong holder changes nothing, and in particular cannot
  disturb X's claim.
- unclaimed → a plain claim of N.

So of any number of concurrent steals and claims **exactly one** changes the
holder, and every other one exits `refused:claimed` naming the holder it lost
to. The result names the previous holder (`stolen_from`).

**`nj release`** — the holder gives the claim up. With the state read at *g*:
`claimed N` → append *g+1* `released N`; on `EEXIST` or `ENOENT` (above)
re-read — if a stealer got there first, `refused:claimed` naming the new
holder, since N no longer has anything to release. `claimed H`, H ≠ N → `refused:claimed` naming H (a
release of someone else's claim is a steal and must say so). Unclaimed →
exit 0, nothing to do. `assignee` is **left as it is** — it records who
worked on the element; clearing it is an explicit `nj set --assignee=`.

**`--ready` (amends § 9 "`--ready`").** Condition 5 is added:

5. the element is unclaimed, or claimed by the acting name.

So `NJ_AUTHOR=agent-7 nj list --ready` shows what agent-7 may take or already
holds, and never an element another agent has claimed. A backlog without
claims answers exactly as in v3. Claims do not affect `list` without
`--ready`, `tree`, `show` or `doctor`'s exit code.

**Visibility.** Every entry object gains the derived field `_claim`:
`{"by": "<name>", "since": "<ISO-8601>"}`, or `null` when unclaimed — derived
like `_problems`, never stored in the element file. Human `list` and `show`
mark a claimed element with its holder. A reader lists the directory and
reads the highest entry; since nothing is ever removed from a live
directory (above), the only way the read can be stale is a transition
landing concurrently — the reader just sees the generation as it was a
moment ago, the same staleness every other `list`/`show` read already has.

**Git (`.gitignore`, amends § 4 and § 14).** `nj init` writes a third
pattern, `.nanojira/claims/`, after the two of § 4. An existing backlog gains
it through `doctor`:

- `doctor` reports **`backlog:claims_unignored`** (warning, backlog-level)
  when `.nanojira/claims/` exists and `.gitignore` has no line that is
  exactly `.nanojira/claims/`. A backlog that never claimed anything carries
  no finding, so v3 backlogs stay clean.
- `doctor --fix` then **appends** the line to an existing `.gitignore`, with
  the discipline of step 0: the line is added exactly once, verbatim, after a
  final newline if the file lacks one, in the file's own line ending (CRLF
  kept, DECISIONS 101) — for a file with **mixed** line endings, the last
  line's ending, or `LF` if the file is empty or its last line has none
  (DECISIONS 114 point 7); nothing else in the file changes. Without a
  `.gitignore`, `--fix` creates none and says so in a note — it is the
  user's file, and its absence may be deliberate.

**Doctor (§ 14).** New problem codes, all warnings, none blocking `--ready`
beyond condition 5:

| Code | Produced by | Doctor | Blocks `--ready` |
|---|---|---|---|
| `claim:mismatch` | the element is `claimed N` but its `assignee` is not N (a crash between the append and the mirror write, or a hand edit) | warning | no |
| `claim:orphaned` | a claim directory for an element that is archived or does not exist (backlog-level when it does not exist) — **not** merely `done`: a done-but-still-live element can still legitimately be claimed (DECISIONS 114 point 6) | warning | — |
| `backlog:claims_unignored` | `.nanojira/claims/` exists and `.gitignore` lacks the line (above), backlog-level | warning | — |

Stray temp files inside `.nanojira/claims/` — a crash between writing an
entry and linking it — are `backlog:stray_tmp` like every other temp file
(§ 12), although the element scan skips `.nanojira/` (§ 4): `doctor` checks
the claims tree for them explicitly.

`doctor --fix` gains one step, after step 7 (stray temp files, which now
covers the claims tree): **7a** remove the claim directories of orphaned
claims — archived or gone, never merely `done` (DECISIONS 114 point 6) —
and append the `.gitignore` line as above. **It never touches a live
claim's entries**: no pruning while the element could still be claimed
(DECISIONS 114 point 1, closing review scenario S6) — the earlier
"prune every live claim directory to its highest entry" step is dropped
entirely, not narrowed. It never resolves a `claim:mismatch` either — which
of the claim and `assignee` is right is exactly the kind of question § 14
forbids guessing. `nj archive` and `nj rm` remove the claim directories of
the elements they move or delete (entries, then `rmdir`; a directory that is
not empty afterwards — a stale process appended in between — is left for
`doctor` as `claim:orphaned`).

`nj unarchive` removes a leftover claim directory for the element it
restores — the same wholesale removal `archive`/`rm` use — **before the
first move**, while the element is still archived (DECISIONS 115, P-6): by
the time an ordinary unarchive reaches this point, `archive` has already
removed the claim directory (above), so this only ever fires on the rare
`claim:orphaned` straggler a partially-cleaned archive left behind (a stale
process appended mid-archive). No legitimate claimant can be active on an
archived element — `claim` refuses one (`refused:archived`) — so this is
always safe to remove outright, never a live claim's entries. A straggler's
own in-flight `link()`, racing this removal, meets `ENOENT` (above), retries,
re-reads the now-archived element, and is refused the same way. Either way,
the unarchived element always starts unclaimed, exactly as a freshly
`new`-created one would.

**Output.** `claim` and `release` return the write result shape (§ 9 table)
plus `claim`: `{ok, id, changed: […], entry: {…, _problems, _claim},
_problems, claim: {by, since}|null, stolen_from?, previous_assignee?}` —
`stolen_from` after a steal, `previous_assignee` when the claim overwrote a
different `assignee` (P-4); `changed` names `assignee` and `status` when
written; a release reports `changed: ["claim"]`.

### Limits, disclosed (add to § 12 "Limits")

- Claims are exclusive among processes on **one** local filesystem — the
  agents sharing a working tree, the case NanoJira is built for. Two clones
  on two machines each accept a claim for the same element; the second push
  then conflicts on `assignee` in git, which is where cross-machine
  coordination belongs. `link()` is part of the "local filesystem" guarantee
  of § 12, like `O_CREAT|O_EXCL` and `rename`.
- A claim guarantees nobody else *claims*; it does not stop an agent that
  ignores claims from writing. That is deliberate (see the principle): the
  alternative is a lock.
- The claim sequence grows by one entry per transition until `doctor --fix`
  removes the whole directory once the element is archived or gone (above) —
  a few bytes per claim, bounded by the number of claims made.
- **A same-named re-assertion that loses a race leaves one doomed entry in
  the history, briefly** (review § 1.5, DECISIONS 114/115): if a
  re-assertion's own mirror write fails just as a separate, successful
  re-assertion or steal under the same name lands ahead of it, the chain
  still shows the failed attempt's entry until the newer one supersedes it —
  its own rollback, which restores `claimed N` rather than releasing it
  (DECISIONS 115), typically meets that newer generation and is abandoned,
  since there is nothing left for it to usefully restore. No process's
  belief about who currently holds the claim is ever wrong — this is a pure
  audit-trail oddity in the *history*, not the *state* — and it is disclosed
  here rather than fixed: closing it would mean giving rollback special
  knowledge that a same-named entry doesn't count as "someone else moved
  on", which reopens exactly the trust question § 0 already settles the
  other way.

### Acceptance criterion

27. **Claims.** Twenty processes run `nj claim --id=TSK-001` in parallel,
    each with its own `NJ_AUTHOR`: exactly one exits 0; the other nineteen
    exit 1 with `refused:claimed` naming the winner; the element is claimed
    by the winner and its `assignee` is the winner's name; `doctor` is clean
    but for `backlog:claims_unignored` where the fixture's `.gitignore` lacks
    the line. A claim by the holder again is exit 0, re-asserting with one
    more `claimed` entry (DECISIONS 114 point 4) — `changed` is empty unless
    `--status` changes the status. `release` by another name is
    `refused:claimed`; by the holder it releases the claim and keeps
    `assignee`. **Steal race:** ten concurrent `--steal=<holder>` have
    exactly one winner, and **no claim is lost** — the final holder is the
    one process that reported success, the claim sequence holds exactly one
    `claimed` entry per successful claim or steal and nothing between them,
    and a steal naming the wrong holder, run concurrently with the others,
    changes nothing. A landed steal whose own `assignee` write then fails is
    reported as `claim:mismatch`, not rolled back — the steal stands
    (DECISIONS 114 point 5). `release` racing a steal of the same claim:
    exactly one of the two succeeds. `NJ_AUTHOR=b nj list --ready` omits an
    element claimed by `a` and lists one claimed by `b`; a backlog without
    claims answers `--ready` exactly as in v3. A claimed element can still be
    `set`, `note`d, archived and removed by anyone, and `archive`/`rm` remove
    its claim. A plain claim whose `assignee` write fails
    (`NJ_FAULT=before-rename`) is rolled back and ends `released`; a
    re-assertion whose `assignee` write fails instead **keeps its claim** —
    its rollback restores `claimed N`, the entry it read, not a release
    (DECISIONS 115). A done-but-live element keeps its claim through
    `doctor --fix` (only archived or gone elements are `claim:orphaned`,
    DECISIONS 114 point 6); a stray temp file in the claims tree is
    `backlog:stray_tmp`, removed by `doctor --fix`. `nj unarchive` of an
    element with a leftover orphaned claim directory removes it wholesale,
    the same as `archive`/`rm`, before the first move: the unarchived
    element always starts unclaimed (DECISIONS 115, P-6). `nj init`
    writes `.nanojira/claims/` into `.gitignore`; on an existing backlog with
    claims, `doctor --fix` appends it once, keeping CRLF, and never creates a
    missing `.gitignore`. `claim` without a name is `missing_argument`; on an
    archived element, `refused:archived`.

### Open questions — ruled by the lead (2026-09-28)

- **P-1 Claims gitignored — RULED: yes.** `nj init` writes the line; existing
  backlogs gain it through `backlog:claims_unignored` and `doctor --fix`
  (above). This is the one byte change to existing output in this proposal:
  init's `.gitignore` (AC-1/AC-2's init fixture follow). AC-24's migration is
  unaffected — a v2 backlog has no claims, so no finding and no append.
- **P-2 `--ready` condition 5 — RULED: accepted.** An opt-in `--unclaimed`
  filter would leave the default racy; backlogs without claims are
  unaffected.
- **P-3 No expiry — RULED: accepted.** A TTL needs a clock both agents agree
  on, and turns "a crashed agent's claim" into "a slow agent's claim silently
  stolen"; explicit `--steal=<holder>` plus orphan cleanup covers the crash
  case.
- **P-4 A claim overwrites a hand-set `assignee` — RULED: accepted**, and
  reports it as `previous_assignee`; refusing would let any stale
  hand-written `assignee` block claiming forever.
- **P-5 No `--ready`-eligibility requirement — RULED: accepted.** Agents claim
  incomplete elements in order to complete them.
- **P-6 Does `nj unarchive` need to clean up a leftover orphaned claim
  directory? — RULED (DECISIONS 115): yes**, option (b). `nj unarchive`
  removes a leftover claim directory wholesale, the same removal
  `archive`/`rm` use, while the element is still archived and before the
  first move — an unarchived element always starts unclaimed (above,
  "Doctor"). No legitimate claimant can be active on an archived element
  (`claim` refuses one), and a straggler's `link()` meets `ENOENT`, retries,
  and is refused the same way; it never inherits a pre-archive claim.
