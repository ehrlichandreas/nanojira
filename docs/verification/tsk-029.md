## `workingDir()` doesn't change resolution

From a cwd entered through a symlink (`<R>/lnk` → `<R>/real/a/b`), with
`PWD=/nonexistent/logical` set, V3-2 and `ccbc951` give identical results:
- `--backlog=../../../other/backlog` → `<R>/other/backlog`;
- `NJ_BACKLOG=../../backlog` → `<R>/real/backlog`;
- `--description-file=../d.txt` reads `<R>/real/a/d.txt`.

All three resolve against the physical cwd, `$PWD` is never consulted, and
this is v2 behaviour (F7). The only other relative resolutions are a
`.njrc` value (against its own directory) and `--file` (against the
backlog); neither touches the cwd.

## Findings

**T1 — medium, security: the ownership check (F1) and the FIFO fix (D90) can be raced.**

- **The window.** `readNjrc` checks `lstat(file)` (link owner), then
  `stat(file)` (target owner and type), then `readFileSync(file)`: three
  lookups by path. Anyone who can write to the directory holding the `.njrc`
  can present one file to the checks and another to the read.
- **What the attacker needs.** A decoy that passes the check, i.e. a regular
  file owned by root or by the victim. On macOS an unprivileged user can
  **hardlink other users' files** into a directory on the same volume
  (checked: `ln /private/etc/hosts` gives a uid-0 link;
  `ln /Library/Preferences/com.apple.AssetCache.plist` a uid-235 one). The
  decoy is therefore free.

**Demonstration** (all as me, uid 502):

- `.njrc` is swapped atomically (`rename`) between a hardlink of
  `/private/etc/hosts` (root, passes the check, parse error "line 7") and
  a hardlink of a uid-235 plist (refused: "owned by uid 235").
- Of 300 runs of `nj list`:
  - 152 refused on the payload;
  - 144 read the decoy;
  - **4 reported "line 1: unknown key '<?xml version'"**, i.e. they parsed
    the uid-235 file's content after the ownership check had passed. With
    the attacker's own file as payload, the victim's `nj` would obey it
    (F1's `/tmp` scenario).
- The same race with a regular file and FIFOs **hung `nj` in 1 of 150 and
  1 of 200 runs**: `stat` saw a regular file, and `readFileSync` opened the
  FIFO.

Scripts: `/tmp/nj-audit-mut/toctou-*`, `/tmp/nj-audit-mut/own-*`
(`swap.js`, `runner.js`).

**Fix:** check what is read.
1. `lstat` for the link owner, as now.
2. Then `fd = openSync(file, O_RDONLY | O_NONBLOCK)`.
3. `fstatSync(fd)` for the target's owner, `isFile()` and ELOOP/ENOENT
   handling.
4. Read from the same `fd`.

`O_NONBLOCK` makes a FIFO fail fast instead of blocking. The remaining
lstat/open gap only concerns the *link's* owner. The bytes read are then
always the ones whose owner was checked.

**T2 — medium: the top-level net relabels a real bug as `io_error`, and the bug leaves a half-archive that `doctor` calls clean.**

- **The net.** `nj.ts` now maps *every* error with a string `code` and
  `syscall` to `io_error`, one line. That is right for genuine OS answers
  (A5 above). But a product bug that ends in a failing syscall now looks
  like an environment problem, and loses the stack that said "bug".
- **A real case found** (V3-2 code, the net is `ccbc951`):
  - Under `group: hierarchy`, with `archive/EPIC-001` present as a regular
    *file*: `nj archive --id=TSK-001` gives V3-2 `internal_error` + stack;
    `ccbc951` gives `io_error` — `EEXIST: file already exists, mkdir
    '<abs>/archive/EPIC-001'`.
  - DECISIONS 94 says the merge planner verifies every target before the
    first move, and that a file/folder mismatch is a conflict (`exists`,
    nothing moved). The planner missed it.
  - Afterwards the active `EPIC-001/TSK-001/TSK-001.md` carries
    `archived: 2026-09-21T18:00:00Z` (stamped in place per D91 B16 before
    the failing `mkdir`). `nj list` shows TSK-001 as active, and `list
    --json` gives it an `archived` timestamp with `_problems: []`.
  - `nj doctor`: "2 entries, 0 errors, 0 warnings". The stray file
    `archive/EPIC-001` is not reported either.
  - After removing the file, a retry archives correctly, without a double
    stamp.
- **The same shape** (a file where `nj` needs a folder) gives a bare
  `io_error` EEXIST in `mkdir` for:
  - `archive` as a file (groups `type` and `hierarchy`);
  - `tasks` as a file (`new`);
  - a file `EPIC-001/TSK-002` where `new` must create the task's folder.

  These are defensible as "an OS answer about a path", but a named
  `exists`/conflict would say what is wrong. Missing folders (`archive/`,
  `tasks/`, `subtasks/`, `.ids/` after a clone) are all handled correctly,
  by creating them.
- **Recommendations:**
  1. **Forward the half-archive to Verifier-B (V3-2):** the planner's
     file/folder check, and a doctor finding for an active element carrying
     `archived:`.
  2. Keep the net, but let it add what `nj` was doing (the command), and
     keep `internal_error` for errors thrown outside the known I/O helpers.
     Or print the stack under an env switch, so a bug still has a way to
     show itself.

**T3 — low–medium: spaces-and-tabs trimming makes other whitespace significant, and the messages hide it.**

- Before, `trim()` removed all Unicode whitespace. Now NBSP, `\v`, `\f`
  and U+2028 at a value's end stay part of the path:
  - `invalid_backlog_njrc` "no backlog at `<abs>/backlog ` (from …)", where
    the trailing character is invisible;
  - a line holding only NBSP or `\v` is now `invalid_njrc` "no '=' in ' '".
- A BOM at the start of line 2 is, as D98 rules, part of the key. The
  message then reads **"unknown key 'backlog'"**, because the BOM is
  invisible, which contradicts itself on screen.
- The behaviour is defensible (§ 4 doesn't define whitespace; D98 wanted
  the BOM counted). The messages aren't. **Fix:** quote key and value with
  escapes (`JSON.stringify`, or `\uXXXX` for anything outside printable
  ASCII) in every `.njrc` error, so the invisible character shows. § 4
  could also name the whitespace set ("space and tab").
- CRLF, a tab-indented comment, and a BOM at the very start still work. A
  lone `\r`, mid-file or as the last byte, is `invalid_njrc` at its line, as
  D98 rules. Frontmatter and every other parser are untouched: only
  `config.ts`'s `.njrc` code changed.

**T4 — low: a legitimately committed `.njrc` owned by another account is a hard error with no way out named.**

- Examples: a repo cloned by root or a CI user, a checkout on a shared or
  NFS filesystem, `sudo git clone`. Every `nj` run below it that reaches the
  `.njrc` fails with `invalid_njrc` "owned by uid N, not by you", and there
  is **no hint**.
- `--backlog`/`NJ_BACKLOG` bypass it, since they never read a `.njrc`.
- **Fix:** add the hint: "use --backlog=<path> or NJ_BACKLOG, or chown the
  file". git's `safe.directory` is the precedent for also offering an
  explicit trust setting.

**T5 — info.**
- The target-owner check works statically: my symlink → a uid-235 target is
  refused; my symlink → a root-owned target is accepted and parsed.
- The non-POSIX skip (`typeof process.getuid !== 'function'`) turns the
  check off entirely where uids don't exist. Windows isn't a target
  platform (§ 12), so this is acceptable and stated in the code.
- Running as root accepts only root-owned `.njrc` files, which is the right
  direction.
