# v3.10 verification (TSK-058/059, D182, spec § 14 step 7b / § 15 item 57)

Scope under review: `522ef5c` (implementation) + `652a027` (tests, red) +
the final `4d0a9c3`/`72c41cd` version bump. D182:

- (A) `nj doctor --fix` releases every claim held on an element in the
  final configured status, live or archived, whoever holds it, via the
  same unconditional release mechanism v3.8 B already uses, recorded
  identically in the claim log. Claims on unfinished elements are never
  touched, stale or not. Plain `doctor` (no `--fix`) never writes.
- (B) the last remaining "a epic"-style message (the `--input`
  plan-nesting validator's wrong-type-child error) is now routed
  through `article()`.

## 1. Diff review

`src/commands/cmd-doctor.ts`:
- `fixStep7a` (orphan claim-dir removal, pre-existing) now captures the
  holder via `highestEntry(dir)` **before** `removeClaimDirWholesale`,
  and reports `"${id}: released ${holder}"` when the highest entry was
  a `claimed` one, falling back to the old generic "removed the
  orphaned claim directory for ${id}" when it wasn't (e.g. only a
  `released` entry, or an empty dir).
- `fixStep7b` (new): iterates `allClaimDirs`, skips any id whose element
  isn't live or isn't in `cfg.statuses[cfg.statuses.length - 1]`, and
  for the rest calls `releaseUnconditional(ctx.backlog, id, ts)` —
  the exact same primitive v3.8 B's auto-release-on-final-status uses
  — reporting `"${id}: released ${holder}"` whenever something was
  actually released. Wired into `doctorFix` between `fixStep7a` and
  `fixStep8`.

`src/commands/cmd-new.ts`: one-line change in `validatePlanNode`'s
wrong-type-child message, now `` `${article(parentType)} ${parentType}
cannot have ${article(String(type))} ${String(type)} child` ``.

`src/core/claims.ts`: unchanged. Read `transition`'s CAS loop closely —
each round calls `highestEntry(dir)` **fresh** and attempts its write
at `baseGen + 1`, retrying on `EEXIST`/`ENOENT`. `releaseUnconditional`
never carries a stale, previously-scanned holder name into its write;
it always targets whoever is the *current* holder at write time. This
is the structural reason `fixStep7b` is race-safe (see § 5).

## 2. `--fix` releases final-status claims, live and archived, any holder

Built `/tmp/verifier-v310/bl3/backlog`: a live task through `nj new` →
`nj claim --as=alice` → hand-edited `status: done` directly in the
frontmatter (bypassing `nj set`, to leave the claim dir still in a
`claimed` state — simulating data that reached `done` without going
through the status-change path that already auto-releases per v3.8 B).
`doctor --fix --json` →
```
"fixed": ["TSK-404: released carol", "TSK-001: released alice"]
```
(`TSK-404` is this round's orphan-dir fixture, see § 5.) Claim log for
`TSK-001` gained a new generation `2: released\nalice\n<ts>\n`;
`nj show --id=TSK-001` reads `_claim: null` afterward.

Archived case: in the AC-55 oracle run (`C3`), a `done` element moved
to `archive/` with a hand-reconstructed claim dir is released
identically — confirmed reading `ac-55`'s C3 block and its 25/25 pass
against `dist/nj`.

## 3. Claim-log entry matches v3.8 B

## 4. Claims on unfinished elements are untouched, stale or fresh

Built `/tmp/verifier-v310/bl2`: two `todo` tasks (`TSK-001`, `TSK-002`),
each with a hand-written claim dated `2020-01-01T00:00:00Z` (well past
the 24h staleness threshold). Plain `doctor --json` reports
`claim:mismatch` + `claim:stale` for both, writes nothing. `doctor
--fix --json` → `"fixed": []`; both claim dirs unchanged (still just
generation `1`); the same two warning pairs still present afterward.
Freshness doesn't matter either — confirmed on a second combined run
(§ 5) where a `todo` task with a *fresh* claim sat alongside a `done`
one in the same `--fix` invocation: only the `done` one's claim moved,
the `todo` one's claim and its `claim:mismatch`/`claim:stale` warnings
were completely unaffected by the same call.

content of every claim-dir file and every element file byte-identical

(confirmed against AC-55's C5).

## 7. Interaction with step 7a (orphaned claim dirs)

Same `/tmp/verifier-v310/bl3/backlog` fixture as § 2, but built with
*both* cases present in one run:
- `TSK-404`: a claim dir for a nonexistent id (`claimed\ncarol\n...`) —
  step 7a's orphan-removal target.
- `TSK-001`: the live `done` task with a still-`claimed` entry (`alice`)
  — step 7b's target.

Single `doctor --fix --json` →
```
"fixed": ["TSK-404: released carol", "TSK-001: released alice"]
```
`TSK-404`'s claim directory was removed wholesale (step 7a, holder
captured before removal per § 1); `TSK-001`'s claim dir gained a new
`released` generation in place (step 7b). Both fired in the same pass
without interfering with each other; re-ran `--fix` once more
afterward — `"fixed": []`, confirming idempotency holds across the
combined case too.

## 8. Concurrency: a claim taken between scan and fix?

Hand-constructed a double-generation claim dir before running `--fix`
once — generation 1 `claimed\nalice\n...`, generation 2
`claimed\nbob\n...` — simulating a steal that happened between any
scan step 7b might do and its write. `doctor --fix` released **bob**
(the current/latest holder at write time), never alice. This matches
the structural argument in § 1: `releaseUnconditional`'s `transition`
re-reads `highestEntry(dir)` fresh on every CAS round and targets
whoever that read finds, so step 7b's earlier scan only decides *which
ids* to attempt, never *who* to release — a claim taken (or re-taken)
between the scan and the write is released correctly, not bypassed or
stale-released.

## 9. The report names id + holder; "TSK-404: released nobody"

Confirmed in `fixed[]` output throughout: every release line is
`"${id}: released ${holder}"`, both prose and JSON array entries (same
array, `--json` just serializes it).

The gate-observed **"TSK-404: released nobody"** wording, investigated
specifically: `test/ac/ac-27-claim.js`'s existing orphan-removal test
case (`C9` block, "doctor --fix: orphan removal only") hand-writes
`writeGen(x, 'TSK-404', 1, 'claimed', 'nobody', LATER)` — `'nobody'`
here is a **literal test-fixture holder name**, not a code-generated
sentinel for "no holder". `TSK-404` is a nonexistent element id used to
exercise the orphan-dir path. The message is honest: the orphaned claim
directory genuinely was held by a (fictional) user named `nobody` in
this fixture. Not a bug. Reproduced directly: a fresh orphan claim dir
hand-written with holder `carol` reports `"TSK-404: released carol"`
(§ 7) — the holder name is read straight from the claim log, whatever
it happens to be.
