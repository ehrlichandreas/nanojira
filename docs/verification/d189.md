# D189 verification (refactor-harness scratch probes clean up)

Adversarial verification of `c58634e` (the fix) plus `36e9d8d` (the red
test, `test/edge/refactor-harness-scratch-cleanup.js`), against
`docs/DECISIONS.md` item 189 (`3ff56f8`): every white-box probe under
`tools/refactor-harness/scratch/` must remove the `mkdtempSync` fixtures
it creates, on success, on failure, and on an uncaught exception, never
touching anything else under `HARNESS_SCRATCH_BASE`.

## 1. Diff review

`c58634e` adds `tools/refactor-harness/scratch/lib/cleanup.js` — a
`created` array, a `track(dir)` that pushes and returns its argument
unchanged, and a single process-wide `process.on('exit', …)` handler
that `rmSync(dir, {recursive:true,force:true})`s every tracked
directory, best-effort. Each of the 10 probes (`bc.js`, `r3.js`,
`r3bc.js`, `r4.js`, `r4bc.js`, `r5.js`, `r6.js`, `r6bc.js`, `r8.js`,
`verify.js`) gets one new `require('./lib/cleanup.js')` line and wraps
every `fs.mkdtempSync(...)` call site in `track(...)`.

Grepped the whole `scratch/` tree for `mkdtempSync` directly (not
trusting the diff's own framing): **13 call sites across the 10
files, every one already wrapped in `track(...)`** — including the
three sites that are NOT a probe's main `mk()` helper (`r5.js`'s extra
inline `mkdtempSync` for its `init --json` fixture, and `verify.js`'s
two extra inline calls for its discovery and no-backlog fixtures).
`r4bc.js`'s `mk()` reuses the `r3bc-` label prefix (a pre-existing
copy-paste artifact, not introduced or touched by this commit) — noted
for completeness, not a D189 defect.

`track()` only ever queues the exact path `mkdtempSync` just returned —
nothing computed, no globbing, no parent-directory removal — so "only
paths the probe created itself" holds by construction, not just by
observation.

## 5. Edge cases

**Older tags/worktrees without `scratch/lib/cleanup.js`.** `gate.js`
obtains its worktree with a full `git worktree add --detach WT
<step>`, so `tools/refactor-harness/scratch/` at `WT` is always whatever
existed at that exact step's own commit — a step before D189 has the
old, un-wrapped probes AND no `lib/cleanup.js`, self-consistently (old
behaviour, litters `/tmp` again, but nothing crashes). `--harness=<rev>`
overlays the *entire* `tools/refactor-harness` directory from one
revision in one `git checkout <rev> -- tools/refactor-harness`, so
`scratch/*.js` and `scratch/lib/cleanup.js` always arrive together from
the same revision — never mixed. `baseline.js`'s own `SCRIPTS` constant
resolves relative to its own `__dirname`, i.e. to whichever
`tools/refactor-harness` is active in `WT` at the time, same guarantee.
**Not a gap** — confirmed by reading `gate.js`'s `useTests`/`--harness`
code, not assumed.

**SIGTERM / SIGINT / a timeout kill.** This is not hypothetical — it
happened on the Implementer's own gate run on `c58634e`
(`/tmp/implementer-d189-gate.log`): `refactor-harness-scratch-
cleanup.js` failed 1/23, `bc.js` leaving all six `bc1..bc6` directories
behind. I reproduced the mechanism directly: ran `r6.js` in the
background with a fresh scratch base, sent it `SIGTERM` after 0.3 s.
Result: exit code 143 (128+15, the standard signal-killed convention),
and **every directory the probe had created up to that point was left
behind** — the `process.on('exit', …)` handler in `lib/cleanup.js`
never ran, because Node's default disposition for `SIGTERM` (no
listener registered) terminates the process immediately without firing
`'exit'` at all. The test's own `runProbe()` passes a `120000` ms
`spawnSync` timeout, which sends `SIGTERM` to an overrunning probe by
default — under load (as in the gate's own CPU-contended run), a probe
that would normally finish well inside that window can be killed mid-
run. This is a real, gate-observed gap in `c58634e`, not a theoretical
one, and the Lead's own condition for calling it a defect rather than a
documented limitation ("unless the gate actually kills probes") is
met.

A second, smaller gap: the test's own failure messages (`T.check(...
!r.error ...)`, `T.eq('... is empty ...', ...)`) never surface `r.status`
or `r.signal` — a signal-killed run and a genuine cleanup bug currently
print the identical "leftover directories" message, with nothing in the
test's own output distinguishing them. Confirmed by re-reading the test
file: neither call site threads `result.status`/`result.signal` into
its `detail` argument.

As of this writing, the Implementer has an in-progress, uncommitted fix
for the signal gap (`SIGTERM`/`SIGINT`/`SIGHUP` handlers in
`lib/cleanup.js` that clean up and re-raise), independently confirmed by
the Lead; verifying that follow-up is a separate task and out of this
report's scope — left untouched here per the usual rule against acting
on another agent's in-progress, uncommitted work.

## Addendum: the signal follow-up (`84b2605` + `f7f9f65`)

`84b2605` gives `lib/cleanup.js` its own `SIGHUP`/`SIGINT`/`SIGTERM`
handlers: each one runs `cleanup()`, removes its own listener, then
`process.kill(process.pid, name)` — re-raising the same signal against
the now-listener-free disposition, so the default action still
terminates the process by that signal. `f7f9f65` adds three `bc.js`-only
legs (poll for the first fixture, send the signal, assert
`result.signal === '<the signal>'` AND an empty scratch base) and
threads `status`/`signal` into every existing "empty afterwards"
failure detail, closing the second, minor gap named above.

**Diff review.** Both gaps named in the base report are addressed
exactly as described; nothing else in `lib/cleanup.js` changed.

**Mutations**, both in the shared tree, restored immediately via `git
checkout -- tools/refactor-harness/scratch/lib/cleanup.js` each time
(confirmed clean before continuing — a parallel teammate correctly
flagged a brief window where the first restore had not yet landed; see
below):

- Removed the `process.kill(process.pid, name)` re-raise line: **3 of
  32 checks fail**, exactly the three new `bc.js` signal legs, each
  reporting `got code=1 signal=null` — the probe now survives the
  signal outright (its own code continues and exits normally) instead
  of dying by it.
- Removed `'SIGHUP'` from the `SIGNALS` array (kept `SIGINT`/`SIGTERM`):
  **1 of 32 checks fail** — only the `bc.js SIGHUP` leg, naming the
  leftover `bc1-*` directory and `signal=SIGHUP` (the OS still killed
  the process by the un-handled signal, it just never got a chance to
  clean up first).

**Live repro, beyond `bc.js`.** Ran `r6.js`, `r3.js` and `verify.js`
under all three signals too (poll for the first fixture, signal, wait).
All three leave an empty scratch base in every case — no litter,
confirming the safety property holds repo-wide, not just for `bc.js`.
But the parent-visible exit shape differs from `bc.js`'s: `wait`
reported plain exit code `0` (normal completion), **not** a
signal-terminated exit, for `r6.js`/`r3.js`/`verify.js` under all three
signals, while the identical technique against `bc.js` reliably gives
`143`/`130`/`129` (128+15/2/1, i.e. truly killed by the signal). Node
only delivers a re-raised signal once the event loop gets a turn; these
three probes run a tight, purely synchronous `spawnSync` loop with a
20 s timeout each but no artificial delay, and in practice outrun the
asynchronously-redelivered signal and reach their own normal `exit(0)`
before the second copy of the signal is ever processed. `bc.js` (and
`r3bc.js`/`r4bc.js`/`r6bc.js`) instead `spawn()` their fault-injected
child asynchronously and sit in an ~10 s idle `await`, giving the event
loop ample room to act on the re-raised signal, so it reliably dies by
it. **Net effect: the actual safety property (no leftover fixtures)
holds for every probe under every signal, confirmed empirically, not
just for `bc.js` — but the stronger claim "the probe dies BY the
signal, not by its own exit code" that `f7f9f65`'s comment and the
committed test assert is only demonstrated for `bc.js`, and does not
generalise to the purely-synchronous probes.** This is not a defect in
`84b2605` or `f7f9f65` — both are honest about testing "one probe is
enough to prove the class of bug" — but it is worth naming precisely,
since the Lead asked directly whether the re-raise really gives the
parent `signal=…` and not an exit code: for `bc.js`, yes; for the
purely-synchronous probes, empirically, usually no (the signal is
absorbed without visibly terminating the process), though no fixture
ever leaks either way.

**Edge cases, as asked:**

- *A probe blocked inside `spawnSync(nj, …)` only handles the signal
  once the child returns.* Confirmed: synchronous blocking calls hold
  the main thread, so the JS-level signal handler cannot run until
  control returns to the event loop. Longest bound: the `20000` ms
  `spawnSync` `timeout` used by `r3.js`/`r4.js`/`r5.js`/`r6.js`/
  `verify.js` (grepped every `timeout:` in `scratch/*.js` — `20000` is
  the maximum anywhere; `r8.js`'s one `spawnSync` call has no explicit
  timeout at all, unbounded in theory, bounded in practice by `nj`
  itself always returning quickly for an ordinary `set` call). 20 s is
  an acceptable worst-case latency for a developer-run or gate-run
  probe-kill, not a user-facing path.
- *A second signal during cleanup.* `cleanup()` is idempotent
  (`rmSync(..., {force:true})` inside a `try/catch`, safe to run twice
  on the same, already-removed path) and JS is single-threaded, so a
  second delivery of the same signal cannot interleave with an
  in-progress handler invocation — at worst it is coalesced by the OS
  (standard, non-queuing POSIX semantics for non-realtime signals) or
  processed as a second, harmless `cleanup()` call once the first
  handler returns. Not a reachable corruption path.
- *`SIGKILL`.* Reproduced directly: `kill -KILL` on a `bc.js` run with
  one fixture already created → `wait` reports `137` (128+9), and the
  fixture is left behind every time. This is an **unfixable, documented
  known limit** — no userspace process can install a handler for
  `SIGKILL` — not a defect in `84b2605`.

**Output identity.** Re-ran all 10 probes at the final HEAD for this
task (`f7f9f65`) against a matching detached worktree at `3e5e22b`,
both sides with their own isolated `HARNESS_SCRATCH_BASE`. One probe

times). With that fixed, all 10 probes show only `mkdtemp` suffixes and

**Gate** (`/tmp/implementer-d189b-gate.log`, `f7f9f65` against

### Addendum verdict

**PASS. The SIGTERM/SIGINT/SIGHUP gap named in the base report is
CLOSED**, confirmed by the gate's own before/after (`c58634e` red 1/23,
`f7f9f65` clean) and by direct, repeated `SIGTERM`/`SIGINT`/`SIGHUP`
repro against `bc.js` and three other probes — zero fixtures left

nuance is worth carrying forward, not blocking: the "dies by the
signal, not an exit code" property is demonstrated for `bc.js` only;
the purely-synchronous probes keep the safety guarantee (no litter) but
can finish via their own normal exit code before the re-raised signal
lands, so `result.signal` is not a reliable way to detect "this probe
was killed" for those probes specifically.
