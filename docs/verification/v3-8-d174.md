## 2. Real mid-plan write failure (H4, D174.1's real leg)

Live reproduction of AC-52's own H4 scenario: `epics/`+`tasks/` writable,
`subtasks/` `chmod 555` after the epic and task (`@t`) already wrote.
Plan: epic → task (`ref:"@t"`) → subtask (`ref:"@a"`).

```
{"ok":false,"error":"internal_error",
 "created":["EPIC-001","TSK-001"],
 "refs":{"@t":"TSK-001"},
 "failed_at":"@a"}
```

- `created` lists exactly what was actually written before the failure.
- `refs` holds `@t` (the task really was written) and correctly
  **excludes** `@a` — the failing subtask's own ref never appears,
  even though it was declared. This is the D174-correction half
  (`848b111`): the first draft of this fix asserted the opposite and the
  Lead caught it before I saw this commit; I re-derived the same
  counterexample independently (a `refs` entry pointing at an id nothing
  was ever written to is the same silent-wrong-answer class D173
  removed from `depends_on`) and it holds.
- `failed_at` names `@a` by its own declared ref, matching `labelOf`'s
  existing precedent for a thrown-`Fail` mid-plan failure.
- The subtask file itself: confirmed absent from `subtasks/` on disk.
- `internal_error` is the correct code here (not `io_error`, which is
  reserved for `init`'s own target and the working-directory check
  specifically per § 9's table) — consistent with what a plain `nj set`
  on the same read-only target already returns.

The fix generalizes the write loop's `catch` from "enrich only a thrown
`Fail`, reraise anything else bare" to "enrich any error that isn't the
write-phase's own invariant assert" (§ 3), wrapping a raw OS error
(`EACCES` here) in a `Fail` so it gets the same `created`/`refs`/
`failed_at` treatment as a thrown `Fail` already got before this fix.

## 3. The D173 invariant assert still crashes loudly

The one thing this broadened `catch` must **not** do is swallow a broken
internal invariant (an unresolved `@ref` reaching the write phase at
all — validation is supposed to rule this out entirely) and dress it up
as an ordinary plan failure. Confirmed by mutation, not by reading: I
disabled the "declared earlier" forward-ref check in `validatePlanNode`
(`if (false && !declaredSoFar.has(d))`), rebuilt, and fed a plan with a
task `depends_on`-ing its own just-declared `@ref` (a self-reference the
validator would normally reject). With the validator gap open, the
invalid ref reaches the write-phase assert:

```
Error: unresolved ref '@t' reached the write phase at [0].children[0]
  — this must have been caught at validation
    at ... (stack trace, not swallowed)
{"ok":false,"error":"internal_error"}
```

No `created`, no `refs`, no `failed_at` — this is `nj.ts`'s own generic
top-level `catch` (`anything that reaches here keeps its stack`), not
`emitPlanFailure`. The `InternalInvariantBroken` class the fix introduces
is checked and rethrown (`if (e instanceof InternalInvariantBroken) throw
e;`) before the broadened catch's generic-error branch ever runs, so it
never gets the write-failure enrichment. Restored the validator mutation
afterward; `node tools/bundle.js --check` confirmed `dist/nj` byte-
identical to pre-mutation.
