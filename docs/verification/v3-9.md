## 1. `set --parent` — the move itself (A1-A3)

Hierarchy fixture (`EPIC-001`/`EPIC-002`, `TSK-001` with subtask `SUB-001`
holding a note and a claim):

- **Subtask reparent**: `set --id=SUB-001 --parent=TSK-002` moved the file
  to `EPIC-002/TSK-002/SUB-001.md`. `id`, `title`, body (description +
  acceptance), the note (`nj log` still shows `created`/`claimed`/`note`
  in order) and the claim (`_claim: {by: "alice", ...}`) all read back
  identical at the new path.
- **Task-with-children reparent**: `set --id=TSK-001 --parent=EPIC-002`
  (`TSK-001` owning a live child `SUB-002`) moved the **whole folder** —
  `SUB-002`'s own file came along, still named `SUB-002.md`, still with
  `parent: TSK-001` **unchanged** (it never moved relative to its task;
  the folder moved, not the child's own relationship). Confirmed by
  listing both subtrees before and after, not just checking the task's
  own file.
- **Type-group and flat layouts**: same reparent under `layout.group:
  "type"` (the default) and `"flat"` — in both, the file never leaves
  its folder (`tasks/TSK-001.md` throughout); only the frontmatter's
  `parent` field changes. Direct contrast with the hierarchy case above.

## 3. No-op, combined fields, batch, `--input`, round trip

- **No-op**: `--parent` equal to the current parent: `changed: []`,
  `updated` **unchanged** (not merely unwritten-but-bumped) — a true
  no-op, not a write that happens to produce identical bytes.
- **Combined with another field**: `--parent=EPIC-002 --title="T1
  renamed"` in one call: `changed: ["title", "parent"]` (flag-processing
  order, as the code comment promises), file moved AND retitled in the
  same write.
- **Batch**: `set --id=SUB-002,SUB-003 --parent=TSK-002` — per-id,
  independently: `SUB-002` (previously elsewhere) moved and reports
  `changed: ["parent"]`; `SUB-003` (already there) reports `changed: []`
  — same no-op discipline inside a batch as standalone.
- **`--input`**: `{"parent":"TSK-001"}` via `set --input=-` moved the
  file exactly as the flag form does.
- **Round trip**: moved `SUB-003` away and back (`TSK-002` →`TSK-001`→
  `TSK-002`); `diff` of the two frontmatter blocks with `updated:` lines
  stripped: **zero bytes different**. This is DECISIONS 177's
  replacement for D176's mistaken "`nj undo`" — confirmed to actually
  hold, not merely that AC-53's own A9 leg passes.

## 4. Concurrency / compare-before-write guard on the moved file

Built a standalone rendezvous script (same protocol as
`test/fault/nj-fault-before-compare.js`: `NJ_FAULT=before-compare` pauses
after the first read, a parallel writer mutates the target file, then
drops `.nj-fault-go` to release `nj`).

- **Without `--force`**: a `set --parent` racing a concurrent edit of the
  *same frontmatter file* (not yet moved) is refused —
  `changed_in_parallel`, exit 1 — and the file never moves (confirmed:
  still at the old path, nothing at the new one). The guard runs on the
  frontmatter write, which happens **before** `runMove` — exactly the
  ordering `cmd-set.ts` promises (`movePlan` is only *run* after the
  guarded write lands).
- **With `--force`**: the write proceeds (overwriting the parallel
  writer's change, standard `--force` semantics elsewhere), **and the
  move still completes** — file lands at the new path, old path gone.

This is new coverage beyond AC-53's own legs (which don't exercise the
fault hook) and confirms the guard composes correctly with the new move
step rather than being bypassed by it.

### 11a. `8b23bfe` — nj-mcp finds its sibling by its own extension

`path.dirname(argv[1])` with the literal `'nj'`. Under a D179 release
layout (`<ver>/nj.cjs` + a `nj`/`nj.cmd` wrapper pair, `current/` another

checks its own basename: `path.basename(argv[1]).endsWith('.cjs')` picks
`'nj.cjs'` for the sibling when running as `*.cjs`, `'nj'` otherwise —
matching `dist/`'s own flat (no-extension) layout exactly, so nothing
changes for the everyday dev build.
