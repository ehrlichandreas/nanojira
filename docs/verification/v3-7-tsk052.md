## 1. E/F acceptance quality warnings

**Diff review.** `core/load.ts`'s `loadElement`-path addition is gated by
`el.type === 'task' || el.type === 'subtask'` (the outer `if`) — an
epic never reaches either branch, confirmed live (AC-49 E5). Within
that gate: `!acceptanceOk` (section absent/empty) adds
`incomplete:acceptance` and, only when additionally `el.status ===
'done' && !el.archived`, also `done:no_acceptance` (F) — the archived
exemption (D167) is an explicit `&&`, not inherited from anything else.
The `else if` branch (section present with content) adds
`acceptance:no_checkbox` (E) only when `!sectionHasCheckbox(...) &&
!el.archived` — structurally exclusive with F, confirmed by the
`if`/`else if` shape, not just by convention. `sectionHasCheckbox`
(`core/parse.ts`) scans strictly between the section's own heading and
`sectionEnd` (next `#`/`##` or EOF) using the exact same `CHECKBOX_RE`
`nj check` itself uses, and skips fenced-code-block spans (`` ``` ``/`~~~`,
tracked by a `fence` state variable) — one shared regex and one shared
section-boundary function, so E's scan and `check`'s own scan can never
disagree on what counts.

- Both warnings' write-feedback prose reproduces exactly: `⚠ TSK-009 has

**Mutation testing.** Removed the `!el.archived` exemption from both E

## 2. `problems.ignore` — and a structural test-coverage finding (I8)

**Diff review.** `cmd-doctor.ts`'s finding list is filtered once, at the
very end, by `ctx.cfg.problems.ignore` — one `filter` call covering
both backlog-level and element-level findings, confirmed to run after
every other `findings.push(...)` site, not threaded individually into
each. `core/derive.ts`'s `elementProblems(el, ignore)` (used by `show`,
`list`, write feedback, and `archive`/`unarchive`'s own `_problems`
construction) applies the identical filter. Crucially, `isReady` (the
readiness computation) reads `el.problems` **directly** — confirmed by
reading the function: no `ignore` parameter, no filter, nothing routed
through `elementProblems` at all — matching § 7's "never the readiness
computation itself" exactly.

**Validity rules confirmed in `core/config.ts`'s `validateProblems`**:
a code with no `SEVERITY` entry at all → `config:unknown_code` (warning,
skipped — `sev === undefined`); a recognised code whose severity isn't
`'warning'` → `invalid_config` (`errs.push(...)`, not a warning) — this
is the one axis (error-severity and `incomplete:*`) that can never be
silenced, confirmed structurally, not just by the two AC-49 legs (I3,
I4) that exercise it. `readProblems` additionally re-filters to
`SEVERITY[c] === 'warning'` before the list ever reaches `isReady`-
adjacent code, so even a hypothetical validation gap couldn't let a
non-warning code leak into the suppression set.

**Live reproduction**, each confirmed:
- `problems.ignore: ["done:no_acceptance"]` suppresses it from `show`'s
  `_problems`, `doctor`'s findings, and write feedback, while
  `incomplete:acceptance` (a different, non-ignorable code on the same
  element) still fires — matches I1 exactly, re-confirmed independently.
- `config:unknown_key`/`config:unknown_code` are themselves eligible for
  `problems.ignore`, per § 7's own closed list (both warnings) — not
  exercised independently this round beyond AC-49's own I5/J1/J2 legs,
  which already cover it.

**The finding.** AC-49's I8 sets out to prove "`unknown:status` (a
warning that *also* blocks `--ready`) still blocks `--ready` even while
ignored" — the one case meant to distinguish "suppressing the report"
from "fixing the underlying defect." I mutated `isReady`'s
`BLOCKS_READY` check to respect `cfg.problems.ignore` (`BLOCKS_READY.has(c)
&& !cfg.problems.ignore.includes(c)` — i.e., the exact bug I8 is written
to catch) and reran AC-49 directly: **all 91 checks still passed.**
Tracing why: `isReady` (`core/derive.ts:32-35`) checks `el.status !==
cfg.statuses[0]` *before* the `BLOCKS_READY` loop even runs. Cross-
referencing `BLOCKS_READY` (`core/constants.ts`) against § 7's
warning-severity, ignore-eligible codes, the only two codes in both
sets are `unknown:status` and `done:open_children` — and both are
*structurally* incompatible with `el.status === cfg.statuses[0]`:
`unknown:status` means the status isn't any configured value at all
(so it can't equal `statuses[0]`, which is configured), and
`done:open_children` is only ever added when `el.status === 'done'`
(`core/load.ts`'s `markOpenChildren`, guarded by `if (el.status !==
'done') continue;`) — and `validateConfig` requires the *last* status
to be literally `'done'` with at least two entries, so `statuses[0]`
can never itself be `'done'`. **Every element that could ever carry one
of the two ignorable, `BLOCKS_READY` codes already fails the earlier
status-equality check on its own, for a completely independent reason**
— so the `BLOCKS_READY`-respects-`ignore` loop this mutation targets is
currently unreachable by any input the data model can produce, and no
test (I8 included) can distinguish correct from broken behaviour there.
**This is not a product defect** — the spec's own guarantee ("ignoring
a warning does not change readiness") holds for every input that
exists today, just not *because* of the mechanism I8 is written to
check; it holds because the two candidate codes are confounded by an
earlier, unrelated gate. Worth flagging to the Oracle: either note this
structurally-unfalsifiable state explicitly (so a future `BLOCKS_READY`
code that *can* coexist with `statuses[0]` gets a real test when it's
added), or restructure `isReady` so the two checks are independent of
each other, if testability here matters enough to invest in.

`src/core/derive.ts` restored after this mutation; `tools/bundle.js
--check` confirms byte-identical.

## 3. Config forward compatibility (D166, with its correction)

**Diff review.** `TOP_LEVEL_KEYS` (`core/config.ts`) lists exactly the
seven recognised keys; any other key at the top level, or inside
`layout`/`layout.folders`/`claims`/`problems`, produces a
`config:unknown_key` *warning* (`warnings.push`), never `errs.push` —
confirmed by reading every one of the four nested-block validators
(`validateLayout`, the folders sub-check, `validateClaims`,
`validateProblems`), each with the identical pattern. `minVersion`'s
running-version comparison happens in `loadConfig`, **before**
`validateConfig` is even called — confirmed structurally (the
short-circuit `return` happens first) — so a too-new `minVersion`
never reaches the generic validation path and its own
`needs_newer_nj` is the only code produced. `context()` (`core/context.ts`)
checks `needsNewerNj` unconditionally, before the `tolerateConfig`
branch `doctor` uses to exempt itself from `invalid_config` — so
`doctor` is **not** exempt from `needs_newer_nj`, matching spec's "there
is nothing `doctor --fix` could repair about the running binary's own
version."

**Live reproduction:**
- `nj --version` and `nj <command> --help` both still succeed against a
  backlog whose `minVersion` is `99.0.0` (confirmed exit 0 for both) —
  neither resolves/validates the config at all, structurally.
- `parseVersionTuple`/`compareVersionTuples` (`core/version.ts`) verified
  directly in Node against every DECISIONS 166 example: `"3.9.0"` <
  `"3.10.0"` (numeric, not lexicographic) — confirmed `true`.
- **The read-only, live check against the real, installed older
  binaries**, as asked: built a fresh config at HEAD, added `"problems":
  {"ignore": []}` and `"minVersion": "3.5.0"` to it, then ran both
  `workspace/bin/nanojira/3.5.0/nj` and `…/3.6.0/nj` against it —
  **both still succeed** (`nj list` → `(no matching elements)`, exit 0),
  confirming the D166 correction (unknown top-level keys were always
  silently ignored by older binaries, never rejected) holds for the two
  real, installed builds other teams are running, not just as an
  assertion.
