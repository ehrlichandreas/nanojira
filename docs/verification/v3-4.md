## Findings

### G1 — low: a crash between step 0's two renames can leave a stray, unreferenced `.ids/`

If the process dies after renaming `.nanojira.json` → `.nanojira/config.json`
but before renaming `.ids/` → `.nanojira/ids/`, the backlog is no longer
`ctx.legacy` (the v3 config now exists), so it's read as a v3 backlog
missing its ids folder: `doctor` reports `backlog:ids_missing` +
`id:no_tombstone`, and `--fix` backfills **fresh** tombstones at
`.nanojira/ids/` for every element — correct recovery, confirmed. But the
**original** `.ids/` directory, with the original tombstones for the same
IDs, is never referenced, reported, or removed again; it sits in the
backlog forever as two empty-looking folders doing the same job. Harmless
(never-reuse is still protected, doubly so) but a cosmetic leftover a user
would have to notice and clean up by hand — nothing in `nj` ever will.
Low priority; not blocking.

### G2 — low–medium: a crash *after* both renames but *before* the `.gitignore`/README fixups permanently and silently skips them

This is the one worth fixing. `fixStep0` only runs the `.gitignore` and
README replacements as part of the *same* invocation that does the two
renames; `doctorFix` only calls `fixStep0` `if (start.legacy)`. Once both
renames land, `ctx.legacy` is false on every later run — step 0 can never
run again, for any reason, on that backlog.

```sh
# simulate: rename config + ids by hand (as step 0 would), stop there
mv backlog/.nanojira.json backlog/.nanojira/config.json   # (into a fresh .nanojira/)
mv backlog/.ids backlog/.nanojira/ids
# .gitignore still says ".nanojira-index.json"; README.md is still v2 text
nj doctor --json      # {"ok":true,"problems":[]}  -- clean, nothing flagged
nj doctor --fix       # fixed: ["regenerated STATUS.md"] -- .gitignore/README untouched
```

Both files stay wrong forever, with **zero** signal from `nj` at any point
— not a warning, not a note, not an exit code. The `.gitignore` consequence
is real, if modest: the line still ignores `.nanojira-index.json` (the v2
cache name), not `.nanojira/index.json` (the v3 one), so once the search
index exists it's no longer actually gitignored by that pattern and risks
an accidental `git add`.

This is a narrow window (two back-to-back renames), but it's exactly the
"crash mid-step-0" scenario the task asked me to probe, and migration is a
once-per-backlog operation a crash can hit at any instruction boundary —
machine loses power, OOM-killer, `kill -9` from a supervising script.
**Fix:** make the `.gitignore`/README fixups independent of `ctx.legacy` —
run `fixGitignore`/`fixReadme` (idempotent either way: they already check
for exact-match-replace-once and no-op otherwise) once per `--fix`
regardless of whether step 0 itself ran this time, or at minimum have
`doctor` warn when `.gitignore` still contains the literal v2 pattern on an
otherwise-v3 backlog.
