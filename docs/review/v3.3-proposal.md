# Review — proposal v3.3, MCP wrapper (`38dfa99`, D122/D144)

Verifier, 2026-10-04. Independent review, assigned by the Lead. Work in
`/tmp/verifier-v33` (detached worktree at `38dfa99`). Removed before
writing this. Read: `docs/proposals/v3.3.md` in full, DECISIONS 122/143/
144 in full, `src/core/args.ts`/`context.ts` (to check the confinement
and schema-exclusion claims against actual code, not just prose),
`test/ac/ac-15-no-dependencies.js` (the existing dependency-freedom
test's exact methodology). Checked the proposal's protocol claims
against the **currently published MCP specification, revision
`2026-07-28`** (fetched live — this post-dates my training data, so I
did not rely on memory for it), specifically its versioning,
stdio-transport and cancellation pages.

**VERDICT: needs changes.** The architecture is sound and the scoping is
disciplined (§ 6 below) — this is not a rewrite. But one protocol-level
gap is substantial enough to need explicit text before promotion (the
proposal was written against an older MCP versioning model than what is
currently published), and two confinement/testability gaps are concrete
and cheap to close. None of the four require rethinking the design;
all four are additions to the proposal's own text, each traceable to a
specific section.

## 1. Protocol — mostly sound for its target era, but silent on the current spec's versioning model

**Checked against MCP spec revision `2026-07-28`** (the "current"
revision as published at the time of this review — fetched live from
`modelcontextprotocol.io`, since this is dated after my training
cutoff). This revision is a genuine protocol-model change from what
the proposal describes: **every request now declares its own protocol
version via a per-request `_meta` field, the server accepts or rejects
each request independently, and there is no longer a single
session-wide `initialize` handshake** — that handshake model is now
called "**legacy**" (`2025-11-25` and earlier), with "**dual-era**"
servers/clients supporting both. The spec's own compatibility matrix is
explicit: a server implementing *only* the legacy handshake (exactly
what § B describes: `initialize`, `tools/list`, `tools/call`, the two
notifications, nothing else) is fully compatible with **legacy** and
**dual-era** clients, but a strictly **modern**-only client talking to
such a server is listed as **"Fails."**

**This is not necessarily a defect in the design** — it's a defect in
the proposal's *text*, which asserts "the client sees the server's
declared version in the response and disconnects if it cannot work with
it" as if that's still the only model, without acknowledging the
current spec has moved past it. Two things make this *probably*
survivable in practice, and I'd like them stated rather than assumed:

- The spec's own backward-compatibility page describes exactly how a
  **dual-era** client detects a legacy server: it sends `server/
  discover` first; `nj-mcp` (having no such method) answers with the
  standard unknown-method error, `-32601` — **which is exactly what
  § B already specifies for any unknown method**, with no special
  casing needed. A dual-era client correctly reads that as "legacy,
  fall back to `initialize`" and proceeds normally. So § B's existing,
  minimal design already happens to interoperate correctly with
  dual-era clients, by the general unknown-method rule it already has
  — this is worth saying explicitly in the proposal, as the reason the
  hand-rolled minimal subset is still sufficient, rather than leaving a
  reader to wonder whether `2026-07-28`'s existence invalidates § B.
- A strictly **modern**-only client (one with no legacy fallback at
  all) is the one combination that fails outright. Whether that's a
  real population `nj-mcp` needs to interoperate with depends on which
  client the project's own agents actually use when `nj-mcp` ships —
  which this review can't answer, but the proposal should at least name
  the question and the chosen scope (legacy + dual-era, not modern-only)
  as a deliberate decision, the same way § G names deliberately
  excluded scope elsewhere.

**Recommend**: add a short paragraph to § B stating which protocol era
`nj-mcp` targets (legacy handshake, relying on dual-era clients'
`server/discover` probe falling through via the existing unknown-method
path), and noting this is a scope decision, re-examined if the official
SDK client used in § F's tests ever drops legacy/dual-era support
entirely. This doesn't require re-opening B-1's ruling — the hand-rolled
minimal subset is still the right call — it requires the proposal to
show its awareness of the current spec rather than read as if the
handshake model it describes is still the *only* one.

**Everything else checked against `2026-07-28` holds up:**

- **stdio framing** (newline-delimited, no embedded newlines, stdout
  carries only valid MCP messages, `stderr` free for logging): unchanged
  from the proposal's description, confirmed against the current
  transport page verbatim.
- **`notifications/initialized`**: correctly described (client → server,
  post-handshake, fire-and-forget).
- **`notifications/cancelled`, accepted as a no-op**: confirmed
  spec-compliant, not merely defensible-by-reasoning. The current spec:
  "Servers receiving cancellation notifications **SHOULD** ... not send
  a response for the cancelled request" (a SHOULD, not a MUST) and "The
  client **SHOULD** ignore any response to the cancelled request that
  arrives afterward" — i.e. the protocol already expects and tolerates
  exactly what § B chooses to do (finish anyway, send the response). The
  proposal's own safety reasoning (killing a write mid-flight is exactly
  the half-done state § 12 exists to prevent) is good additional
  justification, but isn't even strictly necessary — the baseline
  protocol already permits this.
- **Error codes** `-32700`/`-32600`/`-32601`: correctly used. **Not
  addressed: `-32602` (Invalid params).** The proposal doesn't say
  whether a `tools/call` whose `arguments` don't match the tool's
  declared schema (missing required field, wrong type) is reported as a
  JSON-RPC-level `-32602`, or passed through to `dist/nj` and reported
  as a *tool* error (`isError: true`) when the CLI itself rejects it
  (`missing_argument`, etc.). Both are defensible; the proposal should
  pick one and say so — right now a reader has to guess whether schema
  validation happens in `nj-mcp` before spawning the child, or is left
  entirely to the CLI's own validation surfacing as a tool-level error.
- **`capabilities` in the `initialize` response**: not mentioned at all.
  A real client's handshake normally inspects the server's declared
  `capabilities` (at minimum `{tools: {}}`, since § G already rules out
  resources/prompts/logging) before calling `tools/list`. Cheap to add
  one sentence; currently a silent gap a strict client could trip on.

## 2. Process-per-call — sound by construction, two confinement/mechanism gaps worth stating explicitly

**Concurrency and pipelining**: correctly handled *by construction*, not
by any special logic the proposal needs to add — each tool call spawns
its own `dist/nj` child and gets its own JSON-RPC response correlated by
request `id`; concurrent/pipelined calls are just concurrent children,
each going through § 12's own compare-before-write exactly as any two
concurrent CLI invocations already do. No new concurrency model exists
to get wrong, consistent with D-1's own framing.

**Zombie/orphan handling**: not addressed in the proposal text at all.
If `nj-mcp` itself is killed (or crashes) while a spawned `dist/nj`
child is mid-write, that child is reparented, not killed — a narrow,
low-probability risk given `nj` writes are already short-lived and
protected by atomic rename, but worth one sentence (e.g. "each child is
spawned and awaited; the server does not detach children, so an
orphaned child can only outlive a crashed server, never a cleanly-
exited one"). Implementation-level, not a blocker.

**Environment passing — `NJ_AUTHOR`/`NJ_NOW`**: both are ordinary
environment variables; standard child-process spawning inherits them
automatically, so no special design is needed, and the proposal doesn't
need to say anything beyond what § C-4 already states (the `as`
parameter defaults to the server's own `NJ_AUTHOR`). Checked — not a
gap.

**Environment passing / backlog pinning — `--backlog`, the one real
gap.** § A says `nj-mcp` resolves its backlog once at startup and
"serves that one backlog for the life of the process." The proposal
never states the *mechanism*: does every spawned `dist/nj` child get an
explicit `--backlog=<the exact path resolved at startup>` (or the
equivalent `NJ_BACKLOG`), or does each child simply inherit `nj-mcp`'s
own `cwd`/environment and **re-run its own § 4 search**? The difference
matters: a child that re-resolves from scratch could, in principle,
land on a *different* backlog than the one `nj-mcp` itself resolved, if
anything in the search path changes between server startup and a later
tool call (a `.njrc` edited, a symlink swapped, even the njrc-swap race
this project just spent two rounds hardening against). **Recommend**:
state explicitly in § A or § D that every spawned child receives
`--backlog=<the server's own resolved path>` explicitly, so the "one
backlog for the life of the process" guarantee is mechanical, not
incidental.

**Is backlog confinement actually airtight against a crafted tool
argument? Checked directly in source, not just read as asserted.**

- **`--file` cannot be used to address a path outside the backlog.**
  Confirmed in `src/core/context.ts`'s `resolveTarget`: a `--file=<path>`
  (even an absolute one, which § 9 explicitly permits) is only ever
  resolved against `ctx.elements` — the set of files `nj` already
  discovered by scanning the *confined* backlog tree. A path outside
  that tree, or one that doesn't match any already-scanned element,
  always comes back `not_found`. `--file` is a disambiguation lookup
  into an already-known set, never an arbitrary-path write primitive —
  this holds for `nj-mcp` exactly because it holds for the CLI it
  shells out to, unchanged.
- **Can a tool's generated input schema (§ C-2) accidentally expose a
  `backlog` parameter, reopening the per-call override § A explicitly
  rejects?** This is the one place the proposal's own design (schema
  generated mechanically "from the same per-command flag table the
  CLI's argument parser reads") creates a real risk if read too
  literally. Checked `src/core/args.ts`: `--backlog` is **not** part of
  any per-command flag table — it's injected separately via a
  module-level `GLOBAL_CONTROLS` constant, combined with each command's
  own table only inside `checkFlags` itself. This means a schema
  generator reading from the **per-command** table (as § C-2 literally
  says) would exclude `--backlog` *by construction*, without needing a
  special exclusion rule — reassuring, and not a coincidence (whoever
  wrote this architecture apparently already separated "global" from
  "per-command" controls for exactly this kind of reason). **But the
  proposal doesn't say so, and none of AC-32..36 test for it.** An
  implementer who instead generates schemas from "every flag `checkFlags`
  would accept" (the natural reading of "shares the same validation"
  elsewhere in § C-2's own text) rather than strictly the per-command
  table would reintroduce the exact loophole § A rules out. **Recommend**:
  state explicitly in § C-2 that schema generation reads the per-command
  table only, excluding `GLOBAL_CONTROLS` (`--backlog`) and `--json`
  (meaningless for a tool whose result is always structured), and add
  an acceptance criterion asserting no generated tool schema contains a
  `backlog` field — cheap, and it's exactly the kind of drift the
  `COMMANDS`-array precedent (cited in § C-2 itself) says this project
  has already been burned by once.

## 3. Schemas from a shared flag table — the refactor's correctness proof is appropriately strong

**AC-36 (replay against `c7-baseline`) is a reasonable, well-precedented
proof mechanism, not a weak point.** This project has used exactly this
replay-gate technique to catch (and in one case, to confirm the absence
of) real behavioral drift at every turn this round — the batch-writes
refactor, the before-compare catchability fix, the claim/release
key-order regression, the njrc-swap ENOENT fix all leaned on the same
full-corpus byte-replay to prove "no observable change" rather than
asserting it. A corpus this large (6313+ calls across the full suite) is
a strong, not merely nominal, check that the flag-table move changes no
CLI-observable behavior. The residual risk (a case not yet in the
corpus) is the same limitation every replay-based proof in this project
already accepts, not something specific to this proposal. No changes
needed here.

## 4. Safety — the gating choices are sound; checked for anything else that should be gated

**`doctor --fix`'s gate is schema-level, not call-time**, confirmed by
the proposal's own framing (§ E: "absent from `tools/list` unless...")
— if the `--allow-destructive` flag is off, there is no schema entry a
client could even construct a call against. This is the right shape:
a launch-time decision the operator's client configuration makes,
unreachable from inside a tool call. `rm` is omitted unconditionally
(not merely gated) — also schema-level, the strongest form of "not
offered."

**Considered whether anything else on the tool list should be gated,
and didn't find one.** `claim --steal=<holder>` forcibly takes over
another holder's claim — the closest candidate to "destructive" left
ungated — but this is already an ungated CLI feature today (§ 12a), not
something MCP newly exposes, and its effect (reassignment, not data
loss) doesn't rise to `rm`'s or `doctor --fix`'s level. `archive`/
`unarchive` being offered ungated is correctly justified (mutual
inverses, § 11a). I don't see a write on the list that needs a gate the
proposal missed.

## 5. Testability — the SDK-as-devDependency precedent is sound (already explicitly ruled); one concrete, cheap addition recommended

**D144 (B-1) already explicitly ruled on the devDependency question** —
this isn't open for me to re-litigate, and the proposal faithfully
reflects that ruling (§ B, § F). I did check one adjacent point the
ruling doesn't directly cover: does a test-only SDK client dependency
conflict with `ac-15-no-dependencies.js`'s existing guarantee? No —
confirmed by reading that test's own methodology: it copies `dist/nj`
*alone* into a bare directory and confirms it still runs, checking the
**shipped artifact**, not `test/`'s own tooling. Since `@modelcontextprotocol/
sdk` is explicitly never bundled into `dist/nj-mcp` (§ B), this guarantee
is unaffected by construction.

**But there is no equivalent acceptance criterion for `dist/nj-mcp`
itself.** AC-15 exists specifically to prove `dist/nj` ships with zero
runtime dependencies — `dist/nj-mcp` makes the identical claim (§ B:
"genuinely zero new dependencies, even at build time"), but none of
AC-32 through AC-36 re-assert it for the new artifact. **Recommend**:
add a criterion mirroring AC-15's own methodology (copy `dist/nj-mcp`
alone into a bare directory, confirm it still starts and completes an
`initialize`/`tools/list` round-trip) — cheap, directly reuses an
existing, already-trusted test pattern, and closes the one place the
proposal's central "no new dependency tree" claim (the entire reason
for B-1's ruling) isn't independently checked for the new binary the
same way it already is for the old one.

**How the replay gate and `run-all.js` integrate the MCP harness**: § F
describes a small `test/` harness plus "a handful of representative
calls driven through `nj-mcp` ... diffed against the same corpus's
CLI-direct results," but doesn't say whether this lives inside
`baseline.js`/`gate.js` itself (which are currently dependency-free,
same discipline as `test/`) or as a separate script. Minor clarity gap,
not a blocker — worth a sentence in § F once implementation starts.

## 6. Over-engineering check

**None found; if anything the proposal is notably disciplined.** The
hand-rolled protocol subset is deliberately minimal (3 methods, 2
notifications, nothing speculative); § G explicitly excludes resources/
prompts/other transports/auth with reasoning tied to this project's
actual trust model, not hypothetical future need; the tool surface
(13 commands) tracks the CLI's own existing surface one-for-one rather
than inventing new groupings or conveniences. `nj-mcp`'s own
`--backlog` CLI flag (§ A's "Shape") mirrors the CLI's own existing
flag, not new complexity. I don't see anything added beyond what an
MCP-speaking agent actually needs to do what the CLI already does.

## Summary

Four items need the proposal's text updated before promotion, none
requiring the design to change:

1. **(§ B)** State explicitly which MCP protocol era `nj-mcp` targets
   against the currently-published spec (`2026-07-28`, which has moved
   to a per-request versioning model) — note that dual-era clients'
   `server/discover` probe already falls through correctly via the
   existing unknown-method path, and name the modern-only-client gap as
   a deliberate, acknowledged scope choice.
2. **(§ A/§ D)** State explicitly that every spawned `dist/nj` child
   receives `--backlog=<the server's own resolved path>`, so backlog
   confinement is mechanical, not incidental.
3. **(§ C-2 + a new AC)** State explicitly that schema generation reads
   the per-command flag table only, excluding `--backlog`/`--json`, and
   add an acceptance criterion asserting no generated tool schema
   contains a `backlog` field.
4. **(§ F + a new AC)** Add an AC-15-equivalent for `dist/nj-mcp` itself
   (copy-alone-and-run), mirroring the existing test's own methodology.

Two minor clarifications worth a sentence each, not blocking: how
`-32602`/schema-validation failures are reported (protocol-level vs.
tool-level), and whether `initialize`'s response declares a
`capabilities` object.
