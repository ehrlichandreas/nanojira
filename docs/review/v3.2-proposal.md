Verifier, 2026-10-03. I wrote none of this proposal; independent review
assigned by the Lead before any promotion (D122/D123), proportionate to
scope — most of v3.2 is not concurrency-heavy, so this reads closer to my
NJ_AUTHOR/unarchive reviews than the claim-protocol one. Work in

`test/` touched. Read: the full proposal; current § 4, 5, 7, 8, 9, 12, 12a,

real code); DECISIONS 122/123.

## Verdict: **needs changes** — a short, precise list, none of them a redesign

The core designs are sound and each reuses existing machinery correctly
(§ A reuses `set`'s guarded write; § B adds no new mechanism, just a
`doctor` reading what `_claim` already carries; § C is a pure read reusing
the already-loaded body; § D explicitly disclaims "no new mechanism, just N
uses of the existing one," and that claim mostly holds). One finding is a
genuine internal contradiction that would mislead whoever builds the test
fixtures from this text; the rest are precise, cheap text additions the
Oracle can fold in without touching any ruled decision.

## Required changes, in order of severity

### 1. (High) § D's own example output contradicts § D's own preflight/runtime split

§ D classifies `refused:archived` explicitly as a **preflight** condition,
twice — in the rules prose ("each command's own existing
refusal-before-anything-is-written conditions: an archived element
(`refused:archived`)... now checked once per ID up front") and again in
AC-31 ("A preflight failure on any one ID (… an archived element …) aborts
the **whole** batch — nothing is written for any ID"). But the pinned
example output directly under "Output — RULED" shows:

```json
{ "ok": false, "results": [
  { "id": "TSK-001", "ok": true, "changed": ["status"], … },
  { "id": "TSK-002", "ok": false, "error": "refused:archived" }
]}
```

TSK-001 is shown **successfully written** (`changed: ["status"]`) in the
same batch as TSK-002 failing with `refused:archived` — but if
`refused:archived` is preflight, and preflight failure on *any* ID aborts
writing for *every* ID, TSK-001 could never have been written at all. The
example and the rule cannot both be true. This isn't a nitpick: this
example is exactly what someone writing AC-31's actual test fixture, or
implementing the wrapper, will copy first. **Fix:** replace TSK-002's error
with a genuine *runtime* code — the text's own examples of runtime failures
are `changed_in_parallel`, `refused:claimed`, a `fault:<hook>` — e.g.
`{"id": "TSK-002", "ok": false, "error": "refused:claimed"}`, which
correctly illustrates "one succeeds, one fails at runtime, in the same
batch" without contradicting the preflight rule.

### 2. (Medium) `STATUS.md` regeneration count for a batch is unstated

§ 13 ("Writes, with `STATUS.md`") measures and accepts a ~12–14% cost per
single write for the full-scan regeneration. § D never says whether a
batch of N IDs regenerates `STATUS.md` **once**, after the whole batch, or
**N times**, once per ID's own write — and since § D's own framing is "no
new mechanism, just N uses of the existing one," the unstated default is
almost certainly N regenerations, which is N× the already-measured
per-write cost, compounding linearly with batch size for a feature whose
whole motivation is doing N things in one call instead of N calls.
**Recommend:** rule it explicitly — regenerate once, after every ID's
write phase completes — both for the obvious performance reason and
because it matches the "one atomicity story instead of three independent
ones" motivation § D opens with: a `STATUS.md` that settles once, after
the batch, is a more honest "atomic report" than one that flickers through
N intermediate states no caller ever sees.

### 3. (Medium) A repeated ID in the same batch (`--id=A,A`) is not addressed anywhere

Searched the whole document: no mention of what happens when the same ID
appears twice in `--id=A,B,C`. Three readings are all plausible from the
text as written (process it twice — and does the second occurrence's
compare-before-write then spuriously fail with `changed_in_parallel`
against the first occurrence's own just-completed write, since nothing
distinguishes "the backlog moved because of someone else" from "the
backlog moved because of this same batch's own earlier entry"?; silently
dedupe to one write but two `results` entries; or treat it as a preflight
error) and the proposal rules none of them. Given `results` is defined as
"one entry per ID, in the order `--id` named them" — a caller zipping
`results` against its own `--id=A,B,C` string would get two entries
either way, with genuinely different plausible outcomes depending on which
reading ships. **Recommend:** rule this explicitly; the cheapest, least
surprising choice is probably a preflight `invalid_value` for a batch
containing a repeated ID ("each ID is resolved and validated" already
implies uniqueness is part of what preflight should check), but any of the
three is implementable — the proposal just needs to say which.

### 4. (Medium) The batch failure shape doesn't say whether `hint` survives

§ 9's generic failure shape is `{ok: false, error: "<code>", hint: "…"}`
(hint optional) — several single-write refusals carry a genuinely useful
hint (`refused:claimed`'s "use `--steal=<holder>`", `exists`'s "move or
delete it, then unarchive again"). § D's batch failure entry is pinned as
exactly `{id, ok: false, error: "<code>"}` — no `hint` in the shape, and no
sentence saying whether that's deliberate (dropped for batch simplicity) or
just an abbreviated example that still allows the optional field. **Fix:**
one sentence either way — I'd lean towards keeping `hint` as optional here
too, the same way § 9 already does for the single-write shape, since a
failed batch ID is exactly where an agent most wants the recovery hint and
there's no cost to keeping the field optional.

### 5. (Medium) Claim-age staleness is never tied to `NJ_NOW`

§ 12 pins `NJ_NOW` as the deterministic-testing clock for **every**
timestamp-sensitive behaviour in the spec ("if set, every timestamp the
tool writes... uses exactly this value... it exists so that AC-2's
byte-exact golden comparison needs no normalisation"). § B's `claim:stale`
condition is `now − _claim.since` exceeds the threshold — and "now" is
never connected to `NJ_NOW` anywhere in § B or the rest of the proposal
(the only `NJ_NOW` mention in the whole document is in § C, as an analogy
for why `find` uses `toLowerCase()` not `toLocaleLowerCase()` — unrelated).
Without this, AC-29 ("An element claimed more than `claims.staleAfterHours`
… ago reports `claim:stale`… one claimed less than the threshold ago does
not") cannot be written as a byte-deterministic test the way every other
criterion in this spec is — a test would need either real wall-clock
waiting or a claim timestamp picked "far enough in the past relative to
real `Date.now()`," which is exactly the un-pinned-clock problem `NJ_NOW`
exists to eliminate. **Fix:** one sentence in § B stating that the "now"
`doctor`/`list`/`show` use for the staleness comparison is `NJ_NOW` when
set, matching § 12's existing discipline.

### 6. (Low) The new `claims` config block doesn't say what an unknown key inside it does

§ 5 sets a clear precedent for exactly this shape of question: "An unknown
key inside `layout` or `layout.folders` is invalid — a typo must not
silently fall back to a default." § B's new `.nanojira/config.json`
`"claims": {"staleAfterHours": 24}` block is directly analogous (an
optional, nested object with one currently-defined key) but the proposal
only validates the **value** of `staleAfterHours` ("a non-integer or
negative value is `config:invalid`") and says nothing about a sibling key
inside `claims` that isn't `staleAfterHours`. **Fix:** one sentence,
modelled on `layout`'s own: an unknown key inside `claims` is
`config:invalid`, the same typo-safety the rest of § 5 already has.

### 7. (Low) Checkbox-marker scope is shown by example only, not stated as a rule

The task I was given names this precisely, so I checked it precisely:
every mention of the pattern `nj check` scans for in the proposal shows
only `- [ ]`/`- [x]` (the dash marker) — matching § 7's own canonical
example, which also only shows dash-prefixed checkboxes. CommonMark (and
Markdown generally) also permits `*` and `+` as equivalent unordered-list
bullets, and some flavours tolerate a checkbox after a numbered marker
(`1. [ ]`); the proposal never states whether `nj check` recognises any of
these, or deliberately scopes to `-` only. Rule #4 ("flips exactly the one
character inside the brackets... not the line's leading whitespace")
implies indentation (hence nested lists) is tolerated, but doesn't resolve
the bullet-*character* question. Separately: the write side says ticking
"normalise[s] to lowercase" — but nothing states whether an **already**
uppercase `[X]` (a plausible hand-edit) is recognised as "ticked" on
*read*, for both counting and for `--off`'s no-op check (rule 3: "`--off`
on an already-empty [box] exits 0... writes nothing" — is `[X]` "already
empty" or "already ticked" to this logic?). **Fix:** one sentence stating
the exact marker set (`-`, and whether `*`/`+`/numbered) and whether `X`
(uppercase) counts as ticked on read, not just on write.

## Not a required change, but worth recording

- **`not_found` reused for "no such checkbox"** (the task's own question:
  can an agent tell "element missing" from "no such checkbox" apart?). As
  written, no — both produce the bare code `not_found` with no
  machine-readable distinction, only differing hint/prose text. I checked
  whether this is a *new* kind of ambiguity or consistent with the existing
  design: § 9's own failure-code table already reuses `not_found` for
  several conceptually distinct "the referenced thing isn't there" cases
  (`--parent`/`--depends-on`/`--file` naming nothing, a
  `--description-file` that can't be read, and — confirmed empirically in
  my V3.1-A/B/C work — the primary `--id` itself not resolving), none of
  which carry finer-grained codes either. So `nj check`'s reuse is
  *consistent* with established practice, not a regression from some
  stricter existing norm. That said, § 9 also states outright "agents
  branch on codes, never on prose" — and this is the one place where that
  promise is in genuine tension with a real diagnosability need (a caller
  that gets `not_found` from `nj check --text=…` cannot tell, from the code
  alone, whether to fix its `--id` or its `--text`). **Recommend: keep
  `not_found`** — changing it would be the first departure from an already
  multiply-precedented pattern, for a purely additive, optional
  improvement — but if the team ever wants better diagnosability here
  cheaply, a distinct code (purely additive, e.g. following
  `ambiguous_target`'s own naming style) is available with no other cost,
  since this is new behaviour with no existing callers to break.
- **Fence-indentation has no stated limit.** The fence-tracking rule
  ("matched at the start of a line after optional leading whitespace") sets
  no bound on that whitespace; CommonMark itself caps a fence's indentation
  at ≤3 spaces (4+ demotes it to an indented code block, a different
  construct). The proposal's unbounded reading is *more* permissive about
  what counts as entering/leaving a fence than CommonMark — which, for
  `nj check`'s purpose (never false-matching a checkbox-shaped line inside
  example code), is the safer direction to err in, not a defect. Not
  requiring a fix; worth one clarifying clause if the Oracle wants to close
  the gap to CommonMark precisely.
- **Nested/longer fences:** correctly specified. "Closed by a matching or
  longer fence of the same character" correctly implements CommonMark's
  rule that a fence is closed only by a same-character fence of length ≥
  the opening one — which is also exactly the mechanism that lets a longer
  outer fence "contain" a shorter fence-like line as literal content. No
  issue found.
- **`toLowerCase()` folding, edge cases.** The choice itself (never
  `toLocaleLowerCase()`) is correct and for the right stated reason
  (determinism, consistent with `NJ_NOW` pinning). Two known, narrow
  `toLowerCase()`-specific quirks exist regardless of locale and are worth
  being aware of, not fixing: Greek final sigma (`ς` vs `σ`) is not
  context-folded by `toLowerCase()`, so a needle/haystack differing only in
  final-vs-medial sigma position won't match; and U+0130 (LATIN CAPITAL
  LETTER I WITH DOT ABOVE) folds to a two-code-unit sequence (`i` +
  combining dot above) under plain `toLowerCase()`, a Unicode table fact,
  not a Turkish-locale one — an extremely narrow edge for an English-first
  task tracker, not worth spending round-one design budget on.
- **`nj find`'s performance claim, verified against real code, not just
  argued.** Checked `src/core/load.ts`: `loadElement()` unconditionally
  does `fs.readFileSync(file, 'utf8')` — the full file, body included —
  for every element, on every read command, today. `find`'s claim ("bodies
  are already parsed… adds one substring scan over text `nj` has already
  loaded, not a new read") is accurate, not aspirational: `list` already
  pays this cost (it must, to compute completeness per § 7, which requires
  reading `## Description`/`## Acceptance Criteria`), so `find` genuinely
  adds no new I/O.
- **E.1, the `njrc-swap` fault hook: sound, and correctly targeted.** The
  injection point — "between the ownership `lstat` and the `open()`" — is
  exactly the window TSK-029 T1's fix (`lstat`, then
  `open(O_RDONLY|O_NONBLOCK)`, `fstat`, read, one descriptor) closed; pausing
  there, with a poll-for-marker design copied from the already-proven
  `before-compare` hook, replaces the original flaky timing-based test with
  the same deterministic technique the rest of the suite already trusts.
  No structural concern found.
- **E.2, the stray `.ids/` cleanup: confirmed safe against a concurrent
  allocator, and for a stronger reason than "it's probably fine."** The
  cleanup only ever runs against a backlog that is **already v3** (not
  `backlog:legacy_layout`) — and on an already-v3 backlog, no live code
  path ever reads or writes the legacy `.ids/` location at all; every
  allocator call already targets `.nanojira/ids/` exclusively. There is no
  live writer to race against, by construction, not by a guard that could
  fail. Separately, the "only if every tombstone name is already mirrored"
  check can only ever be too conservative under a stale read (the mirrored
  set is monotonically growing — tombstones are never removed — so a
  stale read of `.nanojira/ids/` can under-count, never over-count,
  mirrored names), meaning any raciness in the *check itself* can only
  cause a safe "left alone, try again later" outcome, never an unsafe
  deletion of a tombstone that exists nowhere else.

## Consistency with the current spec and D123

Checked § 7's existing byte-for-byte exceptions (H1 sync, `nj note`,
section-role writes) and the "not fenced-code-aware... deliberately out of
scope for round one" rule § A explicitly carves an exception against: the
proposal's own framing ("the one place in the spec where fence-awareness
exists; § 7's general rule is otherwise unchanged") is accurate and doesn't
overreach into claiming anything about section writes. Checked the closed
code tables (§ 7 problem codes, § 9 failure codes): `ambiguous_target` and
`claim:stale` are both genuinely new strings, no collision with anything
existing. Checked § 12a's `claim`/`release` step-1 refusal list against
§ A's and § D's own "step 1" lists for `check`: all three name the same two
preconditions (archived, unreadable-stub-for-this-element-only) with the
same reasoning (a claim/check reserves or edits one element and moves
nothing, so the backlog-wide stub guard doesn't apply) — consistent.
Checked § 13's trigger (~12,000–15,000 elements) against `find`'s claim of
sharing the scan path with no new cost model — confirmed by code, above.
No contradiction found with any D123 ruling's own text; the gaps above are
all places the proposal is *silent*, not places it *contradicts* a ruling.
